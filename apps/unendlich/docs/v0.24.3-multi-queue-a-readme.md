# v0.24.3-multi-queue-a — Compute queue acquired, mesher unchanged

First step of the multi-queue work. **Adds a separate compute queue
to `VulkanContext` without using it.** The mesher still submits to
the graphics queue, exactly as before. No behavior change is
expected; no perf delta is expected.

This is Ship A of the planned three-ship sequence:
- **Ship A (this one)**: compute queue created, unused. Validates
  that the device-create plumbing works on Honeykrisp without any
  behavior change.
- **Ship B (next)**: mesher flips to use compute queue. Adds semaphore
  sync. Real async-compute behavior.
- (Ship C if needed): tuning, ownership transfers, edge cases.

## Why three ships, not one

c.17-a's regression is the cautionary tale. Adding a single Vulkan
feature flag (multiview) caused 5ms/frame CPU recording overhead for
reasons we still don't fully understand. Multi-queue work touches
the same `create_device` code surface, with more changes than c.17-a
had. Splitting into A→B→C means:

- If Ship A causes a regression, we know it's from the queue/device
  plumbing alone — there's nothing else to confound the bisect.
- If Ship A is clean, we ship B with confidence that the device-create
  part is solid, and any regression in B is from the mesher submit
  path specifically.

## What Ship A does

1. **`pick_physical_device` scans for a dedicated compute queue family.**
   Looks for any queue family with `COMPUTE_BIT` set but `GRAPHICS_BIT`
   NOT set. On most desktop GPUs (NVIDIA, AMD, Intel discrete) this
   exists. On integrated GPUs and on Apple silicon via Honeykrisp,
   probably not — those typically expose a single queue family that
   does everything.

2. **If no dedicated compute family**, fall back to using the graphics
   family. If that family supports >= 2 queues, request 2 queues with
   priorities `[graphics=1.0, compute=0.5]`. The lower compute priority
   signals the driver that graphics work should preempt compute when
   both are ready. If only 1 queue is available, the compute queue
   handle ends up equal to the graphics queue handle (no benefit, but
   no breakage).

3. **`VulkanContext` gains four new fields:**
   - `compute_queue_family: u32` — family index used for compute.
   - `compute_queue: vk::Queue` — the queue handle.
   - `compute_queue_is_distinct: bool` — true iff using `compute_queue`
     provides any independence from `graphics_queue`. Ship B+ should
     short-circuit to the graphics queue if this is false.

4. **Startup logs report what we got.** Look for these lines:
   ```
   Picked physical device <name> (graphics qf=X, present qf=Y,
       compute qf=Z dedicated=<bool>)
   Compute queue family: index=Z dedicated=<bool> (graphics_qf=X)
   Compute queue acquired: family=Z distinct=<bool>
       (graphics handle reused: <bool>)
   ```

## What we're checking with Ship A's hardware run

When you run this ship on Honeykrisp, four possible outcomes:

**Outcome 1 — dedicated compute family exists.**
```
compute qf=N (N != graphics_qf), dedicated=true, distinct=true
```
Best case. Honeykrisp exposes async compute. Ship B will plug into
this directly.

**Outcome 2 — same family, multiple queues.**
```
compute qf=X (same as graphics_qf), dedicated=false, distinct=true,
graphics handle reused: false
```
Second-best. Same hardware lane but separate queue handle. The OS
scheduler can arbitrate. Ship B will still help but parallelism
may be smaller than Outcome 1.

**Outcome 3 — same family, single queue.**
```
compute qf=X (same as graphics_qf), distinct=false,
graphics handle reused: true (warning logged)
```
Worst case. Honeykrisp exposes only one queue. Ship B becomes
a no-op (we'd just be using the same queue). We'd file this as a
driver limitation and pivot to OS-level priority work or accept
the chug as platform-bound.

**Outcome 4 — device-create fails or DEVICE_LOST.**
Most concerning. Would indicate Honeykrisp's queue handling has
edge cases we triggered. We'd revert and investigate before any
Ship B work.

## Honest concerns

- **Multi-queue work on Honeykrisp is unmeasured territory** for this
  engine. The c.13-scout probe checked multiview capability; nothing
  has probed queue family layout before. Ship A's startup logs are
  the first measurement.

- **The `priorities_two = [1.0, 0.5]` choice** is a heuristic. Drivers
  may ignore it entirely, may use it as strong scheduling input, or
  may interpret it differently than expected. We can tune in Ship B
  if early results suggest the prioritization isn't doing what we
  want.

- **If we hit Outcome 3** (single queue, no separate handle), Ship B
  becomes pointless and we need to pivot. The right pivot is probably
  per-frame mesher work-budget limiting (cap mesh dispatches per
  frame so they don't pile up) — different shape of fix, would still
  reduce chug magnitude. Filed for that contingency.
