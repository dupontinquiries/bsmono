# v0.24.6-gpu-mesh-bench — GPU sparse mesher + comparison binary (Layer A.2)

Layer A.2 of the GPU-resident world arc. Layer A.1 (v0.24.5) added
the `SurfaceRecord` representation and `extract_surface` CPU function.
This ship adds:

1. The compute kernel `chunk_mesh_sparse.comp` that consumes
   `SurfaceRecord[]` and emits axis-aligned quads (one per face bit).
2. The Vulkan plumbing `render::gpu_meshing_sparse::SparseGpuMesher`
   that drives it: upload buffer, output buffers, pipeline,
   descriptors, dispatch, fence sync, readback.
3. A new bin `gpu-mesh-bench` that compares CPU naive mesher output
   to GPU sparse mesher output on a representative chunk grid.

This is NOT a production-wired path yet. The bin exists to **validate
the GPU mesher works on real hardware** before we trust it enough to
route real mesh requests through it. Once the bench reports topology
parity and reasonable performance, the next ship wires it into the
production meshing pool.

## How to use

```bash
cd ~/Code/unendlich-development/unendlich-game

git checkout -- assets/shaders/ 2>/dev/null

./commands/update_from_claude_zip.sh unendlich-v0.24.6-gpu-mesh-bench.zip
git add -A
git commit -m "Update to v0.24.6-gpu-mesh-bench (Layer A.2: GPU sparse mesher)"
./commands/tag_current_version.sh

# Build (note: requires both "render" and "gpu" features).
cargo build --release --features="render,gpu,hot-shaders" \
    -p unendlich-engine --bin gpu-mesh-bench

# Run.
cargo run --release --features="render,gpu,hot-shaders" \
    -p unendlich-engine --bin gpu-mesh-bench
```

The bench opens a hidden GLFW window only to satisfy `VulkanContext`'s
surface requirement; no rendering happens. A future "headless Vulkan
context" path would eliminate the window dependency.

## Expected output

For each chunk in the test grid (36 chunks total: chunk_y in [-1, 0,
1, 2] crossed with cx in [-1, 0, 1] and cz in [-1, 0, 1]):

```
  chunk     records    cpu_v      cpu_us      gpu_us  speedup    match
  -----------------------------------------------------------------
  (-1,-1,-1)    1843     7372         420        1820     0.2x  OK (1843)
  ( 0,-1,-1)    1742     6968         418        1683     0.2x  OK (1742)
  ...
```

What we expect to see:

- **Topology match: 36/36** — both paths produce the same number of
  quads per chunk. If a chunk shows MISMATCH, the kernel has a bug
  (likely face-mask interpretation or per-face emission count).
- **CPU times around 100-500 us/chunk** — typical for the existing
  naive mesher.
- **GPU times higher than CPU** for v1 — almost certainly. The GPU
  pays for: upload to HOST_VISIBLE, dispatch + barriers + fence wait,
  readback. Per-chunk the round-trip dominates the compute. For one
  chunk in isolation the GPU mesher is slower than the CPU. **This
  is expected.**

The point of v1 is correctness, not speed. v2 batches multiple chunks
per dispatch to amortize the round-trip; v3 (eventual) avoids readback
entirely by binding the GPU output buffers directly to the renderer's
vertex sources.

## What to look for

**Per-chunk topology parity** is the binary success criterion. If
36/36 match, the kernel is producing the right set of quads.

**Per-chunk timing** is informational. Don't read it as "GPU is
slower so this is failing" — read it as "single-chunk round-trip
cost on this hardware is X us." That number tells us how much
batching we need before the GPU path becomes a win.

## What this ship does NOT do

- **No production wiring.** Real chunks loaded during play are still
  meshed by the CPU mesher. The new path is only exercised via the
  bench binary.
- **No batching.** v1 dispatches one chunk per call. v2 will batch.
- **No greedy merging.** v1 emits one quad per face bit (matching the
  naive CPU mesher). The GPU output is more triangles than the
  greedy CPU mesher would produce. v2 considers greedy on GPU.
- **No lighting / AO / tints / sub-voxel decorations.** v1 emits
  flat per-block-type colors via a hash-palette. Visual regression
  vs the CPU mesher is intentional and accepted.
- **No headless Vulkan context.** Bench opens a hidden GLFW window.
  Filed for later.

## Honest concerns

1. **First-run risk on Honeykrisp.** This is the first time the
   sparse path is exercised against AGX firmware. The compute
   dispatch pattern matches the existing `gpu_mesher_vk` and
   `chunk_generation` shaders (both work on AGX), so I'm cautiously
   optimistic. If it crashes or produces wrong output, the bench is
   the right place to find out — it's isolated from gameplay.

2. **`block_color` palette is provisional.** v1 picks visually
   distinct colors per block type via a simple hash. Real lighting
   / climate-tint integration comes when we connect the kernel to
   the world model. Don't read color discrepancies between CPU and
   GPU output as a bug — they're expected for v1.

3. **`MAX_RECORDS_PER_CHUNK = 16384`.** Surface block count is
   typically 1500-3000. 16K is generous. A worst-case checkerboard
   chunk could exceed; the path returns `TooManyRecords` and the
   caller falls back to CPU. Not tested with adversarial input.

4. **`VERTEX_CAPACITY = 43_690`, `INDEX_CAPACITY = 65_535`.** Sized
   for 6 quads per record at worst case. If chunks regularly hit
   the index limit (~10K quads = ~60K indices), the kernel sets the
   overflow flag and we return `Overflow`. Caller falls back. Not
   tested.

5. **`Mutex<()>` serializes all `mesh_chunk` calls.** v1 is one-at-
   a-time. Concurrent meshing requires per-chunk command buffers
   and is filed for v3.

6. **Fence wait is blocking.** `mesh_chunk` blocks the caller until
   GPU completes. v1 fine for the benchmark; v2's production wiring
   needs to manage async dispatch + later collection so the bin's
   render loop isn't blocked.

## What comes next

Layer A.3 (next ship if bench reports parity): **production wiring**.
Route Near-LOD mesh requests through the GPU path behind
`UNENDLICH_GPU_MESHER=1`. Needs:

- Async dispatch model (don't block the mesh-worker thread on fence).
- Failure fallback (overflow / too-many-records → CPU mesher).
- Result handoff into the existing `MeshResult` channel.

After A.3 works: visual lighting integration (read sky uniform in
the kernel) and per-block tinting from world_model fields.

Layer B (GPU generator, already default via `Backend::Auto`) and
Layer C (octree storage) follow once meshing is production-stable.
