# v0.24.25-shader-bin-fix — the blank screen was stale SPIR-V

## TL;DR

The "blank screen after chunk loading completes" you've been seeing
since shipping the v0.24.20-vertex-pack work is the shader binaries
in `assets/shaders/*.spv` not being rebuilt from the post-v0.24.20
GLSL sources. This ship:

1. Rebuilds the 5 stale `.spv` files from current GLSL.
2. Rewrites `build.rs` so this can't happen again — recompile
   decisions now use a SHA-256 of the GLSL source stored next to
   the `.spv`, not file mtimes. Mtime comparison gave false negatives
   after `unzip` (archive mtimes preserved, GLSL and SPV got equal
   timestamps, `src_mtime > out_mtime` was false, stale `.spv` kept).
3. Writes a hash sidecar (`*.spv.hash`) next to every shipped SPV
   so first build after this update is a no-op rather than a forced
   recompile.
4. Adds a loud cargo warning the next time anyone ships a GLSL
   change without rebuilding the SPV.

No production code is touched except `build.rs`, the SPV binaries,
and the version strings. Cargo versions bumped to
`0.24.25-shader-bin-fix`.

## Why the screen was blank

The v0.24.20-vertex-pack ship replaced the 24-byte CPU `Vertex`
(3×f32 pos + 3×f32 color) with an 8-byte GPU-only `PackedVertex`
(A2B10G10R10_UNORM_PACK32 + R8G8B8A8_UNORM). It updated:

- The pipeline's `VertexInputBindingDescription` (stride: 8) and
  `VertexInputAttributeDescription`s (formats: A2B10G10R10 + RGBA8).
- The renderer's upload path to pack 8 bytes per vertex.
- The GLSL source `chunk.vert` and `chunk_shadow.vert` to declare
  `in vec4 in_pos_unorm` / `in vec4 in_color_unorm` and reconstruct
  world position from `chunks[gl_InstanceIndex].aabb_min`.

What it did NOT update: the compiled `chunk.vert.spv` and
`chunk_shadow.vert.spv` checked into the build tree. Those binaries
still declared `in vec3 in_position` (R32G32B32_SFLOAT, 12 bytes) at
location 0, and treated their input as the world position directly.

Running this combination:

| Component                        | Format                            |
|----------------------------------|-----------------------------------|
| Pipeline vertex-input attr 0     | A2B10G10R10_UNORM_PACK32 (4 B)    |
| Shader (stale SPV) input 0       | vec3 in_position, read as f32     |
| Pipeline vertex-input attr 1     | R8G8B8A8_UNORM (4 B)              |
| Shader (stale SPV) input 1       | vec3 in_color, read as f32        |

Vulkan validation can't catch this — the pipeline's job is to fetch
bytes in the declared format and deliver to the bound location. The
shader's job is to interpret them. The shader sees vec3 at location
0 and gets the first three normalized components of the
A2B10G10R10_UNORM_PACK32 decode — which are in `[0, 1]`. It then
multiplies these microscopic positions by `view_proj` and emits
clip-space coordinates inside a 1-block cube at world origin.

The player at world (0, 93, 0) is 93 blocks above this cube and
sees nothing regardless of camera direction. The terrain is there;
it's just being rasterized into the void.

The stale `chunk_cull.comp.spv` compounded it (the v0.24.20 GLSL
fixed `commands[slot].first_instance = i` from a hardcoded `0`), but
the vertex-shader mismatch alone is enough to fully blank the world.

## Why this fooled the investigation for so long

Every other symptom is consistent with the rendering pipeline being
healthy:

- `loaded` and `rendering` counts climbed normally (the renderer's
  bookkeeping is correct; it's the shader that's wrong).
- `main` pass GPU time was 50–100ms during chunk load and dropped
  to ~1ms in steady state. The drop is the well-documented
  "magic switch" from `DESIGN_NOTES.md` Increment 61: world-gen
  workers free their P-cores when `gen_pending` hits 0, GPU stops
  being CPU-starved. It happens whether or not anything is being
  rasterized — uploads contend with draws on the same memory bus,
  not on whether vertices land in-frame.
- `upload_fails: 0` (the renderer succeeded at every upload).
- Cull pass times (`0.04ms` steady) tracked the slot count, not
  the visible count.
- The "blank during loading also" observation (when ticks were off
  and on a fresh world) ruled out every world-state hypothesis.

The investigation tree from this session's first half (octree
work, edit paths, tick handlers, chunk version bumps) is all
correct — those things aren't the cause. The mesh-churn finding
(empty meshes for all-air sky chunks causing the queue to stay at
180/128) is a real efficiency bug but it's separate, pre-existing,
and unrelated to the blank screen.

## What changed in this ship

### `assets/shaders/*.spv` — refreshed binaries

Five SPVs were stale; all are now rebuilt from current GLSL:

| File                        | Old size | New size | Reason                                    |
|-----------------------------|----------|----------|-------------------------------------------|
| `chunk.vert.spv`            | 1832     | 3352     | v0.24.20 vertex-pack (CRITICAL).          |
| `chunk_shadow.vert.spv`     | 2120     | 3572     | v0.24.20 vertex-pack (CRITICAL).          |
| `chunk_cull.comp.spv`       | 6648     | 6664     | v0.24.20 `first_instance = i`.            |
| `chunk.frag.spv`            | 31832    | 31844    | Minor since v0.24.19 (comments / atmos).  |
| `froxel_fill.comp.spv`      | 17460    | 17476    | Minor since c.17 work.                    |

Compiled with `glslangValidator --target-env vulkan1.2`, same flags
the in-tree `build.rs` uses.

### `assets/shaders/*.spv.hash` — new sidecars

One per shipped SPV, content `sha256(<corresponding GLSL>)`. These
make the first build after this ship a no-op (no recompile triggered).

### `build.rs` — content-hash gating

The recompile decision is now:

```text
if sidecar_hash == sha256(current_glsl) && spv_exists: skip
else: compile, write sidecar
```

The mtime-based gate is gone. The script now also:

- Emits `cargo:rerun-if-changed=` for each individual shader file
  (the previous directory-watch is unreliable on some filesystems).
- On `glslc`/`glslangValidator` not installed AND a stale SPV
  detected (sidecar hash mismatch), emits a big visible warning
  with install instructions for Fedora/Asahi, Ubuntu/Debian, macOS.
  The previous "no compiler" path was silent when SPV files
  happened to exist — that's how this got past us in the first
  place.
- Carries the SHA-256 implementation inline (~50 lines, FIPS 180-4),
  no new crate dependency. Build scripts get their own dependency
  tree and adding a hash crate would slow every clean build.

## How to apply

```bash
cd ~/Code/unendlich-development/unendlich-game
git checkout -- assets/shaders/ 2>/dev/null
rm -f events.jsonl probe-*.csv

./commands/update_from_claude_zip.sh \
  ~/Code/unendlich-development/claude-zips/unendlich-v0.24.25-shader-bin-fix.zip

# Verify the fix shipped:
strings assets/shaders/chunk.vert.spv | grep -E "^in_"
# Expected: in_pos_unorm  /  in_color_unorm
# If you see in_position / in_color, the unzip didn't take.

git add -A
git commit -m "Update to v0.24.25-shader-bin-fix"
./commands/tag_current_version.sh

cargo build --release --features="render,gpu,hot-shaders" -p unendlich-engine 2>&1 | tail -30
cargo run --release --features="render,gpu,hot-shaders" -p unendlich-engine --bin unendlich-world
```

When you run, the world should be visible immediately — terrain
rendering through the cull/main passes at normal cost, the
`magic-switch` transition still happens at chunk-load-complete but
both phases now show actual geometry.

## How to verify the fix worked

Compare `strings` output of the bundled SPV:

```bash
strings assets/shaders/chunk.vert.spv | grep -E "^in_"
```

Expected output: `in_pos_unorm` and `in_color_unorm`.
If you see `in_position` and `in_color`, the binary is still stale —
something between the zip and your build clobbered the new SPV.

Run the engine briefly and check the log. Steady-state `main` pass
should now correlate with how much geometry is in your frustum:

- Camera pointed at terrain: `main p50 ≈ 5–15ms` (real drawing).
- Camera pointed straight up at sky: `main p50 ≈ 1ms` (legitimate,
  nothing to draw — same behaviour Increment 61 documented).

If you point at terrain and `main p50` is still ~1ms with a blank
screen, the SPV update didn't take. Drop me the result of the
`strings` check above.

## Related: the empty-mesh churn is still there

Independent of this fix, the streaming loop still re-submits all-air
sky chunks every drain because the mesher returns an empty
`ChunkMesh`, the upload removes the renderer slot, the candidate
filter sees `mesh_version_for == None`, and the cycle repeats. At
RD=6 this is ~180 chunks burning ~2800 meshes/sec. It's CPU waste
only; doesn't affect visible output.

The fix is small but didn't belong in this ship — keeping the
diff narrow so the validation is unambiguous. Filed for the next
ship:

- Either cache "empty at version V, don't resubmit" in
  `world_renderer.rs::upload_prebuilt_mesh_at_lod`,
- Or gate at the streaming-loop candidate filter via
  `chunk.is_all_air()`,
- Or — the long-term answer — emit a render-time "empty" marker
  in `self.meshes` so the version check sees Some(V) and skips.
