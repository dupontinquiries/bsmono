# v0.24.NEXT — evict_chunk_lod wired up (RC42.1 followup)

## What

`upload_prebuilt_mesh_at_lod` had two **inlined** stale-LOD-eviction
blocks (one in the mesh-cache-hit branch, one in the normal upload
path). Both removed the stale `(coord, oldLod)` from `self.meshes`
and routed slots through `try_cache_park` / `pending_destroy`, but
**forgot to clear the matching entry from `self.empty_mesh_versions`**.

Replaced both inline blocks with calls to `self.evict_chunk_lod(...)`,
which does the same slot/cache routing **plus** the missing
`empty_mesh_versions.remove(&key)` step.

Side effect: `evict_chunk_lod` was previously defined but never called
(the open item flagged in the RC30-42.1 cumulative README). That
dead-code situation is resolved.

## Why this is a real fix

`empty_mesh_versions` records `(coord, lod) → version` so the
dispatcher doesn't re-mesh chunks that meshed to empty at their
current version. Entries are inserted whenever a mesh comes back
empty (line ~1217), and previously only cleared on:

- non-empty re-upload at the **same** `(coord, lod)`, or
- full chunk eviction (`evict_chunk` retains by coord only).

When the player crossed a LOD band, the stale tier's empty record
was leaked. `loaded_chunk_coords()` iterates `empty_mesh_versions`
keys every frame (used by the bin's streaming/eviction loop at
`unendlich_world.rs:1860`), so the leak both bloated memory and
inflated the streaming loop's per-frame work proportionally to
LOD-band-crossings-since-startup. Bounded by total chunks × LODs,
but never reclaimed during a session.

The visible LOD double-draw bug (v0.23.2's original concern) was
already fixed by the inline blocks; this change preserves that fix
and additionally closes the leak.

## Files changed

- `crates/unendlich-engine/src/render/world_renderer.rs`
  - Two ~18-line inline blocks → two 7-line `evict_chunk_lod` loops.
  - Net diff: -22 lines, no semantic change to the cache-hit /
    upload paths beyond the added `empty_mesh_versions` cleanup.

## How to verify

```bash
./scripts/sanity.sh                          # 25-test subset, fast
cargo test --lib --release -p unendlich-engine --features render,gpu  # full 788
```

Expected: sanity prints `test result: ok. 25 passed`; full suite
still 788/0.

The `stale_lod_key_*` tests (4 of the 25) cover the predicate that
both call sites still use to pick what to evict. The pool /
mesh_buffer_pool / GPU-meshing-CPU-ref tests cover the surrounding
lifecycle so regressions in slot/cache/upload accounting surface.

## Behavioral change at runtime

Run with the README's flag set:

```bash
UNENDLICH_RENDER_DISTANCE=6 UNENDLICH_LOD_BANDS=2,6,6 \
UNENDLICH_GPU_MESHER=2 UNENDLICH_GPU_MESHER_MID=1 \
  cargo run --release --bin unendlich-world --features render,gpu
```

- Walk back-and-forth across a LOD band repeatedly.
- Before: `empty_mesh_versions.len()` grows monotonically with
  LOD-band crossings of all-air or empty chunks (sky chunks
  especially); chunks fully outside render distance still clean up.
- After: `empty_mesh_versions.len()` is bounded by current
  in-radius chunks × in-use LOD tiers.

If you have a debug accessor for `empty_mesh_versions.len()` exposed
(I didn't add one), you can confirm directly. Otherwise the
practical signal is steadier streaming-loop CPU time over long
play sessions near a LOD boundary.
