# v0.24.2c.10 — No-latency baseline (FIF=1 + MAILBOX + late-input)

The first ship in the no-latency commitment. Three small changes that
together shift the engine from "buffer-and-stall" to "draw-the-latest-
input-now, miss the deadline if you have to." DRS deferred to c.11.

## What's new

### 1. `MAX_FRAMES_IN_FLIGHT = 1` (was 2)

CPU now records frame N+1 only AFTER the GPU has finished frame N. No
CPU lookahead, no command-buffer queue absorbing input latency. The
frame the player sees reflects the most recent input that made it into
the just-recorded command buffer.

Trade-off: if GPU is slow, CPU sits idle waiting on the fence. The
companion DRS system (coming in c.11) adapts resolution when the GPU
starts missing budget so this trade rarely costs throughput.

This is a one-constant change in `world_renderer.rs` and
`chunk_renderer.rs`. All the pool-sizing and per-frame-cycle code
already used the constant correctly, so the change ripples cleanly.

### 2. Present mode: MAILBOX as default (was FIFO when VSYNC=1)

Three-way knob now:

- `UNENDLICH_VSYNC=1` (or `=on`, `=fifo`) → FIFO. Capped to refresh,
  no tearing, but CPU/GPU may block on present queue. **Old default.
  Choose for quiet fans, accept latency.**
- `UNENDLICH_VSYNC=immediate` (or `=tearing`) → IMMEDIATE. Zero
  latency, may tear. **Choose for input-critical workflows like
  first-person where tearing is less perceptible than latency.**
- Default (unset or `=mailbox` or `=0`) → MAILBOX. Newest-wins, no
  tearing, CPU never waits on present. **The no-latency baseline.**

If MAILBOX isn't supported by the surface (some Asahi/Wayland configs),
we fall back to FIFO with a `log::warn!` so you know latency mitigation
is degraded.

### 3. Late input poll

The mouse delta is now polled TWICE per frame: once at top (existing
behavior, handles resize/esc/click cleanly), once just before the draw
command-buffer record. Late-poll mouse delta gets applied to camera
rotation right before render — so the matrix used to render this frame
reflects the very latest pointer position.

Implementation:
- `apply_mouse` is called twice per frame (with delta zeroing in between).
- A second `glfw.poll_events()` + `flush_messages()` runs just before
  the `draw_frame` call.
- Other late events (esc, resize) drained too but acted on next frame —
  fine because they're sparse.

**Why this matters**: camera rotation is the highest-frequency, most-
latency-sensitive input in an FPS-style voxel engine. Late-poll reduces
input-to-photon latency by however many milliseconds the CPU-side state
management consumed (chunk mgmt, mesh updates, physics tick). At RD=8
with heavy streaming that's potentially 50+ms of recovered latency.

### Test specs

Two new specs in `tests/specs/`:

- `rd2_smoke.unendtest` — updated to drop `UNENDLICH_VSYNC=1`. Now
  exercises MAILBOX by default. Same workload as before.
- `rd2_fifo_compat.unendtest` — explicitly forces VSYNC=1 (FIFO). A/B
  comparison spec: run both, compare `cpu_acquire_p50_ms` between
  them to measure how much latency MAILBOX shaved off.

## What's NOT in c.10

**Dynamic resolution scaling (DRS).** Deferred to c.11. DRS requires
an off-screen render target, a blit-upscale pipeline, and a frame-
budget controller — it's a real renderer refactor on its own. Shipping
the three small changes first lets us validate the no-latency baseline
in isolation before stacking DRS on top.

If the three c.10 changes alone produce smooth low-latency play
across RD ranges, DRS becomes the targeted fix for the residual
overload events. If overload is still visible, DRS in c.11 attacks
it head-on.

## Expected impact

At RD=2 (the smoke test workload), `cpu_acquire_p50_ms` was 8.0ms in
c.9 (almost exactly one vsync interval at 120Hz — the FIFO stall).
With MAILBOX it should drop to <1ms. `wait_fences` spikes (p99=175ms
in c.9) should also drop because we're not queueing frames.

At RD=8 (heavier workload), the late-input pollshould reduce input-to-
photon latency by ~the duration of CPU-side state management
(currently ~5-50ms depending on streaming pressure). The `acquire`
and `wait_fences` distributions should also improve.

## Validation workflow

Run both specs:

```bash
# c.10 default (MAILBOX, late-input).
cargo run --release --bin unendlich-world --features render --features gpu --features hot-shaders \
    -- --test-spec tests/specs/rd2_smoke.unendtest

# Forced FIFO (the old c.9 behavior).
cargo run --release --bin unendlich-world --features render --features gpu --features hot-shaders \
    -- --test-spec tests/specs/rd2_fifo_compat.unendtest
```

Compare the two `.unendresult.json` files. Upload both to chat. I'll
diff them: specifically `stats.cpu.acquire.p50_ms`, `stats.cpu.wait_fences.p99_ms`,
and `stats.total.p50_ms`. If MAILBOX is doing its job, the first two
should drop substantially in `rd2_smoke` vs `rd2_fifo_compat`.
