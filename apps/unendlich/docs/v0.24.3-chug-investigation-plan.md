# v0.24.3 — Chug investigation and frame-pacing plan

Consolidated session notes from 2026-05-14. No code shipped this session;
this document captures the framing improvements that make the next
sessions' code work cleaner.

The engine sits at `0.24.2-c.13-instrumentation-followup-prep` post-revert
of c.17-a. Next code session resumes from there.

## What we set out to solve

Player observation: input does not match expected character motion. On a
120Hz display (range of target hardware: 90-500Hz), any perceptible
mismatch counts as a hitch. The standard for "good" is competitive-game
responsive: motion arrives within ~4ms (240Hz frame) of input intent,
consistently, not just on average.

## What we learned that changed the model

### 1. The chug is render-thread blocking, not present-mode pacing

3-mode A/B at rd=2, post-revert engine, 120Hz monitor:

- **MAILBOX (default)**: "Competitive game loss; not immersive in dynamic
  world." Small frequent hitches felt through camera rotation. Newest-wins
  hides some stutter but render-thread variance leaks through.
- **FIFO** (vsync on): "Still bad; lookaround worse; keys-to-brain
  slightly better." Predictable input cadence wins for input feel, but
  missed deadlines amplified to multiples of refresh interval.
- **IMMEDIATE** (vsync off, tearing allowed): "One big hitch throws me
  out then back in." Raw render-thread variance exposed directly. Most
  jarring at chug moments. No swapchain-side latency between chugs.

All three modes show the SAME underlying chug. They differ only in how
the swapchain handles it. Conclusion: vsync mode choice is not the fix.

### 2. Steady-state FPS ceiling affects perceived hitch severity

User observation: other engines and Minecraft, when running unlocked at
FPS ABOVE monitor refresh, feel measurably more responsive. This is a
well-known competitive-gaming effect with concrete mechanics:

- Higher FPS → more input samples per second → fresher input position
  even when not all frames are displayed.
- With MAILBOX at 200 FPS on a 120Hz monitor, presented frame is ≤5ms
  old at vblank. At 120 FPS it's ≤8.33ms old. ~60% input-to-photon
  reduction for "the same" presented frame rate.
- Frame-time variance averages out — slow frames don't display when
  the mailbox has a newer one ready.
- Deeper CPU/GPU pipelining → better tail-latency tolerance.

### 3. Our engine has 2.5× of latent throughput

At rd=2 MAILBOX post-revert:
- `wait_fences p50` = 2.18ms (waiting for vsync/present)
- `gpu total p50`   = 1.86ms (GPU work)
- `cpu record p50`  = 0.85ms (command recording)
- If perfectly pipelined: max(2.18, 1.86, 0.85) = 2.18ms → ~460 FPS
- Observed: 186 FPS

The 2.5× gap means stages are partly serial when they should overlap.
Some combination of: MAX_FRAMES_IN_FLIGHT=2 too low, fence-per-frame
forcing CPU↔GPU dependency, descriptor update timing in critical path,
swapchain present blocking on graphics queue submit completion.

### 4. The chug's perceptual character is amplified by low ceiling

At 186 FPS average, chug frames of 200-400ms mean MAILBOX presents the
same stale frame for 200ms (no fresh frame to substitute). That stale
duration IS the felt hitch.

At 360+ FPS steady state, MAILBOX would have continuous fresh-frame
supply except during the chug itself. The chug becomes perceptually
smaller as a fraction of frame slots, even though the underlying stall
is unchanged.

### 5. VSYNC as a concept is mid-2000s framing

The original purpose was eliminating tearing on 60Hz CRTs that couldn't
sustain 60 FPS. On modern 120-500Hz displays with engines that can
produce frames 5× faster, FIFO throws away latency budget you already
paid for. The real engineering question is "how many frames per second
is enough" — not "vsync on or off."

A configurable FPS cap (~2-3× monitor refresh) with MAILBOX or
IMMEDIATE is what competitive games actually do, and what we should
support.

## Two paths to a fix, both real

Both attack the same code surface (frame scheduling), so the work
overlaps even though the goals differ.

### Path 1: Eliminate chugs entirely

Fix render-thread blocking on mesh uploads / descriptor updates / fence
waits. Possible mechanisms:
- Dedicated transfer queue for mesh uploads (no contention with graphics
  queue).
- Fence-per-resource instead of fence-per-frame (only block on what
  matters for THIS frame).
- Deferred descriptor pool updates (reuse cached writes when possible).
- MAX_FRAMES_IN_FLIGHT tuning.

This is the right fix. Hard work, real solution.

### Path 2: Raise floor framerate

Find pipeline serialization keeping us at 186 FPS when slowest stage
implies 460 FPS theoretical. Probably small changes to fence
configuration, swapchain image count, or submit/acquire/wait order.

Path 2 is cheaper and complements Path 1 perceptually: even if Path 1
isn't done, doubling steady-state FPS makes remaining chugs feel less
catastrophic (MAILBOX has more fresh-frame supply to compensate).

## Forward plan

### Next code session: Investigation A — wait_fences root cause

Same as "Experiment 4" from earlier design notes. Read-only
instrumentation, no scheduling changes.

Add side-channel CPU log around `vkWaitForFences` that records, when
wait_ms > 10ms:
- Current and previous frame indices.
- Timestamp of last `cmd_copy_buffer` for mesh upload + total bytes.
- Timestamp of previous frame's `vkQueueSubmit`.
- Wall-clock at wait start and end.

Walk around for 60s at rd=2 MAILBOX. Paste the chug-events log. The
correlation pattern across ~100 events tells us what's blocking —
uploads, descriptors, swapchain, kernel scheduler, etc.

Files to touch (minimal):
- `crates/unendlich-engine/src/render/world_renderer.rs` — wrap
  `wait_for_fences` call with the log.
- Maybe `crates/unendlich-engine/src/render/chunk_indirect.rs` — record
  mesh upload timestamps.

Estimated effort: 1-2 hours of focused work. Output: structured data
showing exactly what's blocking the render thread during chugs.

**Reminder**: Experiment 4 instrumentation must be READ-ONLY (logging
only, not changing scheduling). c.17-a's regression is the cautionary
tale — even a small careful change can cost 5ms/frame in record time
for reasons we don't fully understand. Fix is a separate ship.

### Code session +1: Investigation B — pipeline serialization

After Investigation A gives us a target, look at where CPU and GPU
stages aren't overlapping. Likely places to inspect:
- `MAX_FRAMES_IN_FLIGHT` constant (currently 2; try 3 with care).
- Order of `submit`, `present`, `wait_for_fences`, `acquire_next_image`.
- Whether descriptor updates happen inside or outside the per-frame
  wait window.
- Whether mesh uploads use the graphics queue or a separate transfer
  queue.

Estimated effort: 1-2 hours instrumentation + 1-2 hours targeted change.

### Code session +2 (or sooner): FPS cap implementation

Small ship: configurable `UNENDLICH_FPS_CAP` env var. Sleep-then-spin
pattern after present. Plays nicely with MAILBOX and IMMEDIATE; ignored
under FIFO (already capped).

```
UNENDLICH_FPS_CAP=240   # cap at 240 frames/sec
UNENDLICH_FPS_CAP=0     # uncapped (current behavior)
UNENDLICH_FPS_CAP=auto  # future: 2.5× detected refresh
```

Once shipped, enables the bench loop (below) to test cap values
objectively.

### Bench infrastructure: filed for later, NOT a blocker

The 5-category benchmark suite (fences, tile binner state churn,
half-precision payoff, order of operations, sleep/wake under vsync) is
filed in DESIGN_NOTES but deferred. Reasoning:

- It would be "fast and low coverage" of the actual GPU design space
  — measuring what we already suspect, not surfacing what we don't.
- Real GPU-space coverage requires broader instrumentation + graphics
  R&D reading. Worth doing in a few weeks when we know the engine
  better.
- The chug fix doesn't need it. Targeted instrumentation (Exp 4)
  produces faster signal than a microbench survey.

When we do build it, the agreed architecture is Option A: standalone
`crates/unendlich-bench/` crate with headless Vulkan context, launcher
integration via `unendlich-launcher bench <name>`, results in
`.unendbench.json`.

### Bench-as-filter pattern: also filed

The user-proposed workflow of "run wide test matrix → bench filters to
top performers → feel-test the winners" is a sound methodology and
worth building when we have the categories worth running. Key insight:
bench is a *filter*, not a verdict. The human picks the winner from
the survivors.

When we build it:
- Spec templating with per-variant fan-out (one template, N variants).
- `bench-suite` subcommand runs all variants, collects results, ranks.
- Output flags top performers as "feel-test recommended."

## What's blocked on what

- Experiment 4 → unblocks targeted chug fix.
- FPS cap implementation → unblocks bench testing of cap values.
- Investigation B (pipeline serialization) → unblocks 2-3× FPS ceiling.
- Bench suite (full) → unblocks systematic regression catching.
- Half-precision benchmarks → unblocks Apple-GPU-specific optimization.

The first two are the unblocking minimum for "engine feels good."

## What's NOT in this plan, and why

- **More vsync experimentation.** Three modes already tested. No more
  signal in that axis.
- **More shadow optimization.** Shadow at rd=2 is 0.72ms p50.
  Not the chug source. c.17 arc paused.
- **Mesh upload batching tuning.** Tested at uploads=1 at rd=2; made
  things worse. Not the lever.
- **LOD tier work.** Engine already has functioning LOD tiers at
  rd>=20 (surprise discovery from earlier in this conversation).
  Not blocking chug fix.
- **The "100 tests" methodology.** Filed; not building before we know
  what's worth testing.

## Architectural commitments still in force

(Carried from earlier arcs; nothing in this session changed these.)

- No-latency philosophy (MAILBOX as default, FIF=1, late-input).
- Path B: launcher first, perf second.
- Hermetic spec runs by default (c.12-e).
- Boot/steady event tagging (c.12-e).
- Triage deletes healthy events, keeps incidents (c.12-e).
- Multiview NOT in driver_hash.
- World-state snapshot intentionally thin (just loaded_chunks +
  non_air_blocks).
- Shadow buckets disabled pending Honeykrisp investigation.
- Migration script uses `cp -r` not `mv` for cross-filesystem safety.
- `diag` is the canonical "share a run" command.
- User prefers `cargo run --release -p <crate> -- ...` over
  PATH-installed binaries.

## Notes on how this session went

This session was framing-heavy, code-light. Several misdiagnoses were
corrected through conversation:
1. Initial belief that vsync mode was the fix → ruled out.
2. Initial belief that chug was throughput → confirmed as tail latency.
3. Initial assumption that bench suite was the right next ship →
   re-scoped to "instrumentation first, then targeted fix, bench
   later when we know what to measure."
4. Initial scope of 5-category 20-bench suite → re-scoped to deferred
   for a few weeks.

The framing improvements compound: next session starts with a clear
single-target investigation (wait_fences root cause) instead of
restarting the strategic discussion from scratch.

Session-level lesson worth carrying forward: when the scope keeps
growing across messages, it's often a signal to consolidate the model
rather than add more dimensions to the experiment. The bench suite
will be better when we build it in a few weeks because we'll know
what's worth measuring.
