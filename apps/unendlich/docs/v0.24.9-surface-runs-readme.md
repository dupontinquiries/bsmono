# v0.24.9-surface-runs — SurfaceRun representation (Layer A.4 prep)

CPU-side foundation for partial greedy meshing on GPU. v0.24.8's
bench results showed GPU v2 (batched, naive) loses to 4-thread CPU
naive parallel by ~25%, ties with greedy+sky-lit MeshingPool. The
gap exists because v2's GPU kernel emits one quad per surface face;
greedy CPU produces ~5-15× fewer quads.

**Full 2D greedy on GPU is hard** — the merge step is sequential
per slice, hostile to GPU parallelization. **1D row-merging is
easy** — runs along one axis are independent per (slice, V-row).
This ship adds the CPU-side data structure for 1D-merged runs.

## What's added

### `SurfaceRun` struct

```rust
pub struct SurfaceRun {
    world_x: i32, world_y: i32, world_z: i32,
    packed: u32,  // block_type | face_dir | length
}
```

16 bytes, std430-friendly, same wire-format size as `SurfaceRecord`.

A run represents N consecutive blocks along one axis, all emitting
the same single face direction, all same block type. The "U axis"
(run direction) varies by face:
- +X / -X faces → run along Y
- +Y / -Y faces → run along X  
- +Z / -Z faces → run along X

### `extract_surface_runs(chunk) -> Vec<SurfaceRun>`

Walks the dense chunk grid in (face, slice, V, U) order. For each
(face, slice, V), iterates along U coalescing consecutive emitting
blocks of the same type into one run.

### Bench reports compression

`gpu-mesh-bench` now reports records vs runs comparison:
```
─ SurfaceRun compression analysis ─

  records:  149494    (extract: ... us)
  runs:      ~40000    (extract: ... us)  
  compression ratio (records/runs): 3-4×
  avg run length: 3-4 blocks
```

These numbers are PREDICTIONS — actual values measured on hardware
when the bench runs.

## What this ship does NOT do

- **No GPU kernel for runs yet.** The compute shader still consumes
  `SurfaceRecord[]`. v0.24.10 (next ship) adds the runs kernel.
- **No production wiring.** Bench is the only consumer.
- **No 2D greedy.** SurfaceRun is 1D (along U only). The other axis
  (V) is one-per-row. Full greedy would merge along V too; not in
  scope for this arc.

## What comes next (v0.24.10 if I get to it tonight)

A second compute kernel `chunk_mesh_runs.comp` that consumes
`SurfaceRun[]` instead of `SurfaceRecord[]`. One thread per run,
emits exactly one quad. The Vulkan plumbing largely mirrors
`SparseGpuMesher`; could be a parallel module `RunsGpuMesher` or
an additional code path inside the existing one.

Expected effect: GPU mesh time drops by the compression ratio
(measured by this ship). If ratio is 3×, GPU v2-runs runs at
~1.5-2ms for 36 chunks instead of ~5.5ms. That'd beat parallel
naive AND MeshingPool.

## Honest concerns

1. **The run extractor walks the chunk 6 times** (once per face).
   That's ~6× more reads than `extract_surface`. Run extraction CPU
   cost is real and reported by the bench.

2. **Run boundaries depend on face-emission predicate.** Two
   adjacent blocks might emit the same face for different reasons
   (one against air, one against glass). They'd merge by the current
   logic. This is correct because both faces have the same geometry
   and same block-type; the visual is identical.

3. **The 16-byte size pins SurfaceRun in shader binding.** If we
   ever want longer runs (>65535 blocks), the packed format needs
   reworking. Practical chunk has runs ≤32 (CHUNK_SIZE), so this is
   massive overhead. Could be reduced to 12 or even 8 bytes in a
   future revision.
