# v0.24.26-octree-on-gpu

**Status:** foundation ship. The GPU now has the octree as a real buffer; no production consumer reads from it yet. Next ship migrates the first consumer (the mesher is the obvious candidate).

**Architecture target:** `architecture-v1.md` §3.1 — GPU-resident octree as canonical world state, read by mesher, renderer, physics, raycast. Today those four consumers each have their own data path. This ship lays the substrate they will migrate to.

## What's wired, what isn't

**Wired**

- The octree substrate exists on the GPU. Every loaded chunk's `OctreeArray` is memcpy'd into a contiguous slice of the pool's buffer alongside the mesh upload.
- Eviction is wired. When a chunk leaves the streaming radius, its octree slot is returned to the allocator.
- The probe pipeline reads from the substrate. `UNENDLICH_OCTREE_VERIFY=1` on shutdown runs ~24 queries per loaded chunk, asserts each result equals `OctreeArray::sample` on CPU, logs counts + first mismatch.

**Not wired** (filed for future ships)

- `chunk_mesh_sparse.comp` still reads `SurfaceRecord[]` extracted on CPU. The natural next ship rewrites the mesher to read the octree directly, deprecating `SurfaceRecord[]` and `world::surface::extract_surface`.
- `chunk_manager::raycast_octree` still walks the CPU-side octree. A GPU raycast pipeline would consume the same substrate.
- The vertex/fragment shaders don't read the octree. Material-on-GPU work would change that, but it's downstream of the mesher migration.
- The `last_modified_tick` deferment infrastructure on `OctreeNode` is dormant — no consumer yet uses it for "skip stable subtrees." It will be the foundation for cache-deferment scheduling per `addendum §A4`.

## Wire format

A chunk's octree is laid out as `OctreeNode[]` (40 bytes per node, asserted at compile time). A chunk's slice is `[base..base+count)` in the global SSBO; `base = OctreeSlot::base_node_index()` is what consumer push-constants carry. Node 0 of each slice is the chunk's root.

GLSL twin lives in `octree_types.glsl` (struct + constants) and `octree_sample.glsl` (sample function). The bit layout matches the Rust `OctreeNode` exactly:

```
  offset  size  field
  ------  ----  -----
      0     4   packed_header  (is_leaf << 31 | depth << 28 | block_id)
      4     4   last_modified_tick
      8    32   children[8]  (octant index = z<<2 | y<<1 | x)
```

Any change to this layout must happen in both `octree.rs` and `octree_types.glsl` in the same commit. `UNENDLICH_OCTREE_VERIFY=1` catches drifts.

## Verifying

```bash
# A clean run with the probe gate on:
UNENDLICH_OCTREE_VERIFY=1 cargo run --release --features="render,gpu,hot-shaders" \
  -p unendlich-engine --bin unendlich-world

# After clicking-to-load-chunks for a few seconds, close the window.
# At the end of the log, look for:
#
#   octree verify: queries=21000 matched=21000 mismatched=0 \
#                  chunks_examined=875 chunks_skipped=0
#
# If `mismatched > 0`, you'll also see:
#
#   octree verify FAIL: first mismatch at chunk=ChunkCoord{...} pos=(...) gpu=N cpu=M
#
# That means the wire format has drifted — do not migrate consumers.
```

## Capacity + cost

| | |
|---|---|
| Octree pool size | 256 MB (tunable via `OctreeBufferPool::with_capacity`) |
| Per-chunk octree size | 1 node (all-air) to ~5000 nodes (heterogeneous); typical surface chunk 200–2000 nodes |
| At RD=6 with ~925 chunks | ~50–75 MB used; plenty of headroom |
| Memory type | HOST_VISIBLE \| HOST_COHERENT (zero-copy CPU writes) |
| Upload cost | One memcpy per chunk, alongside the mesh upload. Sub-millisecond. |
| Probe dispatch cost | ~14000 queries → one 64-wide dispatch → ms-order on M2/Honeykrisp; only runs when verify flag is set |

## Notes for the next ship

When the mesher migrates to read the octree (rather than `SurfaceRecord[]`), the deferment will need MAX_FRAMES_IN_FLIGHT pipelining. The current implementation frees octree slots immediately on evict — fine while only the probe (synchronous) reads them, but a per-frame consumer will see use-after-free.

The natural design: octree slots get the same deferred-destroy treatment as mesh slots (`pending_destroy` queue in `WorldRenderer`). That hooks into the existing frame-counted decrement, so we don't have to invent a new pattern.
