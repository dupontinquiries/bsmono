# v0.24.2c.4 — Chainable runs (max-duration + shutdown-hang workaround)

Two related changes to make `cfg1 ; cfg2 ; cfg3` shell chaining actually work for bisect sequences.

## 1. `UNENDLICH_MAX_DURATION_MS`

Set this to N to auto-shutdown after N milliseconds of wall-clock runtime. The shutdown goes through the normal Esc path — saved chunks, full summary, run-summaries.txt append, the works.

```bash
UNENDLICH_MAX_DURATION_MS=45000 \
UNENDLICH_SHADOW_CASCADES=1 UNENDLICH_SHADOW_LEGACY_FB=0 \
UNENDLICH_INDIRECT=1 UNENDLICH_VSYNC=1 \
UNENDLICH_RENDER_DISTANCE=8 UNENDLICH_LOD_FACTORS=4,8,16,32 \
cargo run --release --features render --features gpu --features hot-shaders --bin unendlich-world
```

When the cap fires you'll see:

```
[2026-05-11T... INFO  unendlich_world] Max duration 45000ms reached — requesting shutdown
```

…and the rest of the normal shutdown sequence proceeds. The flag is registered in `runtime_flags`, so its value is recorded in the per-run flags-in-effect block; two new tests pin that.

## 2. Shutdown-hang workaround (force-exit)

**Problem**: after `Shutdown complete.` was logged, the process would hang. Has been there for months. The Vulkan teardown, save_all, and summary write all completed; the hang was in the implicit drops that fire after `main()` returns. With chained runs, this meant a Ctrl-C between every link — defeating the point of the chain.

**Workaround**: explicit drops with diagnostic logs, then `std::process::exit(0)`.

```rust
log::info!("Pre-exit: dropping mesh_pool (may join worker threads)...");
drop(mesh_pool);
log::info!("Pre-exit: dropped mesh_pool");
log::info!("Pre-exit: dropping chunk_manager (may join chunk-loader workers)...");
drop(chunk_manager);
log::info!("Pre-exit: dropped chunk_manager");
log::info!("Pre-exit: dropping window...");
drop(window);
log::info!("Pre-exit: dropped window");
log::info!("Pre-exit: dropping glfw...");
drop(glfw);
log::info!("Pre-exit: dropped glfw");
log::info!("Pre-exit: calling std::process::exit(0)");
std::process::exit(0);
```

The first `dropped X` log line we DON'T see in the next playtest tells us which Drop is hanging. With that information we can fix the root cause properly. Until then, `exit(0)` guarantees the process terminates — which is what we actually need for chained runs.

Safety of bypassing destructors: everything important (chunk save, run-summary file flush, Vulkan teardown) is already done **explicitly above** the exit call. The only Drops we skip are infrastructure (channel receivers, glfw teardown, worker-thread joins). The OS reclaims those at process exit.

Likely actual hang cause (filed for proper fix later):
- `chunk_loader::_workers` has a leading underscore — no Drop joins them. Workers should die when `request_tx` drops, but if a worker is mid-`generate()` it might not check. Unlikely but possible.
- `glfw` teardown on Asahi + Wayland has been known to hang historically.
- Some Vulkan resource holding a stale Arc keeping a thread alive past device destruction.

The diagnostic logs will tell us next playtest.

## Worked example: chained bisect

```bash
# All four bisect configurations, 45s each, ~3 minutes total, no manual intervention.
for cas in 1 4; do for fb in 0 1; do
  UNENDLICH_MAX_DURATION_MS=45000 \
  UNENDLICH_SHADOW_CASCADES=$cas UNENDLICH_SHADOW_LEGACY_FB=$fb \
  UNENDLICH_INDIRECT=1 UNENDLICH_VSYNC=1 \
  UNENDLICH_RENDER_DISTANCE=8 UNENDLICH_LOD_FACTORS=4,8,16,32 \
  cargo run --release --features render --features gpu --features hot-shaders \
    --bin unendlich-world ;
done; done
```

Output: four run blocks in `run_summaries.txt`, each annotated with its env-vars, under the v0.24.2-c.4 version section. Diff them however you like.
