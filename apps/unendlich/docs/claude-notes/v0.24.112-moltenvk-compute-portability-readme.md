# v0.24.112 — MoltenVK portability for the headless GPU compute contexts

Terrain renders now (v0.24.110 + v0.24.111). This re-enables the GPU compute
paths that were silently falling back to CPU on Mac.

## What was wrong

The engine creates **three** independent Vulkan contexts, and only the main
renderer's was made portability-aware in v0.24.109:

- `render/context.rs` — main renderer ✓ (fixed earlier)
- `world/gpu_generator.rs` — GPU terrain generator (its own headless compute
  instance) ✗ → `ERROR_INCOMPATIBLE_DRIVER`, the "GPU unavailable … Using CPU"
  line in every run
- `world/gpu_chunk_pool_vk.rs` — GPU octree mesher (`UNENDLICH_GPU_MESHER=2`) ✗

Both headless contexts built their `VkInstance` without the portability-
enumeration extension/flag, so MoltenVK's loader refused to enumerate the Metal
device and `vkCreateInstance` failed.

## Fix

Applied the same proven treatment from `context.rs` to both compute contexts:
- instance: add `VK_KHR_portability_enumeration` + `VK_KHR_get_physical_device_properties2`
  and set `ENUMERATE_PORTABILITY_KHR` (macOS only).
- device: enable `VK_KHR_portability_subset` when advertised. These are FP32-only
  compute contexts with no swapchain and no gated features, so just enabling the
  extension is enough — nothing to chain.

All `#[cfg(target_os = "macos")]`; Linux/Asahi is byte-for-byte unchanged.

## What this does NOT bring back

GPU-driven indirect *culling* (`cmd_draw_indexed_indirect_count`) still can't run
on MoltenVK — Metal has no GPU-side draw count. The CPU per-chunk draw path
(v0.24.110) stays in effect for chunk drawing on Mac. This brick is only about
the two compute subsystems: voxel generation and octree meshing.

## How to test

Rebuild **with the `gpu` feature** and the loader env:

```
DYLD_FALLBACK_LIBRARY_PATH="$(brew --prefix)/lib:$DYLD_FALLBACK_LIBRARY_PATH" \
VK_ICD_FILENAMES="$(find "$(brew --prefix)" -name MoltenVK_icd.json | head -1)" \
VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation \
cargo run --release --features render,gpu,hot-shaders --bin unendlich-world
```

1. **GPU terrain generation**: expect `Terrain generator ready (gpu=true)` instead
   of the `ERROR_INCOMPATIBLE_DRIVER … Using CPU` warning.
2. **GPU octree mesher** (separately): add `UNENDLICH_GPU_MESHER=2`. Watch for the
   mesher pool switching off "CPU-only", and for correct terrain (compare against
   the CPU-meshed look you have now).

The octree mesher is the riskier of the two — its compute shaders go through
MoltenVK's SPIR-V→MSL translation for the first time, so that's where a shader
issue (e.g. the `%planes` decoration note we saw) could surface. Generation
should be the cleaner win. Send the log either way.
