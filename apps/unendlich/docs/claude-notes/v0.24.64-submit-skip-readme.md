# v0.24.64-submit-skip

## Tagline

Opt-in cache that skips the per-frame 2197-chunk shell walk in the
meshing-submit phase when the world is stationary. Aims at the
steady-state stutter discovered during RC29 hardware validation:
`cpu.submit=800-880ms/sec` while the GPU is idle.

## Status

(see `docs/v0.24.63-adaptive-uploads-readme.md` for the predecessor).
Not yet built with cargo or run on hardware. Stacked on
v0.24.63-adaptive-uploads and the RC24-28 entity scaffold zip.

## What this ship does

### Before

Each frame, the bin's chunk-streaming submit phase walks every
shell from `0..=RD` around the player, classifies coords by LOD
tier, and does up to 4 DashMap reads per coord to discover whether
each chunk needs (re-)meshing:

- `chunk_manager.get_chunk(coord)` — Arc<Chunk>
- `renderer.mesh_version_for(coord)` — u64 version stamp
- (conditionally) `chunk_manager.octree(coord)` for octree-mode submits
- (in `MeshRequest` build) generator/world_model Arc clones

At RD=6, the walk visits up to (2·6+1)³ = 2197 coords. With the
world fully loaded and stable (all chunks meshed at their current
version, no edits pending, player stationary), every coord answers
"already correct" and the walk produces zero candidates — but the
cost of *discovering* that is ~800ms/sec on M2 Max (~13-20ms per
frame at 30-45 FPS). That cost is responsible for the bulk of the
100-160ms p99 LONG FRAME warnings observed after world settle.

### After

Cache three cheap signals from the previous frame:

1. `chunk_manager.world_edit_tick()` — atomic u64 bumped on every
   block edit (single OR batch) by `replace_edited_chunk` /
   `replace_batch_edited_chunk`.
2. `chunk_manager.loaded_count()` — DashMap.len(). Bumps whenever
   a chunk is inserted (worker generates it) or removed (eviction).
3. `player_chunk` — the player's current chunk coord (already
   computed earlier in the same frame).

Plus a `was_idle` boolean: `true` if the previous frame's walk
produced zero candidates across all four LOD tiers.

If `was_idle` AND all three signals match the cached values, skip
the entire shell walk for this frame. Total cost of the check:
three O(1) reads (2 atomics + 1 i32 triple compare). Reset
`was_idle` to false whenever a fresh walk produces any candidate.

This is a strict superset of "world has visible changes" — we
never wrongly skip work, because any of:
- a block edit anywhere
- a chunk loaded or evicted
- the player crossing a chunk boundary

will change one of the three signals and force a re-walk. The
worst case is one frame of latency on edge cases (e.g. player
moves at the exact frame boundary), which is below the 1/30s
human-visible threshold.

## Activation

```bash
UNENDLICH_SUBMIT_SKIP=1 cargo run --release --bin unendlich-world \
    --features="render,gpu,window"
```

Default off (env unset OR != "1"). A logged confirmation line fires
on startup:

```
[INFO] submit_skip: ENABLED — shell walk skipped when world is stationary
```

Plus a heartbeat at power-of-2 cumulative skips (so an A/B test can
confirm the optimization is firing):

```
[INFO] submit_skip: skipped 64 cumulative frames (world stationary)
[INFO] submit_skip: skipped 128 cumulative frames (world stationary)
[INFO] submit_skip: skipped 256 cumulative frames (world stationary)
...
```

## Architecture changes

### Bin state

Six new variables at the top of `main()` (after the
`adaptive_uploads` controller block, around line 721):

```rust
let submit_skip_enabled: bool = /* env check */;
let mut submit_skip_last_world_edit_tick: u64 = u64::MAX;
let mut submit_skip_last_loaded_count: usize = usize::MAX;
let mut submit_skip_last_player_chunk: ChunkCoord =
    ChunkCoord::new(i32::MIN, i32::MIN, i32::MIN);
let mut submit_skip_was_idle: bool = false;
let mut submit_skip_frames_skipped: u64 = 0;
let mut submit_skip_last_log_frames: u64 = 0;
```

Initial sentinel values (`u64::MAX`, `usize::MAX`, `i32::MIN`) are
guaranteed mismatches — the first frame after enable always runs
the walk, then sets the cache.

### Submit-phase entry (around line 1798)

Pre-walk check before the existing `if !manager_empty { ... }`
gate:

```rust
let cur_world_edit_tick = chunk_manager.world_edit_tick();
let cur_loaded_count    = chunk_manager.loaded_count();
let cur_player_chunk    = player_chunk;
let should_skip_submit  = submit_skip_enabled
    && submit_skip_was_idle
    && cur_world_edit_tick == submit_skip_last_world_edit_tick
    && cur_loaded_count    == submit_skip_last_loaded_count
    && cur_player_chunk    == submit_skip_last_player_chunk;

if should_skip_submit { /* counter + log */ }
if !should_skip_submit && !manager_empty {
    // existing walk + submit code
}
```

### Post-walk tracking refresh (around line 2038)

At the end of the existing `if !manager_empty { ... }` body, after
the submit loop:

```rust
submit_skip_was_idle = total_candidates == 0;
submit_skip_last_world_edit_tick = cur_world_edit_tick;
submit_skip_last_loaded_count    = cur_loaded_count;
submit_skip_last_player_chunk    = cur_player_chunk;
```

Where `total_candidates = near_cands.len() + mid_cands.len() +
far_cands.len() + vfar_cands.len()`, computed before the `Vec`s
are consumed by `into_iter()`. Crucially: we mark idle ONLY when
the walk produced zero candidates — if the pool was full and we
couldn't submit collected candidates, we re-walk next frame to
retry. This avoids a deadlock where a pool-full frame would mark
idle and then never re-attempt the queued work.

## Expected effect

| Metric                          | Before RC30 | With UNENDLICH_SUBMIT_SKIP=1 (stationary) |
|---------------------------------|-------------|-------------------------------------------|
| cpu.submit per second           | ~800ms      | ~0ms                                      |
| Frame p99 (stationary, loaded)  | 100-160ms   | 25-40ms                                   |
| LONG FRAME warnings while still | Frequent    | Stop                                      |
| Frame p99 (moving)              | unchanged   | unchanged                                 |

The optimization has no effect when the player is moving (player_chunk
changes every chunk-boundary crossing, ~1Hz at walking speed). It
only helps the "stand still and look around" steady state.

Same env between two runs except for the single new flag:

```bash

UNENDLICH_RENDER_DISTANCE=6 UNENDLICH_LOD_BANDS=2,6,6 \
  UNENDLICH_GPU_MESHER=2 UNENDLICH_GPU_MESHER_MID=1 \
  UNENDLICH_WARMUP_MS=2000 UNENDLICH_OCTREE_VERIFY=1 \
  UNENDLICH_ADAPTIVE_UPLOADS=1 \
  cargo run --release --bin unendlich-world --features="render,gpu,window"

# With submit-skip:
UNENDLICH_RENDER_DISTANCE=6 UNENDLICH_LOD_BANDS=2,6,6 \
  UNENDLICH_GPU_MESHER=2 UNENDLICH_GPU_MESHER_MID=1 \
  UNENDLICH_WARMUP_MS=2000 UNENDLICH_OCTREE_VERIFY=1 \
  UNENDLICH_ADAPTIVE_UPLOADS=1 UNENDLICH_SUBMIT_SKIP=1 \
  cargo run --release --bin unendlich-world --features="render,gpu,window"
```

In each: wait for `gen_pending: 0`, then stand still for 20-30s
and read the FPS log line's `cpu: ... submit=Xms` and `frame: p99=Yms`.

## Risks and known issues

- **First-frame state**: the sentinel values are
  `(u64::MAX, usize::MAX, ChunkCoord::MIN)`. On startup with the
  flag enabled, the first frame DEFINITELY mismatches and runs the
  walk normally. There's no way for the cache to spuriously fire
  on uninitialised state.
- **DashMap.len() racing**: `loaded_count()` reads the DashMap's
  internal counter. If a worker inserts a chunk between the read
  and the walk, we'd... still be fine. The walk would catch it
  (because in the no-skip branch the walk runs anyway, and in the
  skip-set branch we'd just delay one frame).
- **Chunk version changes without loaded_count change**: this is
  exactly what `world_edit_tick` covers. Edits bump the tick;
  the cache invalidates.
- **Eviction of zero chunks**: `loaded_count` doesn't change. If
  a chunk is evicted and a new one inserted in the same frame and
  the counts happen to match... we'd miss the eviction. But the
  renderer evicts *meshes*, not chunks; the chunks loaded-count
  reflects what's in ChunkManager. New chunks insert + old chunks
  drop is a counted operation. So if a chunk drops AND a new one
  loads in one frame, the count is identical but the new chunk
  WAS just generated → meaning the worker just produced it → which
  means a worker insertion happened → which logically should have
  perturbed the count at some moment, but we read it at frame end.
  IF the race is so tight we miss it: one frame of latency on
  picking up the new chunk for meshing. Below visible threshold.
  Document as known: if this becomes a real problem, replace
  loaded_count with a monotonic insertion counter.
