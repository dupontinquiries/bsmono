# v0.24.109 — macOS/MoltenVK portability enablement

Implements the three setup items from `toolkit/MACOS-MOLTENVK.md` so the engine
can boot on macOS through MoltenVK. All changes are `#[cfg(target_os = "macos")]`
gated — **the Linux/Asahi build is behavior-identical** (the only Linux-compiled
changes are trivial and preserve the existing path).

## What changed (`render/context.rs`)

1. **Instance** — on macOS, request `VK_KHR_portability_enumeration` (+ its
   `get_physical_device_properties2` dependency) and set
   `InstanceCreateFlags::ENUMERATE_PORTABILITY_KHR`, so the loader actually
   enumerates the MoltenVK device. Linux passes empty flags = unchanged.
2. **Device** — on macOS, if the physical device advertises
   `VK_KHR_portability_subset`, add it to the enabled device extensions (the
   Vulkan portability rules require this). Linux keeps `[VK_KHR_swapchain]`.
3. **drawIndirectCount** — on macOS, query
   `PhysicalDeviceVulkan12Features::draw_indirect_count` and only enable it if
   present (requesting an unsupported feature would fail device creation); logs a
   warning if absent. Linux keeps the hard enable (Asahi supports it).

## ⚠️ This is the one kind of change that can't be sandbox-validated

The macOS blocks are only compiled when building *on macOS*, never on Linux, so
they've had no compiler run at all. Treat the first build as iteration: if it
doesn't compile, paste the error and it's a quick fix. The most likely spot is
the `ENUMERATE_PORTABILITY_KHR` constant name (if your ash rejects it, the
fallback is `vk::InstanceCreateFlags::from_raw(0x0000_0001)`).

## Prerequisite (do this first)

Install the **Vulkan SDK for macOS** (LunarG) — it bundles MoltenVK, the Vulkan
loader, and the validation layers. Without a discoverable loader, GLFW can't
create a Vulkan instance and you'll fail at startup. After install, a new shell
should have `VULKAN_SDK` set and `vulkaninfo` should list an "Apple M…" device
via MoltenVK. (If you installed MoltenVK standalone instead, set
`VK_ICD_FILENAMES`/`VK_DRIVER_FILES` to its `MoltenVK_icd.json`.)

## Build + run (isolate concerns with the env gates)

Apply this brick on top of current HEAD, then on the Mac:

```
cargo build              # or: cargo run -p unendlich-engine ... (your usual bin)
```

Run in this order so a failure points at one thing:

1. **Plain (post-FX OFF, default):** just run. This tests *MoltenVK + the engine*
   with none of the post-FX/bloom tower active — the cleanest feasibility check.
   Expect normal rendering. If GPU-driven culling logs the drawIndirectCount
   warning, tell me (we'd then need a draw fallback).
2. **Post-FX on:** `UNENDLICH_POSTFX=1` — should match the no-post-FX look
   (this is the v0.24.103 identity check, now on Metal).
3. **Bloom on:** `UNENDLICH_POSTFX=1 UNENDLICH_BLOOM=1` — soft glow on bright
   areas. This doubles as the first real run of the bloom tower.

Turn on validation while iterating (the SDK layers catch portability mistakes):
```
VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation cargo run ...
```
