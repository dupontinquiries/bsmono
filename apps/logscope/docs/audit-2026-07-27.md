# Audit: the three bug classes that recurred, checked exhaustively

Written after finding the same shapes one at a time as symptoms surfaced, which is the worst way to find
them. Each class below caused at least two real bugs this session.

## Class 1 — `end_frame()` without a matching `begin_frame()`

**Cost:** two rounds. `download()` (fixed _248) and the staging-ring wrap (attempted _274, reverted _276
because that one is a fence and must NOT reopen). Symptom is 99% of dispatches taking the
one-command-buffer-per-dispatch path while `flush_every` appears to do nothing.

**Status: CLEAN.** Every real call is accounted for:

| site | verdict |
|---|---|
| `flush_q4k` ×2 | load-time batching, ends the function |
| `run_guarded` | teardown path |
| `stream_expert_lins` | the A/B `submit` branch of the fence — must not reopen |
| `prefill_chunked` | end of function, added _253 |
| `write_chunked_flushed` | intentional, one per chunk |
| `decode_layers_t` | reopens ✓ |
| `stream_session_window` | one deliberate error bail-out, one reopens ✓ |

**Method note:** the first pass reported three extra hits in `stream_expert_lins` that were the phrase
`end_frame()` inside my own comments. A grep that does not exclude comments manufactures findings — the
same false-positive problem `prechecks` was built to avoid, committed while auditing.

## Class 2 — a registry disagreeing with what the loader does

**Cost:** four instances. `archfeat` claiming Gemma support that `archcfg` denied; `gemma4` requirements
listed while the loader did not know the name; `glm-dsa` sharing DeepSeek's metadata prefix and blaming
the checkpoint for our lookup; the MLA note saying "not wired yet" four lines after the loader announced
MLA active.

**Root cause:** two descriptions of one fact, kept in sync by hand. The mitigations added are the
refusal consulting `archfeat` directly, and tests asserting the two agree — but the class is not
eliminated, only monitored.

## Class 3 — a green gate with an unstated blind spot

**Cost:** at least two. `--gate-moe-stream` reported BIT-EXACT while a reopened frame changed the model's
output on hardware, because it fills fewer experts than `STAGE_RING` has slots and never forces a wrap.
`--gate-perf` reported "speed levers validated" while measuring no speed at all.

**Mitigation:** both now state their limits in their own output. The general rule worth keeping: a gate
that cannot fail on a known bug is worse than no gate, because it converts "untested" into "verified".

## What this audit did NOT check

Anything requiring the target hardware. The remaining open items — whether the two surviving GPU timeouts
are deterministic, whether Q6_K conversion is correct, whether CPU placement pays — all need measurement,
and nothing in a static read will settle them.


## Class 4 (new) — dropping page residency under a live mapping

Found by auditing the GPU memory stack rather than by a symptom, which is the first time that has
happened this session.

`release_map_residency()` runs `MADV_DONTNEED` on every retained model mapping after load, to hand back
~61 GiB of page cache. That is correct when the load pass has finished reading and nothing holds a view.
It is **wrong when experts are file VIEWS**: `RawExpertSrc` keeps `&'static [u8]` slices into the
mapping for the process lifetime, so dropping residency turns every expert fill into a page fault from
disk — converting the view path's entire advantage into its opposite, and stalling the CPU inside the
`write_buffer` that a GPU dispatch is waiting on.

**Is it firing in the logs we have? No.** Scout's `ffn_down_exps` is Q6_K, which forces the host-copy
path, so no views exist when the release runs:

```
MoE file-views unavailable — blk.0.ffn_down_exps.weight is Q6_K ... falling back to the host-copy path
released page cache from 2 mapped file(s) — RSS now anon 36.4 GiB + file 0.0 GiB
```

Qwen3-Coder is the same case for a different reason: it fits resident, so it never streams experts.

So this is **latent** — it needs an all-Q4_K MoE large enough to stream, which is exactly the
configuration the view path was written for and neither of us has run. It would have presented as
catastrophic slowness rather than an error, and the obvious suspects (fills, submits, the fence) would
all have looked innocent.

Guarded now: `mark_map_views_live()` is called where the views are constructed, and the release skips
with a message rather than silently doing nothing. Declaring it at the construction site keeps the fact
next to the thing that makes it true.

**Note on Q6_K.** Fixing the Q6_K kernel unblocks the view path for Scout — and would therefore have
walked straight into this. Two bugs that only meet on a path nobody has taken yet.
