# Where the model work goes next

## The finding that changes the plan

The engine **already has a transform system**, and none of the derivation work
knew about it. `content/bots.json` carries an explicit identity map:

> "Robot↔vehicle identity map (mirrors `robot_parts.c` vehicle branch): every
> part has two lives."

| robot | vehicle |
|---|---|
| chest | hull wedge |
| head | cab |
| visor | windshield |
| shoulders | fenders |
| arms | front wheels |
| thighs | rear wheels |
| shins | exhausts |
| back | turret hump |
| hands_feet | hull nubs |

`content/chassis.json` carries the animation parameters per body frame —
`fold_spin` (160–300°), `xform_dur` (0.78–1.35 s), and proportion multipliers for
arm/leg/head/shoulder/bulk. `robot_parts.c` implements the articulation, the
per-part tint, the weathering, and the alt-mode reshaping. Five part assemblies
exist: `phead`, `pchest`, `ppauldron`, `phand`, `plimb`.

**So the transformation does not need deriving. It needs feeding.**

Every attempt in this thread — descriptor matching, skeleton folding, motion
scheduling — was trying to reverse-engineer an animation the engine already
performs. The reason it kept failing is not that the methods were bad; it is
that the artist never authored a transform between the tank and robot meshes,
because the engine does not use those meshes for transforming. It transforms
*procedural parts*.

## The actual gap

The engine's transform works on parts generated by `gen_props.py` into simple
IQMs. The imported models — Brawl, scorponok, the 1,000+ others — are
high-detail and sit **outside** the slot system entirely. That is the whole
detail gap:

* engine parts: articulate and transform, low detail
* imported models: high detail, cannot transform

The bridge is to put imported geometry into the engine's slots.

## Why the anatomy pass is already most of the bridge

The engine's slot vocabulary splits exactly the way the symmetry pass does:

* **pairs** — shoulders, arms, thighs, shins, hands_feet
* **centreline** — chest, head, visor, back

`anatomy::body_plan` returns precisely that partition, and it works: 74% paired
on Brawl's tank, 78% on his robot and on the t4b mech, 85% on scorponok. The
missing step is not detection, it is **naming** — deciding which pair is
`shoulders` and which is `thighs`.

And that is where the reference skeleton earns its place. `dude.iqm` gives
landmark heights (shoulders 93.3%, hips 68.7%, knees 38.2%), so a pair's height
in the model names its slot. A pair at 90% of model height is shoulders; one at
35% is shins. No matching, no descriptor, no fitting — a lookup against a
measured datum.

## The order I would work in

1. **Name the slots.** Extend `anatomy` to assign each pair and centreline part
   an engine slot name by landmark height. Verifiable by eye on the coloured
   render, which already exists.
2. **Emit a bot definition.** Write the assignment out in `bots.json`'s own
   schema, so the engine loads an imported model as a bot without engine
   changes. This is the point where something testable appears in-game.
3. **Let the engine transform it.** `fold_spin` and `xform_dur` already drive
   the animation. If the slots are named correctly, the fold comes free.
4. **Only then** revisit UV generation and the instancing win (14.4% corpus-wide,
   up to 60% on hero meshes) — both are real, and both are optimisations of a
   pipeline that has to work first.

## What to stop doing

Deriving the transform from two meshes. The robot is *posed*, the tank has a
different axis convention, and no rigid mapping exists between them because none
was ever authored. That line of work produced good tooling — the symmetry pass,
the profile, the verifier — but its stated goal was unreachable, and the engine
made it unnecessary.
