# v0.24.20-vertex-pack — vertex compression + index-shift elimination

Three compounding wins on the upload-pressure path that was confirmed
by v0.24.18's thread-probe data and partially mitigated by
v0.24.19's mesh cache.

## TL;DR

- **3× less vertex bandwidth per chunk upload.** Vertices were 24 B
  (3×f32 pos + 3×f32 color). They're now 8 B (10-bit chunk-local pos
  + 8-bit color). The mesher still emits the 24-B form on CPU; the
  renderer quantizes once at upload time before the memcpy.
- **CPU index pre-shift eliminated.** Each chunk's indices used to
  get walked once on CPU to add a per-chunk vertex offset. They now
  ride the GPU's `vertexOffset` indirect-draw field instead — no
  allocation, no add loop per upload.
- **Cache-visibility counter.** New `parks=N` in the FPS log so you
  can tell "cache had nothing to do" from "cache thrashed."

Default behaviour for the main bin is unchanged; everything is
on-by-default because the changes are formats and pipeline shape, not
optional features.

## How to A/B vs v0.24.19

The single most informative metric is the per-frame upload bytes
already surfaced in the FPS log. Run the same playtest pattern on
both versions and compare:

```
v0.24.19:   upload bytes/frame p50 = X
v0.24.20:   upload bytes/frame p50 = ~X/3   ← expected
```

Combined with the existing thread-probe, the chug% on
`drm_syncobj_array_wait_timeout` should drop further — both because
each upload is smaller, AND because the mesh cache (if enabled)
holds ~3× more chunks for the same VRAM budget.

## What changed

### Win 1: vertex format — 24 B → 8 B

`mesher::PackedVertex` is the new GPU-side type:

| field          | format                          | bytes | content                                                 |
|---------------:|:--------------------------------|------:|---------------------------------------------------------|
| `pos_packed`   | `A2B10G10R10_UNORM_PACK32`      | 4     | chunk-local xyz, 10 bits per axis, [0,1]→[0,32] blocks |
| `color_packed` | `R8G8B8A8_UNORM`                | 4     | RGB with face brightness baked in; A reserved          |

The vertex shader reconstructs world position via:

```glsl
ChunkDraw c = chunks[gl_InstanceIndex];
vec3 chunk_origin = vec3(c.aabb_min.x, c.aabb_min.w, c.aabb_min.z);
vec3 world_pos = chunk_origin + in_pos_unorm.xyz * 32.0;
```

The cull shader writes the per-chunk slot index into the indirect
command's `firstInstance` field so `gl_InstanceIndex` resolves to
the right entry in the chunks-metadata SSBO. `aabb_min.w` was
unused padding before; it now carries `chunk_origin.y`
(`coord.y * 32`). `aabb_min.x` and `aabb_min.z` already carried
the chunk's XZ origin since the cull shader builds the AABB from
`coord.block_origin()`.

Position quantization step is 32.0/1023 ≈ 0.0313 blocks. The
mesher's sub-block details survive this round-trip:

| use case                       | offset magnitude | distinct after quantize? |
|--------------------------------|:----------------:|:------------------------:|
| z-fight nudge (`- 0.05`)        |    0.05          | yes                      |
| top jitter (`±0.0625`)         |    0.0625        | yes                      |
| soft-edge sag (`- 0.25`)        |    0.25          | yes                      |
| surface decoration (`- 0.30`)  |    0.30          | yes                      |

10 unit tests in `mesher.rs` cover round-trip precision, boundary
cases, color quantization, and the Vulkan bit layout.

### Win 2: index pre-shift removed

Pre-v0.24.20 every `upload_mesh` allocated a fresh `Vec<u32>` of
length `idx_count` and added `vert_base_count` to every element so
the indices in the shared buffer pointed at absolute vertex
positions. The indirect command's `vertexOffset` field was
hard-coded to 0.

v0.24.20 inverts this: indices are uploaded unshifted, and
`vertexOffset = vert_base_count` is written into the indirect
command instead. Vulkan adds it to each index during fetch. Same
end result, no per-upload CPU pass over the index list.

Cost recovered: at ~30K indices per typical chunk, that's a 120 KB
allocation + 30K wrapping_adds saved per upload. The non-indirect
fallback paths (`UNENDLICH_INDIRECT=0`) were also updated to pass
the right `vertex_offset` and `first_instance` to `cmd_draw_indexed`.

### Win 3: cache park-attempts counter

FPS log format becomes:

```
cache: hits=N misses=M parks=P size=S/cap=C
```

`parks` is the lifetime count of `try_cache_park` calls — i.e., the
number of chunks that left the streaming radius and could have
populated the cache. It increments **before** the disabled-cache
early return, so even with `UNENDLICH_MESH_CACHE_SIZE=0` you get an
"evict-rate" reading you can use to size the cache before enabling
it.

Reading the counters:

| pattern                      | meaning                                                   |
|------------------------------|-----------------------------------------------------------|
| `hits=0 misses=0 parks=0`    | Playtest never moved enough to evict chunks. Cache idle.  |
| `hits=0 misses=0 parks=N>0`  | Evictions happened but nothing got re-uploaded yet.       |
| `parks ≈ size`               | Cache hasn't yet hit capacity; LRU dormant.              |
| `parks >> size`              | Working set churns past capacity; raise cache size.       |
| `hits > misses`              | Revisit pattern, cache paying off.                        |

## Pipeline shape changes

This ship touches the descriptor-set layout shared by the main
chunk pipeline and the shadow pipeline. Both layouts gain a new
binding:

```
binding 3: STORAGE_BUFFER, VERTEX stage
```

The chunks-metadata SSBO (owned by `IndirectDrawSet`) is bound
into the renderer's per-frame descriptor sets at this slot. The
vertex and shadow shaders read it via `gl_InstanceIndex`.

The Vulkan 1.1 feature `shaderDrawParameters` is now enabled at
device-create time. Honeykrisp/M2 supports it (confirmed via the
Mesa version probe in c.13-scout); enabling it makes
`gl_InstanceIndex = gl_InstanceID + firstInstance` reliable across
drivers.

## Backward compatibility

- The CPU-side `Vertex` (24 B, `pos: [f32;3]`, `color: [f32;3]`) is
  **unchanged**. The mesher, debug overlay, winding-check, and
  every test that constructs `Vertex` values continues to work.
- The legacy `ChunkRenderer` (single-chunk demo, used by
  `unendlich-chunk` and `unendlich-palette`) packs vertices the
  same way and binds a 1-entry chunks SSBO so direct draws with
  `gl_InstanceIndex=0` get the demo chunk's origin. The bins keep
  working.
- The mesh cache (v0.24.19) is unchanged at the API level; both
  fresh-upload and cache-restore paths now write
  `aabb_min[3] = chunk_origin.y` and
  `vertex_offset = vert_base_count`.
- The `gpu_meshing_sparse` bench path (`gpu-mesh-bench` bin) is
  untouched; it produces meshes in CPU `Vertex` form which the
  bench just compares. No production wiring crosses that boundary
  yet.

## Honest concerns

1. **Visual identity.** Vertex positions are now quantized to
   1/32-block steps. This is finer than any feature the eye picks
   up at game-typical distance, and the mesher's deliberate
   sub-block offsets (z-fight nudges, sag, jitter) all survive
   round-trip per the test suite. If you see visible "popping"
   between adjacent quads that weren't there before, the most
   likely cause is a vertex that exits the chunk's natural bounds
   (which the codec clamps); none of the production mesher paths
   do that, but it's the first thing to check.

2. **Color resolution.** 8-bit-per-channel is fine for the current
   palette but loses sub-channel gradients the FP32 path
   technically had. In practice the mesher's color values come
   from a small palette × face-brightness × climate-tint product
   that already fits in 8 bits per channel without banding.

3. **`A2B10G10R10_UNORM_PACK32` driver coverage.** Required Vulkan
   format support for vertex inputs is the optional
   `vertexAttributeAccessBeyondStride` family — but A2B10G10R10
   specifically is a core mandatory format for the `BUFFER` and
   `VERTEX_BUFFER` features in Vulkan 1.0. Should be available on
   every conformant implementation.

4. **`shaderDrawParameters` enable.** Adding a feature to the
   device-create chain that wasn't there before. If a target
   device refuses the feature, `vkCreateDevice` would return
   `ERROR_FEATURE_NOT_PRESENT`. Honeykrisp/M2 has it. Other
   targets in the support matrix should too (all 1.2-conformant
   implementations), but if a future device refuses, the fix is
   to make the feature opt-in based on the existing
   `multiview_support()`-style probe.

5. **What this ship does NOT change.**
   - Shadow pass is still the GPU bottleneck (`shadow_p50 ≈
     4.6 × main_p50` per v0.24.19's logs). The vertex-pack reduces
     the per-vertex transform cost slightly but doesn't address
     the fundamental "every chunk drawn at full detail per
     cascade" issue. That's filed as `c.17` (multiview CSM).
   - CPU meshing pool work is unchanged; the mesher still produces
     verbose Vertex output. The dormant `gpu_meshing_sparse` path
     would address this once it gets wired to production.

## What comes next

The natural follow-ups, in increasing risk order:

1. **Reduce default vertex buffer pool from 3 GB to 1 GB.** With
   3× compression we no longer need 3 GB; 1 GB still leaves
   comfortable headroom for the v0.18.x playtest working set.
   Frees ~2 GB of host-visible memory.
2. **Wire `gpu_meshing_sparse` into production.** v0.24.6's bench
   validated the kernel; the next step is replacing CPU mesher
   calls with batched GPU dispatches. The packed vertex format
   here makes the eventual zero-copy mesher-into-pool path
   straightforward.
3. **GPU-resident chunks.** Generation + extraction + meshing all
   on GPU, never reading block bytes back to CPU. This is the
   "chunks as a function of inputs" architecture from the user's
   long-term vision.
4. **Multiview CSM.** Per the c.17 plan — directly attacks the
   shadow-pass bottleneck this ship doesn't move.
