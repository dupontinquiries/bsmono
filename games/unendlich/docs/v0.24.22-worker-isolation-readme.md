# v0.24.22-worker-isolation — fix the chug at its documented root cause

Implements the next direction filed in `DESIGN_NOTES.md` Increment 61:

> **Worker isolation (P/E core assignment, thread priorities) —
> high-value next direction. Tests the hypothesis directly.**

The chug is **CPU contention**, not GPU saturation. The "magic switch"
in v0.24.17 free-play (5 FPS → 130 FPS in a single frame transition,
static player position, on the frame `gen_pending` hit 0) was the
smoking gun. While chunk-loaders are busy generating terrain, they
preempt the render thread on shared P-cores. The GPU starves because
the render thread can't submit commands fast enough. `wait_fences`
balloons to 200+ ms per frame and you get the 5-FPS chug.

This ship deprioritizes chunk-loader threads so they yield to render
and mesh work. The expected effect: render-thread frame budget is
maintained even during heavy chunk streaming, at the cost of slower
world-gen throughput.

## What this ship does

A new module `unendlich-engine/src/thread_priority.rs` defines four
`ThreadRole`s and a `configure_current_thread(role)` function that
each spawned thread calls early in its life:

- **`ChunkLoader`** (the surgical change): `setpriority(PRIO_PROCESS,
  0, +10)` lowers the thread's nice value by 10, and
  `sched_setaffinity` pins it to the system's "efficiency" cores —
  any CPU whose `/sys/devices/system/cpu/cpuN/cpu_capacity` reports
  less than the system maximum. On M2 Max + Asahi Linux that's the
  4 E-cores; on M2 Max running on macOS this is a no-op (not the test
  platform); on homogeneous systems affinity pinning is skipped and
  only the nice change applies.

- **`MeshWorker`**, **`GpuDispatcher`**, **`Render`**: no syscalls
  issued. Default scheduling. The kernel keeps them on P-cores while
  active because they're nice=0 and the chunk-loaders are nice=+10.
  The role assignment exists for symmetry, so all spawn sites declare
  themselves and so adding RT-priority or QoS-class support later
  doesn't require rewiring callers.

The whole module is Linux-only. macOS / Windows fall through to a
no-op stub. The codebase target is Asahi Linux on the M2 Max, which
is where the chug measurements were taken and where the fix is
expected to land.

## Wired-in points

Four spawn sites updated to call `configure_current_thread`:

1. **`world/chunk_loader.rs`** — the `ChunkLoader::new` spawn loop now
   sets `ThreadRole::ChunkLoader` as the first line of each worker
   closure. This is the only change that does actual scheduling work.

2. **`render/meshing_pool.rs`** — both the mesh-worker spawn (in
   `MeshingPool::build`) and the GPU dispatcher spawn declare their
   roles. No syscalls fire, but the calls are present for symmetric
   documentation and future tunability.

3. **`bin/unendlich_world.rs`** — the main thread declares
   `ThreadRole::Render` right after `thread_probe::init()`. Again, no
   syscalls fire today; the role assignment is positioned so future
   work (RT priority, isolated CPU set) can be added in this one
   place.

## Opt-out

`UNENDLICH_WORKER_ISOLATION=0` disables all priority/affinity changes
for the run. Default is on. This is here for A/B testing — run the
same scenario twice and compare. If the hypothesis is correct, the
=0 run should reproduce the v0.24.21 chug pattern and the =1 (default)
run should hold framerate during chunk streaming.

## What this ship deliberately does NOT do

- **Does not revert v0.24.21's GPU mesher wiring.** The
  `UNENDLICH_GPU_MESHER` env var still exists. Its description in
  `runtime_flags.rs` is updated to mark the path as EXPERIMENTAL and
  not recommended for play. The wiring is dormant when the env var
  isn't set (which is the default). Cleaning up the dormant path is
  filed for a later janitorial ship — keeping this diff focused on
  worker isolation.

- **Does not promote the render thread to real-time priority.** RT
  priority (`SCHED_FIFO`) on Linux requires `CAP_SYS_NICE` or an
  `/etc/security/limits.conf` entry, neither of which we can assume
  on a development machine. The deprioritize-loaders strategy works
  without elevated permissions.

- **Does not pin mesh workers to P-cores explicitly.** The Linux
  scheduler's default capacity-aware policy keeps nice=0 threads on
  P-cores while they're CPU-bound. Adding an explicit pin would
  remove the scheduler's ability to migrate work during transient
  bursts (which it does well). If profiling later shows mesh workers
  drifting to E-cores under contention, we can revisit; the
  `ThreadRole::MeshWorker` site is already the obvious place to add
  the call.

- **Does not change the chug detector or any logging.** The probe
  CSV and FPS-log format are unchanged. Existing analyze recipes
  continue to work; comparison is done at the timer-summary level.

## What to look for

The hypothesis: with isolation OFF, the run reproduces the chug
pattern (sustained high frame times during chunk streaming, like
v0.24.21 Run B's 131ms p50). With isolation ON, the render thread
holds its frame budget even during the same chunk-streaming pressure.

Specific metrics that should improve:

| metric | OFF (chug) | ON (fix) — expected |
|---|---|---|
| total p50 | 50–150ms | 5–20ms |
| wait_fences p50 | 100–250ms | 5–20ms |
| shadow p50 | 70–100ms | 2–10ms |
| main p50 | 25–50ms | 1–5ms |
| frames in 30s | 100–300 | 1500–3000 |

The mesher timer's `near` line should be roughly comparable in both
runs (we haven't changed the mesher; we've changed when the mesher's
output gets a chance to display).

If the data shows ISOLATION ON is dramatically better, this ship is
landed and the chug arc closes. If the difference is minimal, the
hypothesis from Increment 61 is wrong (or this fix doesn't address
the right axis of contention) and we'll need to instrument
differently — probably the thread probe showing what each thread is
doing during the chug.

## Honest concerns

1. **E-core detection requires Asahi kernel support.** Asahi exposes
   per-CPU capacity via the standard Linux sysfs path. If a future
   kernel update changes the sysfs layout, the detection falls back
   to "no E-cores found" and only the nice change applies. We'd
   notice at the debug-log level — the affinity isn't logged louder
   because a degraded mode is still a valid run.

2. **World-gen throughput will drop.** Pinning 12 chunk-loaders to
   4 E-cores caps their effective parallelism at 4. The nice +10
   compounds this. Expect terrain pop-in during fast travel to be
   noticeably slower. The trade is intentional: a slower terrain
   stream is preferable to a stuttering render thread, since the
   player perceives frame drops more than they perceive pop-in.

3. **Affinity pinning prevents the kernel from rebalancing during
   transient idle periods.** If chunk-loaders are idle and mesh
   workers want extra CPU, the kernel can't migrate mesh work to
   E-cores temporarily. This is an acceptable cost because mesh
   workers are already on P-cores by default; the constraint only
   matters in the inverse direction (which we don't want).

4. **macOS users get no chug fix.** A future ship can wire up
   `pthread_set_qos_class_self_np` for the same effect using QoS
   classes (`QOS_CLASS_UTILITY` for ChunkLoader, default for the
   rest). Not in scope here.

5. **v0.24.21's GPU mesher is left dormant rather than excised.**
   Removing it cleanly is a larger refactor (drop the
   `with_gpu_mesher` path in `MeshingPool`, drop the env var, drop
   the dispatcher thread spawn, drop the `queue_submit_lock` plumbing).
   The README in `runtime_flags.rs` now marks the path as not
   recommended. A future janitorial ship can do the clean removal.
