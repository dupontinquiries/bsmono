# v0.24.5-surface-extract — sparse surface representation (Layer A.1)

This ship begins a new architectural arc: GPU-resident world with
simulation and rendering sharing the same data structures. See
DESIGN_NOTES.md increment 49 for the strategic framing.

This first step adds the **representation** without yet plugging it
into the GPU mesher. The format is what the GPU kernel will consume;
ship it first as CPU-only code with tests, then in the next session
add the kernel that consumes it.

## What it adds

### `world::surface::SurfaceRecord`

A 16-byte struct describing one block that has at least one exposed
face. Fields: world coordinates (i32 × 3) + packed (block_type, face_mask).

Critical design decision: **world coordinates, not chunk-local**. The
record carries absolute position so the consumer doesn't need "which
chunk" state. When the future octree migration replaces dense `Chunk`
storage, octree leaves already carry world coords; the record format
survives unchanged.

### `world::surface::extract_surface(chunk) -> Vec<SurfaceRecord>`

Walks the dense block grid once, emitting a record for each block
with at least one exposed face (face that produces against its
neighbor). Uses the canonical `BlockId::produces_face_against`
predicate, so output matches what the CPU mesher would surface.

Typical chunk: 1500-3000 records (~24-48KB) for surface terrain.
Compared to the 32KB dense grid, this is roughly the same size in
the worst case, but most chunks compress significantly because
buried and air cells produce no records.

### Tests

7 new tests in `world::surface::tests`:
- empty chunk → empty surface
- single block → 6 faces all exposed
- 3×3×3 cube → 27 cells, 1 buried, 26 surface
- world coords offset correctly by chunk origin
- boundary block emits outward-facing face
- record is exactly 16 bytes (pins wire format)
- packed bits roundtrip correctly

## What it does NOT do

- **No GPU kernel yet.** The compute shader that consumes
  `SurfaceRecord` buffers is filed for the next ship.
- **No Vulkan plumbing yet.** No HOST_VISIBLE upload buffer, no
  pipeline, no descriptor sets. Filed for next ship.
- **No production wiring.** The current mesh path is unchanged;
  CPU mesher still produces all meshes. `extract_surface` is dead
  code until next ship connects it.
- **No greedy / merged quads.** v1 will emit one record per surface
  block. The GPU kernel (next ship) will produce one quad per face
  bit set in the mask. Greedy merging is v2 work.
- **No lighting / AO / tints.** Records carry block type only.

## Why ship this small step alone

The GPU mesher arc is multi-session work. Shipping the CPU-side
representation independently:

1. Validates the wire format with tests before committing to a kernel.
2. Decouples "find surface" from "mesh surface" — the surface set
   is now an explicit, inspectable artifact.
3. Sets up the format that survives the octree migration. Both
   producers (dense scan now, octree walk later) emit the same
   `Vec<SurfaceRecord>`.
4. Keeps each ship reversible. If the next-session kernel work hits
   problems, this code is still useful infrastructure for other
   consumers (debug overlay, save format, network sync).

## Honest concerns

- **Record size 16 bytes might be too big.** Typical chunk has
  ~2000 records → 32KB upload. That's the same as the dense grid
  it replaces. Compression candidates: u8/u8/u8 for chunk-local
  coords + chunk-base separately uploaded once. Defer until we
  have measurements.
- **`is_meshable` predicate may diverge from CPU mesher.** Both
  paths use `produces_face_against`, but the CPU mesher has
  additional handling for sub-voxel decorations (plants, leaves).
  v1 surface set is opaque-blocks-only; v2 kernel will need a
  parallel decoration pass for plants if we want visual parity.
- **Worst-case allocation is unbounded.** A pathological chunk
  with no buried blocks would emit CHUNK_VOLUME records = 32K × 16B
  = 512KB. Real terrain is 5-10% of that. Worth a max-size cap
  later, but not a v1 blocker.
- **No batching across chunks.** v1 emits per-chunk records.
  Batching multiple chunks' records into a single upload + dispatch
  is a clear v3 optimization once we have the per-chunk path
  working.
