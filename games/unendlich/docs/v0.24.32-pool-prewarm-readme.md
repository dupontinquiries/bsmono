# v0.24.32-pool-prewarm

## Tagline

Bin pre-uploads chunk + 6 neighbors to the shared pool before
mesher submission. Closes the v0.24.30 cross-chunk hole where
not-yet-meshed neighbors silently fell back to open-boundary.

## Status

Built autonomously. NOT built with cargo. Tiny patch: one new
method on `WorldRenderer`, ~25 lines added to the bin's submit
loop, both standing on top of v0.24.31's `upload_if_changed`.

## The bug this fixes

v0.24.30's cross-chunk shader reads neighbor octrees from the
shared pool. In v0.24.29+ mode 2, only meshed chunks got into
the pool (the mesher uploaded during dispatch). So at startup,
when chunk X was meshed first and its neighbor N hadn't yet been
meshed:

- Mesher's dispatcher calls `pool.slot(N)` → returns `None`.
- ChunkMetaGpu's `neighbor_octree_base_*` for that direction →
  `u32::MAX`.
- Shader's `sample_or_neighbor` for the boundary cell → hits
  the sentinel → falls back to open-boundary (returns air) →
  mesher emits the boundary face anyway.

Visual result: chunk seams still z-fight at startup. Once both X
and N had been meshed AND something forced X to remesh, the
seam would disappear. Without a forcing event, seams stayed.

## The fix

Bin's submit loop now pre-warms the pool before sending the mesh
request. For each chunk about to be submitted (mode 2 only):

1. Loop over offsets `(0,0,0)` plus the 6 cardinal directions.
2. For each, query `chunk_manager.octree(neighbor_coord)`.
3. If the neighbor's octree exists, call
   `renderer.upload_chunk_octree_versioned(coord, octree, version)`.

The versioned upload short-circuits when the chunk is already
resident at the same version (v0.24.31). So the cost at steady
state is roughly: 7 lookups × ~30 submissions/sec ≈ 210
HashMap ops/sec under the pool lock — basically free.

## When this matters most

- **First playable frame in a new area.** Every chunk submitted
  is new, no neighbors in the pool yet. Pre-warm puts all 7
  (or up to 7, depending on what's loaded) into the pool. The
  mesher sees the neighbors and emits clean seams immediately.
- **After a block edit.** The streaming layer bumps the
  neighbor's version (`bump_neighbor_if_edge`). Pre-warm
  uploads the new data on the next submission of either the
  current chunk or any other adjacent chunk.

## When this DOESN'T help

- **Pool capacity exhaustion.** If you load enough chunks that
  the 256 MB pool fills up, oldest chunks get evicted. A chunk's
  neighbor might still get evicted between pre-warm and mesher
  dispatch (race window: ~1 ms of pool lock acquisition). Not a
  fix in this ship; v0.24.31 docs filed it.
- **World boundary.** At the edge of the loaded set, neighbors
  may not exist in chunk_manager either. Pre-warm skips, shader
  falls back to open-boundary — correct behavior for the world
  edge.

## Performance impact

Pre-warm cost is bounded:
- 7 lookups × 30 submissions/sec = 210/sec, all cache hits at
  steady state.
- First-time uploads happen during chunk loading anyway — pre-
  warm just moves them earlier.

Net: same upload work, scheduled before the dispatch instead of
during it. Pool lock contention slightly redistributes from
dispatcher thread to main thread.
