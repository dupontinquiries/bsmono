# v0.24.NEXT+1 — flush_pending_copies barrier scope tightened

## What

In `mesh_buffer_pool.rs::flush_pending_copies` (the per-frame
TRANSFER → VERTEX_INPUT sync point that runs when
`UNENDLICH_DEVICE_LOCAL_MESH=1`), the post-copy
`vkCmdPipelineBarrier` had its two `BufferMemoryBarrier`s set to
`offset=0, size=vk::WHOLE_SIZE` — covering the entire ~3 GB vertex
and ~2 GB index buffers regardless of how few bytes the frame's
copies actually touched.

Replaced with `bounded_copy_dst_range`, a pure helper that scans
the pending copy regions and returns the tightest `(offset, size)`
covering all of them. The barrier now scopes to that range.

Also: each per-buffer barrier is now emitted **only if** that
buffer had pending copies. Previously both were always emitted
even when only one of vertex/index had work.

## Why this is a real win on Honeykrisp

Apple Silicon AGX hardware (which Honeykrisp drives) tracks
buffer dirty state at page granularity. A `WHOLE_SIZE` barrier
forces the driver to assume every page of the buffer is dirty,
which serializes more of the vertex pipeline against the
transfer than is actually necessary. A bounded range lets the
driver let unaffected pages keep their existing state, allowing
prior vertex/index fetches in flight to drain in parallel with
the transfer for the affected pages.

Drivers that flatten all buffer barriers to whole-buffer state
(some NVIDIA paths in some configurations) see no observable
change — the access masks and pipeline stages are unchanged,
only the range hint differs. Strict refinement everywhere.

## Why this is not Option B

You asked earlier about the "split upload onto a separate
command buffer with a semaphore" pattern. I confirmed in code
that this codebase runs with `MAX_FRAMES_IN_FLIGHT = 1`
(world_renderer.rs:48, intentional) and a single graphics queue
family (no transfer queue plumbed in `VulkanContext`). With
those two facts, a same-queue semaphore between upload-cmdbuf
and draw-cmdbuf is functionally equivalent to the pipeline
barrier we already have, plus extra submit overhead — zero or
slightly negative net effect.

Option B becomes worth the investment **after** one of:
- `MAX_FRAMES_IN_FLIGHT` is bumped to 2 (gives CPU/GPU overlap
  but adds ~1 frame input latency — fights your stated goal).
- A transfer queue family is plumbed in `VulkanContext` setup
  (file not in this zip; touches the Vulkan init path).

The barrier tightening (this ship) gets you the Honeykrisp win
without either of those structural changes.

## Files changed

- `crates/unendlich-engine/src/render/mesh_buffer_pool.rs`
  - New free function `bounded_copy_dst_range` (~12 lines).
  - `flush_pending_copies` body: per-buffer-conditional barrier
    list, bounded ranges instead of `WHOLE_SIZE`.
  - Five new unit tests for the helper.
- `scripts/sanity.sh` — bumped from 25 to 27 tests; swapped out
  three pool-specialty tests to make room for the five new
  `bounded_copy_dst_range_*` tests.

## How to verify

```bash
./scripts/sanity.sh                                           # 27 tests, fast
cargo test --lib --release -p unendlich-engine --features render,gpu  # full 788
```

Expected: `27 passed / 0 failed` on the sanity script, and the
full suite stays 788/0.

The five new tests pin the bounded-range math exactly. If they
pass and the existing `mesh_buffer_pool` tests still pass, the
change is correct.

## Runtime check

```bash
UNENDLICH_RENDER_DISTANCE=6 UNENDLICH_LOD_BANDS=2,6,6 \
UNENDLICH_GPU_MESHER=2 UNENDLICH_GPU_MESHER_MID=1 \
UNENDLICH_ADAPTIVE_UPLOADS=1 UNENDLICH_SUBMIT_SKIP=1 \
UNENDLICH_SLACK_SCHEDULER=1 UNENDLICH_BIASED_SHELL_WALK=1 \
UNENDLICH_UPLOAD_PRIORITY=1 UNENDLICH_DEVICE_LOCAL_MESH=1 \
  cargo run --release --bin unendlich-world --features render,gpu
```

Watch the `wait_fences` numbers in the FPS log line (or the
`wait_fences_spike` events in `events.jsonl`). The reduction
will be most visible during peak upload pressure: opening a
fresh chunk neighborhood, large LOD-band crossings, or
re-mesh storms after edits.
