# v0.24.17-worker-sweep — extract worker-count sweep

Bench-only ship. Engine code unchanged.

## What's added

Times both extractors at worker counts [1, 2, 4, 8, 16] and prints
a table:

```
Worker-count sweep (extract time vs worker count):
  workers  records_us  rec_speedup     runs_us  run_speedup
        1       ~14000        1.00×       ~20000        1.00×
        2        ~7500        ~1.9×       ~10500        ~1.9×
        4        ~3500        ~4.0×        ~4500        ~4.4×
        8        ~2500        ~5.6×        ~3000        ~6.7×
       16        ~2200        ~6.4×        ~2700        ~7.4×
```

(Predictions — actual numbers depend on M2 Max thermal state, what
else is running, etc.)

The speedups in the table are vs the 1-worker baseline measured in
the SAME run, so they're internally consistent regardless of
absolute timing noise.

## What I expect to find

M2 Max has 12 cores (8 performance + 4 efficiency). Three reads on
what the sweep will show:

1. **2-worker sees ~1.9×** — basically free; second worker fits
   easily.

2. **4-worker speedup drops below 4×.** Already saw 2.04-2.17× in
   v0.24.15 (the per-extractor case where the 1-worker baseline
   came from a SEPARATE sequential run). The sweep's 1-worker
   baseline should be similar to the v0.24.15 sequential extract
   time, making the 4-worker number more consistent at ~4×.

3. **8 and 16 workers see diminishing returns.** Likely 5-7×
   speedup at 8, maybe 6-8× at 16. The bottleneck is probably
   memory bandwidth (each extract touches a chunk's 32³ × 1B =
   32 KB of data; 4 chunks at once = 128 KB pushed through cache).
   Beyond ~8 workers there's likely no improvement and possibly
   regression as e-cores join in.

4. **Hard ceiling at 36×.** 36 chunks in the workload means worker
   counts > 36 would have idle workers. 16 workers × 2.25
   chunks-per-worker is already very thin. For a wider workload
   (say 200 chunks) higher worker counts would have more headroom.

## Why this is just curiosity

This won't change the architectural conclusions:
- Even at the best worker count, GPU v3 honest total (extract +
  dispatch) is bounded below by the 2 ms dispatch floor.
- Even if extract drops to 1.5 ms with 16 workers, total is ~3.5 ms.
- That barely beats CPU naive parallel (5.4 ms, also benefiting
  from parallelism).
- The structural argument doesn't change.

But it's nice to see the curve.
