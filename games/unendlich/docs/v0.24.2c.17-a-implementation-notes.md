# c.17-a implementation notes — multiview shadow render pass

**Status:** plan + code sketch. NOT YET SHIPPED. Written during a
working session between c.13-instrumentation-followup and starting
c.17-a, to capture the actual diff layout so the implementation
session can be focused execution rather than exploration.

**Companion:** `docs/v0.24.2c.17-plan.md` (higher-level arc plan).
This doc is more concrete; the arc plan is more strategic.

## Goal (c.17-a only)

Make the shadow pass render all 4 cascades via multiview, in ONE
render pass, in ONE indirect draw. **Visual output identical** to
c.13-instrumentation-followup — the main fragment shader still
samples only cascade 0, so layers 1-3 are filled-but-unused.

Expected perf result: shadow_p50_ms ROUGHLY EQUAL or SOMEWHAT HIGHER
than c.13-instrumentation-followup's 113.9ms baseline. The win is in
c.17-c when the main fragment shader actually uses cascades 1-3.

If shadow_p50_ms is anywhere near 4× higher (≈ 450ms), multiview is
working but expensive — proceed to c.17-b for frustum-union culling.
If between 110-160ms, multiview is enabling vertex-transform sharing
and we've already got a free win on the wiring.

## Code change shape

Five files change. In dependency order:

1. **`render/context.rs`** — enable multiview feature on device.
2. **`render/shadow_map.rs`** — switch image view to 2D_ARRAY,
   render pass to multiview, framebuffer to 4 layers.
3. **`shaders/chunk_shadow.vert`** — read cascade VP from
   view_params SSBO indexed by `gl_ViewIndex`.
4. **`render/shadow_pipeline.rs`** — descriptor set layout adds
   view_params SSBO binding.
5. **`render/world_renderer.rs`** — descriptor write for
   view_params on shadow pipeline; drop the cascade-VP push constant
   (replaced by SSBO read).

## File-by-file diff

### 1. `crates/unendlich-engine/src/render/context.rs`

Enable the multiview feature on the logical device. Today:
- Multiview support is probed (`multiview_support()`).
- The probe result is published in the GpuInfo blob.
- But the device-create chain doesn't request the feature, so it's
  actually disabled at runtime even though the driver supports it.

Add `PhysicalDeviceVulkan11Features::multiview(true)` to the chain:

```rust
// Around line 431, alongside vulkan12:
let mut vulkan11 = vk::PhysicalDeviceVulkan11Features::builder()
    .multiview(true)
    .build();

// ...

let info = vk::DeviceCreateInfo::builder()
    .queue_create_infos(&queue_infos)
    .enabled_extension_names(&device_exts)
    .enabled_features(&features)
    .push_next(&mut vulkan11)
    .push_next(&mut vulkan12);
```

**Risk:** older drivers might not support `PhysicalDeviceVulkan11Features`.
We require Vulkan 1.2 already, so 1.1 features struct is always
available. No risk.

**Test:** existing `tests/specs/rd2_smoke.unendtest` should still pass.
If `vkCreateDevice` returns `ERROR_FEATURE_NOT_PRESENT`, we'd need to
make this conditional on `multiview_support().multiview == true`, but
c.13-scout proved this is the case on the target hardware.

### 2. `crates/unendlich-engine/src/render/shadow_map.rs`

Three changes inside `ShadowMap::new`:

**(a)** Image view from layer-0-only to all-4-layers, 2D_ARRAY:

```rust
let view_info = vk::ImageViewCreateInfo::builder()
    .image(image)
    .view_type(vk::ImageViewType::TYPE_2D_ARRAY)  // was TYPE_2D
    .format(format)
    .subresource_range(vk::ImageSubresourceRange {
        aspect_mask: vk::ImageAspectFlags::DEPTH,
        base_mip_level: 0,
        level_count: 1,
        base_array_layer: 0,
        layer_count: NUM_CASCADES,                // was 1 via cascade_subresource_range(0)
    });
```

But — we ALSO need a layer-0-only sampling view because the main
fragment shader's `sampler2DShadow` reads only cascade 0 in c.17-a.

Actually wait. If we change `view` to a 2D_ARRAY view, the existing
descriptor write that binds it to `sampler2DShadow` in the main
fragment shader will fail validation (type mismatch). We'd need
either:

- Two views in ShadowMap: `view_array` (4-layer, used as framebuffer
  attachment for multiview) and `view_sample_c0` (1-layer, used as
  sampler descriptor source). Cleanest.
- Or change the main fragment shader to use `sampler2DArrayShadow`
  with hardcoded layer 0. Smaller diff but conflates concerns —
  c.17-c will switch it to per-fragment cascade selection, and
  introducing the array-sampler at c.17-a versus c.17-c is fine but
  premature.

**Decision: two views.** `view` is renamed `view_array` (rendering
target), and a new field `view_sample_c0` is the 1-layer view bound
to the sampler. The main fragment shader's descriptor write switches
from `view` to `view_sample_c0`. Semantics preserved exactly.

```rust
pub struct ShadowMap {
    pub format: vk::Format,
    pub image: vk::Image,
    pub memory: vk::DeviceMemory,
    /// 4-layer view used as the multiview framebuffer attachment.
    /// Each `gl_ViewIndex` rasterizes into the corresponding layer.
    pub view_array: vk::ImageView,
    /// 1-layer view of cascade 0, bound to the main fragment shader's
    /// `sampler2DShadow`. Will be replaced by `sampler2DArrayShadow`
    /// + per-fragment cascade selection in c.17-c.
    pub view_sample_c0: vk::ImageView,
    pub sampler: vk::Sampler,
    pub framebuffer: vk::Framebuffer,
    pub render_pass: vk::RenderPass,
    pub extent: vk::Extent2D,
}
```

Construction:
```rust
let view_array_info = vk::ImageViewCreateInfo::builder()
    .image(image)
    .view_type(vk::ImageViewType::TYPE_2D_ARRAY)
    .format(format)
    .subresource_range(vk::ImageSubresourceRange {
        aspect_mask: vk::ImageAspectFlags::DEPTH,
        base_mip_level: 0,
        level_count: 1,
        base_array_layer: 0,
        layer_count: NUM_CASCADES,
    });
let view_array = unsafe { device.create_image_view(&view_array_info, None)? };

let view_sample_c0_info = vk::ImageViewCreateInfo::builder()
    .image(image)
    .view_type(vk::ImageViewType::TYPE_2D)
    .format(format)
    .subresource_range(cascade_subresource_range(0));
let view_sample_c0 = unsafe { device.create_image_view(&view_sample_c0_info, None)? };
```

**(b)** Render pass: attach `RenderPassMultiviewCreateInfo`:

```rust
// view_mask: bits 0,1,2,3 set = render all 4 cascades simultaneously.
// One value per subpass; we have one subpass.
let view_masks = [0b1111u32];
// correlation_masks: optional optimization hint that all views are
// in the same view-group (the driver can share more state). One per
// subpass.
let correlation_masks = [0b1111u32];
let mut multiview_info = vk::RenderPassMultiviewCreateInfo::builder()
    .view_masks(&view_masks)
    .correlation_masks(&correlation_masks);
// view_offsets: not used (only relevant for cross-subpass dependencies
// with view dependencies). Leave empty.

let rp_info = vk::RenderPassCreateInfo::builder()
    .attachments(&attachments)
    .subpasses(&subpasses)
    .dependencies(&dependencies)
    .push_next(&mut multiview_info);
```

**(c)** Framebuffer: use the 4-layer view, `layers(1)` instead of
`layers(NUM_CASCADES)`. Yes, ONE. The multiview spec says the
framebuffer's `layers` field must be 1 when the render pass is
multiview-enabled; the view_mask determines layer count instead.

```rust
let attachments = [view_array];  // was [view]
let fb_info = vk::FramebufferCreateInfo::builder()
    .render_pass(render_pass)
    .attachments(&attachments)
    .width(extent.width)
    .height(extent.height)
    .layers(1);  // STAYS 1 — multiview attachments use view_mask, not framebuffer layers
let framebuffer = unsafe { device.create_framebuffer(&fb_info, None)? };
```

This counter-intuitive rule is a known multiview gotcha. The
multiview render pass info's view_mask = 0b1111 tells the driver to
render 4 views; the framebuffer's layers stays 1 because the
attachment view itself is the 4-layer array view.

**Cleanup:** `destroy()` must destroy both image views.

### 3. `crates/unendlich-engine/src/shaders/chunk_shadow.vert`

Replace push-constant cascade VP read with SSBO indexed by
`gl_ViewIndex`. Enable the multiview extension at the top:

```glsl
#version 450
#extension GL_EXT_multiview : require    // adds gl_ViewIndex

layout(location = 0) in vec3 in_position;
layout(location = 1) in vec3 in_color;

// view_params SSBO — same struct layout as in chunk.vert, cull, etc.
// Bound at set=0 binding=1 (new for shadow pipeline; was unused before).
struct ViewParam {
    mat4 view;
    mat4 projection;
    mat4 view_proj;
    mat4 inverse_view_proj;
    vec4 camera_pos;
    vec4 near_far_aspect;
    vec4 planes[6];
};
layout(set = 0, binding = 1, std430) readonly buffer ViewParams {
    ViewParam views[];
} view_params;

// Slot layout (must match crates/unendlich-engine/src/render/view_params.rs):
//   slot 0 = VIEW_SLOT_MAIN
//   slot 1..=4 = VIEW_SLOT_SHADOW_C0..C3
// So cascade i (gl_ViewIndex i) reads from slot 1 + i.

void main() {
    uint cascade_slot = 1u + gl_ViewIndex;
    mat4 cascade_vp = view_params.views[cascade_slot].view_proj;
    vec3 used = in_color;     // keep attribute alive
    gl_Position = cascade_vp * vec4(in_position, 1.0);
    gl_Position.x += used.x * 0.0;
}
```

**Push constant block can be removed** — nothing reads it now.

**Risk: descriptor binding mismatch.** The current shadow pipeline
has `set 0 binding 0 = CameraUbo` only. Adding `binding 1 = ViewParams`
requires extending the descriptor set layout (see file 4) AND adding
a descriptor write (see file 5). If the shader requires a binding
the layout doesn't provide, pipeline creation fails.

**Compile step:** the .vert file is precompiled with glslangValidator
into chunk_shadow.vert.spv in assets/shaders/. Need to regenerate. Look
at `commands/` for how shaders get rebuilt; there's likely a script.

### 4. `crates/unendlich-engine/src/render/shadow_pipeline.rs`

**Discovery during planning:** the shadow pipeline currently SHARES
the main pipeline's per-frame descriptor set (the docstring confirms
this — see `shadow_pipeline.rs` line 156 comment). The two pipelines
have IDENTICAL descriptor set layouts because their descriptor sets
are interchangeable at draw time.

Today's layouts:
- **Main pipeline DSL:** binding 0 = UBO (VERTEX|FRAGMENT), binding
  1 = COMBINED_IMAGE_SAMPLER (shadow texture), binding 2 =
  COMBINED_IMAGE_SAMPLER (froxel volume).
- **Shadow pipeline DSL:** binding 0 = UBO only.

Wait — they're not identical today either. Let me look again.

Actually they ARE compatible-via-superset: the shadow DSL has a
subset of bindings (only 0), so a descriptor set allocated for the
main DSL can be bound to the shadow pipeline (the shadow shader only
reads binding 0, which is there). This works because Vulkan allows
the pipeline-time DSL to declare fewer bindings than the descriptor
set provides.

**The right move:** add view_params (binding 3, STORAGE_BUFFER,
VERTEX stage) to BOTH pipelines' DSLs. The main fragment shader
ignores it; the shadow vertex shader reads from it.

```rust
// chunk_pipeline.rs — main pipeline DSL gains binding 3:
let dsl_bindings = [
    /* binding 0: UBO */
    /* binding 1: shadow image sampler */
    /* binding 2: froxel image sampler */
    vk::DescriptorSetLayoutBinding::builder()
        .binding(3)
        .descriptor_type(vk::DescriptorType::STORAGE_BUFFER)
        .descriptor_count(1)
        .stage_flags(vk::ShaderStageFlags::VERTEX)
        .build(),
];
```

```rust
// shadow_pipeline.rs — shadow DSL gains binding 3 too:
let dsl_bindings = [
    /* binding 0: UBO */
    vk::DescriptorSetLayoutBinding::builder()
        .binding(3)
        .descriptor_type(vk::DescriptorType::STORAGE_BUFFER)
        .descriptor_count(1)
        .stage_flags(vk::ShaderStageFlags::VERTEX)
        .build(),
];
```

(Yes, both DSLs declare binding 3 with the same stage flag, even
though only the shadow pipeline's vertex shader actually reads it.
This is correct — Vulkan checks that the DSL is a SUPERSET of what
the shader needs, not an exact match.)

**Update the vertex shader:** point at `binding = 3`, not `binding = 1`:

```glsl
layout(set = 0, binding = 3, std430) readonly buffer ViewParams {
    ViewParam views[];
} view_params;
```

**Push constant range drops** from shadow_pipeline.rs (lines 176-184):
just remove the whole `pcr` block and `push_constant_ranges` chain
from the layout builder.

**Risk:** the main pipeline's descriptor pool must be sized to
include the new STORAGE_BUFFER allocation. Check the pool sizing in
world_renderer.rs's `create_descriptor_pool` (or wherever it lives)
and bump the STORAGE_BUFFER count.

### 5. `crates/unendlich-engine/src/render/world_renderer.rs`

Three changes:

**(a)** Descriptor write to bind view_params SSBO to shadow pipeline's
descriptor set, alongside the existing CameraUbo write. Look for the
existing shadow-descriptor write block. Add binding=1 ViewParams.

**(b)** Drop the `cmd_push_constants` call for cascade_vp (line ~1936
in the current file).

**(c)** The descriptor write for sampler currently uses
`self.shadow.view`. Update to use `self.shadow.view_sample_c0` (the
1-layer view) since the main frag still reads cascade 0 only.

**(d)** Switch shadow pipeline's per-frame descriptor set to be the
SAME as the main pipeline's per-frame set (since both need the same
view_params SSBO). Or, alternatively, add a separate shadow descriptor
set with the SSBO bound. The cleaner path is "reuse the main
descriptor set" because the shadow pipeline already binds it at draw
time.

Need to look at the actual current wiring during the implementation
session to decide; both paths work.

## What c.17-a does NOT include

- Frustum culling for the multiview pass (c.17-b).
- Per-fragment cascade selection in the main shader (c.17-c).
- Per-cascade resolution tuning (c.17-d).
- The `UNENDLICH_MULTIVIEW_SHADOWS=0` fallback env var. Originally
  planned in the arc doc. **Drop it.** Reason: a half-working
  multiview path is more confusing than a complete rollback via
  `git revert`. Easier to bisect.

## Questions to answer before starting

1. **Should the shadow pipeline reuse the main descriptor set, or have
   its own?** Decided during implementation; affects (5d). Either
   works.

2. **Do we need to invalidate any shader cache when switching the
   shader?** If shaders are precompiled and cached, the build process
   must rebuild chunk_shadow.vert.spv. Check `commands/` and Cargo
   build scripts for the actual compilation step.

3. **Is the framebuffer's `layers(1)` correct under multiview?** I
   wrote that above based on what I think the spec says. **VERIFY**
   against the Vulkan spec on
   `VK_KHR_multiview` before shipping — this is a known footgun.

4. **Will the existing fragment shader fail validation when we change
   the sampler view from 2D to 2D (different image)?** The descriptor
   write just rebinds; the type is unchanged (still TYPE_2D
   sampler2DShadow). Should be fine but worth verifying.

5. **The shadow pass's existing subpass dependency uses
   `FRAGMENT_SHADER` and `EARLY/LATE_FRAGMENT_TESTS` stages — does
   multiview change which stages are involved?** Need to check whether
   `VK_DEPENDENCY_VIEW_LOCAL` is needed in dependency flags.

## Honest concerns

- **Subpass dependency stages might need `VK_DEPENDENCY_VIEW_LOCAL`.**
  The current dependencies don't specify it; multiview spec says
  it's the safe default if you don't have cross-view dependencies.
  Verify before shipping.

- **Honeykrisp's multiview path might be undertested.** c.13-scout
  confirmed multiview is REPORTED supported (`max_views=32`), but
  not that complex multiview render passes work without driver bugs.
  Brand-new driver = high risk of edge-case bugs. **Mitigation:**
  start with rd2 (small load), confirm it works, then escalate to
  rd8. If rd2 hits any Vulkan error, do not proceed to rd8 — file
  the bug and pause c.17 for driver investigation.

- **The `c.13-instrumentation-followup`'s `UNENDLICH_SHADOW_BUCKETS`
  also tripped DEVICE_LOST on Honeykrisp, with timestamps inside the
  render pass.** c.17-a does NOT use timestamps inside passes — the
  gpu_timer continues to write timestamps OUTSIDE the render passes.
  So that specific failure mode shouldn't recur. But the Honeykrisp
  shadow-pass code path is now known-fragile, so be alert.
