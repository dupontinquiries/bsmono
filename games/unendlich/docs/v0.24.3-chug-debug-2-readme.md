# v0.24.3-chug-debug-2 — per-frame GPU zone correlation

Second diagnostic ship. Builds on chug-debug-1's GPU-bound diagnosis
by adding per-frame per-zone GPU spike logging. Tells us not just
"GPU was slow" but "which pass on the GPU was slow."

## What it adds

When a frame's `total` GPU zone exceeds 100ms, the engine emits a
`gpu_spike` event with:

- `frame_idx` — matches the field name in `wait_fences_spike` so
  external tools can join on (uuid, frame_idx).
- `total_us` — total GPU time for the frame.
- `shadow_us` / `main_us` / `froxel_us` / `cull_us` — per-zone
  breakdown.

The threshold (100ms) is hardcoded for now. It catches outliers
without flooding events.jsonl during normal frames. If our hypothesis
that one pass dominates each spike is right, the per-zone breakdown
identifies the culprit.

## Why this ship is small

chug-debug-1 ruled out CPU-side causes (76/76 spikes were GPU-bound).
chug-debug-2 narrows the GPU side to a specific pass without changing
any engine behavior. **Diagnostic-only, no scheduling changes.**

Per c.17-a's regression cautionary tale, each diagnostic ship is the
smallest possible change that answers ONE question. After this ship's
data, the next ship is either a targeted fix (if one pass dominates)
or further instrumentation (if the data is ambiguous).

## What it doesn't do

- No fix. Diagnostic only.
- No new env vars.
- No engine API changes (gpu_timer.rs stays engine-agnostic; the
  per-frame data is exposed via `take_last_frame()`, the event
  emission happens in the engine-aware caller world_renderer.rs).
- Doesn't measure within-pass detail. If shadow spikes are uniform
  across the pass vs. concentrated in one draw, this won't tell us
  — we'd need GPU-side instrumentation (timestamps inside the pass).

The **Culprit summary** is the answer we want: which pass dominates
the chug events.

## Interpretation guide

After running, the four likely diagnoses:

- **Shadow dominates (>60% of spikes)**: shadow pass occasionally
  takes 100-200ms despite p50 ~0.7ms. Probable cause: a chunk that
  just loaded has a degenerate draw signature, or the cull compute
  buffer is being read inconsistently. Fix candidates: shadow-pass
  budget limit, descriptor barrier hardening, shadow cascade-level
  worklist throttling.

- **Main dominates (>60%)**: main pass occasionally takes 100ms+
  despite p50 ~0.5ms. Probable cause: similar to shadow but on
  the main draw. Fix candidates: same as shadow but on main.

- **Froxel/cull dominates**: surprising and would point at a
  different mechanism. Probably compute-shader scheduling.

- **No single dominator (each spike has a different culprit)**:
  the chug is a higher-level effect — possibly GPU scheduler
  (Honeykrisp), compositor (KWin), or DVFS clock-ramp. Would
  point at platform-level investigation rather than engine code.

## Honest concerns I want to flag

- **The 100ms threshold is arbitrary.** It catches the chugs we care
  about. If most of your "felt" hitches are between 50-100ms, we'd
  miss them. Worth checking the wait_spikes p50/p99 from chug-debug-1
  — if p50 wait was 110ms, then 100ms gpu_spike threshold catches the
  same events. Good correspondence expected.

- **`gpu_spike` events are emitted with a frame delay** — the GPU
  data is collected one frame after submit completes (that's how
  gpu_timer works). The frame_idx in the event is the SLOT idx
  (0..MAX_FRAMES_IN_FLIGHT), not a global frame counter. Joining
  wait_spike and gpu_spike on frame_idx will produce many matches
  per slot over a run. This is fine for aggregate analysis but
  per-event 1:1 join needs a more careful join key (timestamps).

- **One pass can mask another.** If shadow takes 80ms and main takes
  80ms, total is 160ms and either could be "the culprit." The
  per-zone breakdown helps but exact attribution at the edge is
  fuzzy. We'd address that with sub-pass instrumentation if needed.
