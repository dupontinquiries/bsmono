# v0.24.10-gpu-mesh-runs — GPU runs kernel + v3 bench path

Builds on v0.24.9's `SurfaceRun` representation. Adds the GPU kernel
that consumes runs and emits one quad per run. The bench now compares
three GPU paths (v1 per-chunk-submit, v2 batched-records, v3 batched-runs)
plus the parallel CPU baselines.

## What's added

### `chunk_mesh_runs.comp` compute shader

One thread per run. Reads `SurfaceRun` (16 bytes), decodes face
direction and length, emits exactly one axis-aligned quad covering
the full run extent. Same per-chunk slot layout as the records
kernel — uses the same vertex/index/counter buffers and per-chunk
offset push constants.

Per face direction the quad's two in-plane axes are:
- +X/-X: Y (run axis) × Z
- +Y/-Y: X (run axis) × Z
- +Z/-Z: X (run axis) × Y

Quad winding is counter-clockwise from outside the face (matches
the records kernel convention).

### `SparseGpuMesher::mesh_chunks_batch_runs`

Mirror of `mesh_chunks_batch` but for the runs path. Takes
`&[ChunkBatchInputRuns]` with each chunk's `&[SurfaceRun]`,
returns `Vec<ChunkBatchOutput>` with per-chunk `Result<ChunkMesh>`.

The mesher now owns TWO compute pipelines (`pipeline` for records,
`runs_pipeline` for runs). They share descriptor set layout, push
constants, and per-chunk buffers. Only the bound pipeline differs
between dispatches.

### Bench v3 section

After the v2 batched section and the SurfaceRun compression
analysis, the bench adds a "Runs (v3) path" section reporting:

- Total wall-clock for batched runs dispatch over all 36 chunks
- Quad count comparison: v3 should emit ~3-5× fewer quads than v2
  (the compression ratio measured by the runs analysis)
- Topology validation: per chunk, `quads_emitted == runs.len()`
  AND `sum(run_lengths) == cpu_naive_quad_count`. Both checks
  must pass for each chunk.
- Speedups: v3 vs v1, v2, CPU sequential

Final summary table now includes v3 alongside v2 with the same set
of speedup ratios (vs sequential, vs parallel naive, vs MeshingPool).

## What I'm predicting

The compression ratio (records → runs) is unknown — first measurement
comes from this bench. I'm guessing ~3-4× for natural terrain based
on how horizontal floors and walls dominate surface area in our
generated chunks.

If compression is 3×: v3 should land around 5400/3 = ~1800 us total.
That would put v3 at:
- ~3.0× faster than v2
- ~6× faster than CPU naive sequential
- ~2× faster than CPU naive parallel
- ~9× faster than MeshingPool

**That would be a clear Layer A.3 production-wiring justification**
even accounting for v3's unlit flat colors vs MeshingPool's
greedy+sky-lit.

If compression is closer to 5×: v3 lands around 1100 us. Even better.

If compression is closer to 2× (worst case): v3 lands around 2700 us.
Still beats CPU naive parallel (3800-5500 us) modestly.

## Topology validation expected to hold

For each chunk:
- `quads_emitted == runs.len()` because the kernel emits exactly
  one quad per run.
- `sum(run.length) == cpu_naive.indices.len() / 6` because every
  surface face is covered by exactly one run, and the run's length
  IS the number of face-blocks it covers.

If either check fails, the kernel has a bug. Most likely
suspects: face-direction confusion in the kernel's quad-corner math,
or a run that crosses an axis-direction boundary incorrectly in the
extractor.

## Risks I want to flag

1. **First time running new kernel on AGX hardware.** Same risk
   profile as v0.24.6: validation errors, DEVICE_LOST, or wrong
   output. Topology check catches wrong output; validation errors
   would show in stderr.

2. **Kernel face-direction math is dense.** I wrote 6 separate
   if-else branches with quad corner positions. Each face's winding
   has to be CCW from outside. I followed the records kernel's
   convention but they're not byte-identical because runs are
   stretched along U. If output is visually correct but normals
   are reversed for some face, indices need a winding flip.

3. **Topology check is "expected face count matches CPU" not
   "quads cover same world area."** The check would pass even if
   the kernel emits the right NUMBER of face-blocks but at wrong
   world positions. To catch that we'd need vertex position
   comparison. Filed for later — it would catch a rare bug class
   that's unlikely if the per-face math is right.

4. **I did not test the new kernel on hardware.** I cannot. If the
   bench crashes or shows topology mismatches, that's tomorrow's
   work.
