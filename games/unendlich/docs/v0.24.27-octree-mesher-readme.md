# v0.24.27-octree-mesher — first octree-driven consumer

## What this ships

A new GPU mesher path that reads each chunk's `OctreeArray` directly
from a HOST_VISIBLE SSBO, in place of CPU-extracted `SurfaceRecord[]`.
This is the first **consumer** of the v0.24.26 octree substrate
(which until now was probe-validated but unread by any production
path).

Opt-in via `UNENDLICH_GPU_MESHER=2`. The existing modes are
preserved:

| Value | Mesher | Input |
|-------|--------|-------|
| `0` or unset | CPU greedy mesher | `Chunk` |
| `1` | `SparseGpuMesher` | CPU-extracted `SurfaceRecord[]` |
| `2` (new) | `OctreeGpuMesher` | `Arc<OctreeArray>` (GPU reads directly) |

## What does NOT change

- The CPU mesher's weathering / corner displacement aesthetic. Mode 0
  remains the default and is unaffected.
- The sparse GPU mesher (`UNENDLICH_GPU_MESHER=1`). Untouched.
- Octree substrate (`OctreeBufferPool`, `octree_probe.comp`).
  Untouched.
- Visual production output. Mode 2 isn't the default and produces a
  visually-different (strict Camp 1, no bumpiness) mesh than the CPU
  mesher; using it for actual play would look worse. That's why it's
  opt-in.

## Architecture: which problem this ship moves

Architecture-v1 §3.1 calls for **one substrate read by all
consumers** — the octree. v0.24.26 landed the substrate. v0.24.27 is
the first ship where a real GPU consumer reads it. After this:

- Octree is uploaded by the renderer (substrate consumer #1: visible
  state).
- Octree is read by the GPU mesher when `=2` (substrate consumer #2:
  geometry generation).
- Octree is verified by the probe when `UNENDLICH_OCTREE_VERIFY=1`
  (substrate falsification, not a consumer per se).

This validates the *pattern*: an octree-driven kernel can produce
correct output. Future consumers (raycast, AI sensing, server replica)
follow the same template.

## Scope of this ship — what's deliberately deferred

This is **Ship A** of a two-ship arc per `architecture-v1.md` §6.1
(weathered-block aesthetic). Ship A foundations, Ship B bumpiness.

### Deferred: cross-chunk neighbor lookups

The shader treats out-of-chunk neighbors as air (open boundary). At
chunk borders, the visible side of the boundary block will emit a
face that the adjacent chunk's interior block ALSO emits — net
result is two faces touching at a chunk boundary, which can z-fight
or look double-shaded.

Mitigation in this ship: none. The mesher is opt-in and the visual
artifact is acceptable for a foundation ship.

Fix in a follow-up: bind 7 octrees per dispatch (self + 6 neighbors),
the shader looks up the neighbor's octree directly. Requires either
expanding the per-dispatch metadata SSBO to carry neighbor base_node
indices, or refactoring the meshing pool to share the renderer's
`OctreeBufferPool` buffer (which has every loaded chunk).

### Deferred: Camp 1.5 bumpiness (Ship B)

The shader emits 4 vertices per face (strict Camp 1). The CPU
mesher's per-corner displacement (`corner_y_offset`,
`surface_bumps`, weathering modulation) is *not* implemented here.
Ship B will add a parallel weathering instance buffer + 4×4
sub-vertex grid emission. See `docs/architecture-v1.md` §6.1 for
the design.

The 4×4 choice (instead of 8×8 from the meinkraft predecessor)
trades visual fidelity for mesh size — 16× vertices per emitting
face instead of 64×. We'll bench Ship B and revisit if the 4×4
visual reads weakly compared to what the CPU mesher already
produces.

### Deferred: full color parity with CPU mesher

The shader has a minimal per-block-id color lookup (`color_for_block`
in the GLSL). The CPU mesher applies climate tinting (humidity /
temperature / sky exposure) per face via
`compute_tinted_color_for_face`. That's not replicated here. Mode 2
will look "block-stamped" rather than the CPU mesher's organic
gradient.

Fix in a later ship: GPU-side climate tinting (requires the climate
field on GPU, which is its own substrate).

## How to falsify this ship

1. **Build cleanly.** The mesher path has no Cargo dependencies it
   didn't already have. `cargo build --release --features render` in
   the engine crate should succeed.
2. **Default mode unaffected.** Run with `UNENDLICH_GPU_MESHER=0` (or
   unset). World loads, chunks mesh, visuals are the bumpy CPU
   mesher. F3 stats look like steady-state v0.24.26 (`main p50 ~2.5ms
   shadow p50 ~4ms`).
3. **Mode 1 unaffected.** Run with `UNENDLICH_GPU_MESHER=1`. Same as
   v0.24.26 — strict-Camp-1 sparse mesh, no bumpiness.
4. **Mode 2 works.** Run with `UNENDLICH_GPU_MESHER=2`. Expected logs
   at startup:
   ```
   UNENDLICH_GPU_MESHER=2: constructing OctreeGpuMesher
   OctreeGpuMesher initialized (octree bytes per slot=327680, vert cap=65535, idx cap=65535)
   MeshingPool ready (4 workers + Octree-GPU dispatcher, capacity 64)
   ```
   World loads. Chunks mesh (Near tier through GPU, Mid/Far/VeryFar
   through CPU as before). The visual is strict Camp 1, no
   bumpiness, with possible chunk-boundary z-fighting (the
   open-boundary artifact).
5. **Verify probe still passes.** With
   `UNENDLICH_GPU_MESHER=2 UNENDLICH_OCTREE_VERIFY=1`, shutdown
   should report 0 mismatches (octree substrate is unchanged from
   v0.24.26; this confirms mode 2 doesn't corrupt it).
6. **Clean shutdown.** Quit the game. Logs should show:
   ```
   Pre-exit: dropping mesh_pool ...
   Pre-exit: dropped mesh_pool
   Pre-exit: dropping GPU mesher (if active)...
   Pre-exit: dropped GPU mesher
   Dropping Vulkan context...
   Shutdown complete.
   ```
   If the octree dispatcher hangs, the join in `MeshingPool::drop`
   blocks here. Fix would be to also close the
   `octree_gpu_request_tx` — the current Drop impl does this via
   `take()`.

## Per-chunk cost / capacity notes

- Each batch slot reserves `MAX_NODES_PER_CHUNK = 8192` octree-node
  entries × 40 bytes = 320 KB. 64 slots × 320 KB = 20 MB
  HOST_VISIBLE storage for the octree buffer. Most chunks use far
  less (typical surface chunk ~500-2000 nodes); the slot is
  over-allocated to keep base-index math trivial.
- Vertex + index + counter buffers are sized identically to the
  sparse mesher (65 535 verts × 24 bytes × 64 slots = ~100 MB per
  buffer pair). Same total ~200 MB for output, matching mode 1.
- Per dispatch: one submit, one wait. Same submission shape as the
  sparse mesher.
- Per-thread work in the shader: 7 octree samples (self + 6
  neighbors) at depth 5 = ~35 memory reads worst case, plus
  potentially 6 quad-emissions per cell.
- Workgroups per chunk: 512 (32³ cells / 64 workgroup size).
  Workgroups per batched dispatch: 512 × batch_size.

## Bench expectations vs sparse

Educated guess (no bench yet):
- Octree mode skips CPU `extract_surface` (~50–300µs per chunk),
  but adds GPU-side neighbor sampling which is more work per
  thread. Net per-batch GPU time should be similar to sparse, maybe
  ~10-30% slower because of the extra neighbor lookups vs sparse's
  pre-computed face mask.
- The architectural payoff isn't speed in this ship. It's "we now
  have a kernel that reads the octree, which is the substrate the
  whole architecture is moving toward."

Bench can be measured by toggling between `=1` and `=2` and
comparing F3's mesh log lines.

## Pattern note: substrate ship + consumer ship

v0.24.26 landed the substrate; nobody consumed it. v0.24.27 lands
the first consumer; the substrate is *exercised*. This is the
two-step pattern the architecture wants for every GPU-resident
addition:

1. **Substrate ship.** Wire format pinned with a compile-time size
   assert. Probe consumer for falsification. No production path
   reads it yet.
2. **Consumer ship.** First real reader migrates. Opt-in so the
   production path is unaffected if the consumer has bugs. Lessons
   learned feed back into the substrate if the contract is wrong.

The cost is "two ships per architectural addition" but the value is
"each ship is independently falsifiable and reversible." The
v0.24.26 probe-fix1 (chunk-local-vs-global indices) is the
existence proof — caught a real bug at the substrate boundary
without any consumer to confuse the debugging.
