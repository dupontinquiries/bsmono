# v0.24.3-shadow-size — `UNENDLICH_SHADOW_MAP_SIZE` knob

The chug-debug arc found, finally with rd=8 data, that shadow pass
geometry cost is the dominant chug source. **At rd=8, shadow exceeds
the 8.3ms frame budget in 96.5% of frames** with p50 = 77ms. This is
not a tail phenomenon; it's the steady state.

This ship adds a runtime knob to test how much of that shadow cost
is fragment-bound (scales with shadow map area) vs vertex/draw-bound
(independent of map size).

## What it adds

### `UNENDLICH_SHADOW_MAP_SIZE` env var

Valid values: `512`, `1024`, `2048` (default).

- **2048** (default): 4.2M depth pixels per cascade. Baseline.
- **1024**: 1.05M pixels — 4× fewer fragments. Tests fragment-bound
  hypothesis. Quality impact: shadow edges visibly softer.
- **512**: 262K pixels — 16× fewer fragments. Aggressive cap. Quality
  impact: shadows visibly blocky, but still functional.

Anything else logs a warning and falls back to default.

The CPU-side texel-snap math reads the same value, so visual stability
holds at any setting (just at the lower resolution).

### Spec: `tests/specs/chug_capture_rd8.unendtest`

The original `chug_capture` runs rd=2 (where shadow is fine in steady
state and chugs are subtle). At rd=8 the chug is overt and the
shadow-size lever is testable.

This is the right spec for the A/B test.

## What it doesn't do

- **No fix yet.** A knob to test a hypothesis. The result determines
  the right fix.
- **No new compute shader work.** No code changes to shadow culling,
  cascade splits, or shadow LOD. Just the framebuffer extent.
- **No automatic adaptation.** The knob is static at engine startup.
  Mid-run shadow-size changes would require recreating the framebuffer.

```bash
cd ~/Code/unendlich-development/unendlich-game

# Migrate.

# Rebuild.
cargo build --release -p unendlich-launcher -p unendlich-analyze

# ─── BASELINE: rd=8 at 2048² shadow (default) ─────────────────
# Should match v0.24.3-upload-pressure rd=8 numbers:
# shadow p50 ≈ 77ms, gpu_spike count ≈ 128.
cargo run --release -p unendlich-launcher -- \
    run tests/specs/chug_capture_rd8.unendtest --version @HEAD

cargo run --release -p unendlich-launcher -- diag
UNENDLICH_EVENTS_PATH=~/.unendlich/latest-events.jsonl \
    cargo run --release -p unendlich-analyze -- gpu_spikes
```

Then run again with **1024²** shadow. Spec `[env]` takes precedence
over command-line env (verified in the previous arc), so edit the
spec:

```bash

```

## What we're looking for

**The hypothesis being tested:** shadow GPU cost scales with depth-buffer
area. If true, halving each side (2048→1024) halves the area-quartered,
so cost should drop by ~4×.

| Run | Expected shadow p50 if hypothesis right |
|---|---|
| 2048² (baseline) | ~77ms |
| 1024² | ~20ms |
| 512² | ~5ms |

**If shadow p50 drops by ~4× from 2048² to 1024²:** fragment-bound.
Lower shadow resolution is a viable lever for rd=8+ play. The next
ship would consider making it adaptive (high res at low rd, low res
at high rd) or making it the default at higher rd.

**If shadow p50 drops only modestly (say 77ms → 60ms):** vertex/draw
bound. Fragment count doesn't dominate; we need to attack vertex
count instead — shadow LOD, better cull, or fewer cascades.

**If shadow p50 doesn't drop at all:** something other than the depth
target is the bottleneck. Pipeline setup? Memory access patterns?
This would be surprising but would point at deeper architectural work.

## Test counts

- 70 + 28 + 581 = **679 fast tests pass** (unchanged).
- Critical: the cascade-fit equivalence test still passes. CPU and GPU
  cascade fits agree at the new shadow_size = 2048.0 baseline (and
  would diverge if the parameter wasn't threaded properly).

## Honest concerns

- **The cascade-fit equivalence test runs at 2048².** Lower sizes
  should be safe because the texel-snap math is parametric — both CPU
  (`light.rs::single_cascade`) and GPU (`cascade_fit.comp`) take the
  shadow size as a parameter / push constant, and I updated both call
  sites to read `self.shadow.extent.width`. But the equivalence test
  itself only runs at 2048; runtime mismatch at 1024 would show as
  shadow shimmering during camera motion. Mention so you can flag.
- **This won't fully fix the rd=8 chug.** If shadow is 4× faster at
  1024², that brings p50 from 77ms to ~20ms. Still over budget. The
  full fix likely requires shadow LOD + cascade splits + maybe
  resolution. This ship is one falsification, not the whole answer.
- **Visual quality drops.** Players using low shadow res will see
  it. Eventually we'd want quality settings; for now it's a diagnostic
  knob.
