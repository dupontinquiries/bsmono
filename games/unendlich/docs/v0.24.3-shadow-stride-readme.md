# v0.24.3-shadow-stride — temporal amortization of the shadow pass

The cull_count diagnostic confirmed the chug mechanism: **shadow's
sun-aligned ortho frustum admits 16× more chunks than the camera's
perspective frustum.** Shadow renders ~40 chunks while main renders
~1-5. Same per-chunk cost, vastly different chunk count.

This ship tests the temporal-amortization approach: render only 1/N
of the chunks each frame, cycle through residue classes over N
frames, and DON'T clear the shadow map between frames so old depth
values persist for un-rerendered chunks.

If the math works (and the diagnostic data says it should), at
stride=4 shadow time drops to ~1/4 because only ~10 chunks render per
frame instead of ~40. At stride=8, ~5 chunks per frame.

This is Step 1 of a larger arc. Step 2 (later) replaces the round-
robin selection with fractal temporal dithering — at high fps the
spatial decorrelation of staleness reads as soft noise, not banding.

## How the temporal-hold works

The cascade fits a sphere around the camera's view-frustum slice.
The cascade matrix is **texel-snapped** so a fixed world point maps
to a fixed shadow texel as the camera moves. This means:

- Frame F renders chunks A, E, I (residue 0 mod 4) into the shadow
  map. Their depth lands in specific texels.
- Frame F+1 renders chunks B, F, J (residue 1 mod 4). A, E, I are
  NOT rendered this frame.
- Frame F+1 uses the **LOAD** render pass — depth values for A, E,
  I (and all other previously-rendered chunks) remain in the shadow
  map at the same texels.
- Texel-snap ensures A's contribution from frame F is still at the
  correct world-space-anchored texel when frame F+1 samples it.

This works **as long as the cascade origin doesn't shift by more
than one texel between frames.** When the camera moves fast enough
to shift the cascade by more than one chunk-width, ALL stored depth
values are at slightly-wrong texel positions — so we force a full
render that frame (CLEAR pass, re-render all chunks).

## What it adds

### `UNENDLICH_SHADOW_CHUNK_STRIDE=N` env var

- Default 1 = render all chunks every frame (no behavior change).
- 2-16 = amortize shadow over N frames.
- Beyond 16 = clamped to default (becomes visually obvious).

### `shadow_stride` event per frame (when stride > 1)

Carries: monotonic frame, stride_setting, effective_stride (1 when
force-full triggered), phase, force_full flag + reasons (warmup,
cascade_shift).

### `unendlich-analyze shadow_stride` subcommand

Summarizes how often stride engaged vs force-full triggered, and
why. Phase distribution should be roughly uniform across 0..N if the
rotation is working.

### Internal Vulkan structure additions

- `ShadowMap::render_pass_load` — LOAD-variant render pass.
- `ShadowMap::framebuffer_load` — paired framebuffer.
- The standard `render_pass` (CLEAR) is used for forced-full frames.
- The shadow pipeline is created against the CLEAR pass but used
  with both, relying on Vulkan's render-pass compatibility rule
  (same attachment count + formats).

### Cull shader extension

`CullPushConstants` extended from 8 to 16 bytes — added `stride` and
`stride_phase`. Main cull always passes (1, 0) = admit all. Shadow
cull passes (N, frame%N).

## Force-full-render triggers

The stride is bypassed (CLEAR + render-everything) when:

1. **First N frames** of the run. Initializes the shadow map before
   stride takes over.
2. **Cascade origin shifted > 1 chunk-width** (32m) since the prior
   frame. Old depth values are now at wrong texels.
3. **stride == 1** (feature disabled).

Eviction-aware forcing is filed for later — the cascade-shift
trigger should cover most cases where stale chunks matter.

## What we're looking for

Three things, in this order:

1. **Does the engine run at all without validation errors?** The
   LOAD render pass with `initial_layout: DEPTH_STENCIL_READ_ONLY_OPTIMAL`
   should compose correctly with the CLEAR pass's `final_layout`,
   but validation layers may catch a subtle mismatch. If you see
   ERROR_DEVICE_LOST or layout-transition warnings, that's where to
   look first.

2. **Does shadow time scale down with stride?**
   - stride=1 baseline: shadow p50 ≈ 77ms (matches prior run).
   - stride=4: shadow p50 ≈ 20ms if the mechanism works.
   - stride=8: shadow p50 ≈ 10ms if it works.

   If shadow time stays at ~77ms regardless of stride, the per-frame
   fixed cost (pipeline state setup, command recording, render-pass
   bring-up) is dominating, not per-chunk vertex/draw cost. That
   would be a surprise after cull_count's clear ratio.

3. **What do the shadows look like?** This is the visual artifact
   question. At stride=4 with normal walking, you might see:
   - Subtle "lag" of shadow edges as objects move (chunks rendered
     N frames ago show their shadows at slightly-wrong positions
     for moving content). The world is mostly static though.
   - Sharp banding at chunk boundaries (chunks at residue 0 render
     this frame, chunks at residue 1 don't — visible at borders).
   - More artifacts during fast motion (cascade-shift triggers
     force-full, but right at the threshold there may be jumps).

   Fly mode WILL trigger lots of cascade-shift force-fulls and
   defeat the temporal amortization. Walk-mode is the more honest
   test.

## What success/failure means for next ship

**If shadow time drops proportionally AND artifacts are tolerable:**
- Ship Step 2 (fractal temporal dither for the residue selection).
- Tune default stride for production use.
- File for later: eviction-aware force-full, finer-grained cascade
  shift detection.

**If shadow time drops proportionally BUT artifacts are bad:**
- The mechanism works; we need better noise patterns.
- Step 2 still applies — fractal dither specifically addresses the
  banding pattern.
- Defer ship-as-default until Step 2 is in.

**If shadow time does NOT drop proportionally:**
- The chug isn't from chunk count alone; there's a fixed per-frame
  cost we haven't identified.
- This temporal arc may be wrong; pivot to tighter cascade or per-
  draw overhead investigation.

## Honest concerns

1. **Validation untested.** I haven't run this on real hardware.
   The render-pass compatibility between the CLEAR-pass-created
   pipeline and the LOAD-pass binding is the most fragile bit.
   Vulkan's compatibility rules should allow this, but Honeykrisp
   has surprised us before (the c.5 bisect with per-layer
   framebuffers). If validation complains, the fix is making the
   pipeline against the LOAD pass — but pipelines are bound by
   `render_pass` at creation, so we'd need a second pipeline.

2. **Force-full on fast motion defeats the technique.** Fly mode is
   exactly the workload where chunks shift > 1 chunk-width per
   frame. The temporal amortization works best when the camera is
   stationary or slow, which is the opposite of when chug matters.
   This is a real limitation; not all rd=8 play is fly-mode but
   building/exploring at speed will still chug.

3. **Round-robin produces banding.** Adjacent chunks in slot order
   likely render in different residues, creating sharp edges in the
   "freshly-rendered vs stale" boundary. Visible at chunk borders.
   Step 2 (fractal dither) fixes this; Step 1 likely shows it.

4. **The wait_cascade_center logic uses `view.position`** as a
   proxy for cascade center. The actual cascade center is the
   camera-frustum-slice centroid, which moves slightly differently
   from camera position depending on camera orientation. This is
   an approximation; real cascade center would need re-deriving
   from the cascade matrix. Should be close enough for the > 1
   chunk-width threshold.

5. **First N frames force CLEAR.** If you set stride=16, the first
   16 frames are full renders. At 25fps that's 640ms of "warmup
   chug" at startup. Visible but tolerable.

6. **Eviction-aware force-full not implemented.** If a chunk gets
   evicted while its depth is still in the shadow map, the depth
   persists until another chunk overwrites those texels. Could
   produce phantom shadows. Filed for later.
