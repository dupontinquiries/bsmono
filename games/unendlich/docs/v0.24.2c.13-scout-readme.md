# v0.24.2c.13-scout — Multiview support probe

Tiny diagnostic ship. Adds a read-only probe for `VK_KHR_multiview`
support so c.17's CSM optimization strategy can be planned with real
data rather than assumption.

## Why this ship exists

The c.12-e baselines confirmed what we already suspected: **shadow is
the dominant GPU cost**, with rare massive tail spikes. At rd=2,
shadow is 58% of GPU mean and has p99 spread of 39× its p50. At rd=8
(historical c.10 data), shadow p50 was ~110ms — actively breaking
playability.

Multiview CSM is the highest-impact candidate fix: a single render
pass writes to all 4 cascade layers simultaneously instead of running
4 separate passes. But it requires `VK_KHR_multiview` (Vulkan 1.1
core, also available as an extension). **We need to know whether
Honeykrisp/Mesa supports it before committing to a multi-week
implementation.**

c.13-scout answers this with a single startup query. No engine
behavior changes — just a probe, a log line, and a structured event.

## What changed

### `unendlich-shared` — new `MultiviewSupport` struct

Captures 5 fields from the Vulkan multiview tables:

```rust
pub struct MultiviewSupport {
    pub multiview: bool,           // is it enabled?
    pub max_view_count: u32,       // need ≥4 for CSM
    pub max_instance_index: u32,   // not relevant for CSM
    pub geometry_shader: bool,     // not relevant for CSM
    pub tessellation_shader: bool, // not relevant for CSM
}
```

Plus a `supports_csm()` helper that returns `true` iff multiview is
enabled AND `max_view_count >= 4`.

### `GpuInfo` extended with `multiview` field

Backward-compatible via `#[serde(default)]` — older result files (c.12-e
and earlier) parse cleanly with `MultiviewSupport::default()` (all-false).

**The `multiview` field is NOT part of `driver_hash`.** This is
intentional: a Mesa update that adds multiview support shouldn't
invalidate cross-version comparisons of the runs before/after, since
the engine's behavior in those runs didn't change. The driver
identity is what it is; multiview is a side-channel capability bit.

A `with_multiview()` builder method lets the engine populate the field:

```rust
GpuInfo::new(vid, did, drv_ver, name, info)
    .with_multiview(probed)
```

### `VulkanContext::multiview_support()` — the probe itself

Queries `PhysicalDeviceMultiviewFeatures` (via `get_physical_device_features2`)
and `PhysicalDeviceMultiviewProperties` (via `get_physical_device_properties2`).
Both are Vulkan 1.1 core and pNext-chainable, so the query path matches
what we already do for driver properties (c.12-b).

Read-only, side-effect-free. Safe to call any time after context
construction.

### Engine startup logs the result

Two ways:

**Human-readable log line:**
```
Multiview: supported (max_views=6, max_instance=32767, geom=false, tess=false) | CSM-capable: true
```
or
```
Multiview: unsupported | CSM-capable: false
```

**Structured event** for the analyzer:
```json
{
  "kind": "multiview_probe",
  "payload": {
    "supported": true,
    "max_view_count": 6,
    "max_instance_index": 32767,
    "geometry_shader": false,
    "tessellation_shader": false,
    "csm_capable": true
  }
}
```

### `compare` shows the capability

When at least one column has multiview info populated, a `csm_capable`
row appears in the comparison table:

```
spec               | rd2_smoke
                   | @c.12-e   | @c.13-scout
-------------------+-----------+-------------
shadow_p50_ms      |    0.667  |    0.665
...
driver_hash        | drv-789…  | drv-789…
csm_capable        | —         | yes
assertions         | PASS      | PASS
```

The `—` is for results that predate the field; `yes`/`no` reflect the
probed capability. The row is omitted entirely when no column has the
info.

This is informational only — capability differences don't trigger
a warning the way driver_hash mismatches do. A capability gain is
expected when comparing across a driver upgrade and shouldn't scare
the user.

## What's NOT in c.13-scout

- **Multiview rendering itself.** Engine still uses the per-cascade-pass
  shadow rendering. That's c.17 work, contingent on this ship's
  diagnostic outcome.
- **Multiview enable in device creation.** We query the feature but
  don't enable it on the logical device. Enabling adds it to the
  pipeline barrier surface — premature until we're ready to use it.

## What this ship reveals

After you run the smoke test on c.13-scout, the log line tells us
the c.17 strategy:

| Probe result | c.17 direction |
|---|---|
| `CSM-capable: true`, max_views ≥ 4 | **Multiview CSM** — single render pass writing all 4 cascade layers. Big architectural lift, large expected win. |
| `CSM-capable: false` OR max_views < 4 | **Per-cascade GPU culling + frustum tightening** — reduce per-cascade workload without changing pass structure. Smaller win, less risky. |

Either way, the c.12-e launcher infrastructure makes the comparison
mechanical: run rd8_smoke before, run rd8_smoke after, compare the
shadow_p50_ms and shadow_p99_ms columns.

## Validation

- `cargo test -p unendlich-shared` — **70 pass** (unchanged)
- `cargo test -p unendlich-launcher` — **28 pass** (was 25; +3 for
  multiview compare tests)
- `cargo test -p unendlich-engine --lib --features render` — **580
  fast pass** (unchanged)
- Engine builds with hot-shaders. Multiview probe doesn't touch the
  hot rendering path.

**Real-hardware validation needed:** the query semantics on
Honeykrisp/Mesa 25.3.6 are what we're scouting. The probe itself
should always succeed (it's just a `get_physical_device_features2`
call). What we're learning is the *answer* to the probe.
