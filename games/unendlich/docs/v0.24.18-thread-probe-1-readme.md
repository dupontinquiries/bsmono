# v0.24.18-thread-probe-1 — per-thread diagnostic probe (ship 1)

First of the chug-investigation tooling arc. Adds a default-off,
opt-in thread state probe + an analysis CLI that produces text
reports from the CSV output.

## What this ship does

Adds two pieces:

**1. `thread_probe` module.** Lets threads register a name and tag
their current activity. A background sampler reads each registered
thread's `/proc/<pid>/task/<tid>/stat` + wchan every 100ms and
writes a CSV row per thread per sample. Engine-side chug detector
flags rows where FPS < 20 OR wait_fences > 50ms.

**2. `probe-report` analysis bin.** Reads the CSV. Prints:
- Overview (duration, fps distribution, chug%)
- Per-thread activity histogram
- Per-thread CPU work in ticks/sec
- Hot deltas (moments where many threads changed state at once)
- Chug periods (contiguous chug spans + per-thread state inside)

Designed to print compactly (~100 lines max) so you can paste
output into a chat without burning context.

## How to use

Enable in your free-play run:

```bash
UNENDLICH_THREAD_PROBE=1 \
UNENDLICH_RENDER_DISTANCE=10 \
UNENDLICH_VSYNC=0 \
UNENDLICH_MAX_UPLOADS_PER_FRAME=32 \
UNENDLICH_UPLOAD_BUDGET_MS=8.0 \
  cargo run --release --features="render,gpu,hot-shaders" \
    -p unendlich-engine --bin unendlich-world
```

On startup you'll see one stderr line:

```
thread_probe: sampling every 100ms to probe-1747325789.csv
```

After you quit, analyze:

```bash
cargo run --release -p unendlich-engine --bin probe-report -- probe-1747325789.csv
```

Or slice to a window of interest:

```bash
# Just the chug-and-magic-switch part, e.g. seconds 30 to 90
cargo run --release -p unendlich-engine --bin probe-report -- \
    probe-1747325789.csv --window 30000:90000
```

Optional: `--thread render` to filter to one thread, `--hot-deltas`
to skip everything but the hot-delta section.

## What you'll see in this ship

The probe currently registers ONE thread: the render thread (which
is also the main thread). So the CSV will have render rows + engine-
state rows. That gets you:

- Render thread's activity distribution (mostly `wait_fence` during
  chug, mixed `wait_fence`/`tick_sim`/`working` in healthy state)
- Per-render-thread CPU work — confirms the magic-switch moment
  where it stops spending most of its time blocked on fences
- Hot-delta detection — should highlight the magic-switch as a
  big change in render thread state coinciding with engine_state
  fields shifting (fps jump, mesh_q draining)

What you WON'T see yet: what the mesh pool workers were doing
during the chug period. That's ship 3 (registering them too).

## Why ship now if mesh-pool tagging is the real prize

Two reasons:
1. **Plumbing checkpoint.** Lets you confirm the probe + analyzer
   work on your hardware before I touch the mesh pool's internals.
   If `/proc/<tid>/stat` parsing or the wchan reads have surprises
   on Asahi, better to find them now.
2. **Containment.** Mesh-pool registration requires edits to
   `meshing_pool.rs`. If those edits regress something, ship 1+2
   stays usable.

Ship 3 (mesh + gen pool registration) follows next session.

## Honest concerns

1. **The chug detector threshold is heuristic.** FPS < 20 OR
   wait_fences > 50ms — both numbers picked from looking at the
   free-play log. Real chug might be more nuanced (e.g. a brief
   p99 spike that doesn't pull avg fps below 20). The analysis
   tool's chug-period output is only as good as the threshold.
   Easy to tune in `engine_state_update` if needed.

2. **wait_fences is zero in engine_state** because the
   per-window aggregate isn't easily accessible from the FPS-log
   site. Chug detector falls back to FPS-only. Filed for a follow-up
   if FPS-only proves insufficient — the renderer's cpu_timer code
   has the value, just needs an accessor.

3. **Per-CPU index in /proc/stat field 38 — I used field 36.**
   The field index after the `(comm)` close-paren on Linux is
   slightly version-dependent (older kernels differ). 36 is correct
   for Linux 6.x; if you're on an older kernel and `last_cpu`
   reads as garbage, that's the cause. Easy fix once we see it.

4. **/proc/<tid>/wchan format varies.** On 6.x it's a symbol name
   like `futex_wait_queue`; on older it might be a hex address.
   The analyzer just reports whatever it reads, so this is more of
   "the output may look different on different hosts."
