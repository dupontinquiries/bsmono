# v0.24.2c.12-c — Asset path fix for workspace layout

Tiny hotfix ship. Restores asset loading after the c.12-a workspace
refactor accidentally broke it.

## The bug (c.12-a regression)

The workspace refactor moved `assets/` into the engine crate
(`crates/unendlich-engine/assets/`). But the engine's runtime code
still loads assets via `std::fs::read("assets/shaders/...")` and
`load_directory("assets/biomes")`, both of which are relative to the
process's current working directory. When the launcher runs
`unendlich-world` from a cloned workspace, cwd is the workspace root
— so the runtime code looks for `<workspace>/assets/shaders/...`,
which didn't exist (assets were in `<workspace>/crates/unendlich-engine/assets/`).

Visible symptoms in c.12-b:

```
Biome registry unavailable: I/O error: path does not exist: assets/biomes
GPU unavailable: Shader file missing: assets/shaders/chunk_generation.comp.spv
panic: hot-shaders: failed to read assets/shaders/chunk.vert.spv from CWD
```

## The fix

Restored `assets/` at the workspace root. Three related changes:

1. **Asset directory moved back to workspace root.** `assets/` lives
   alongside `Cargo.toml`, `commands/`, `crates/`, etc. Runtime code
   that uses `"assets/..."` relative to cwd now works as before.

2. **`include_bytes!` paths in engine source updated.** They use
   relative paths from the source file's directory.
   `crates/unendlich-engine/src/render/foo.rs` reaches the workspace
   root with `../../../../`. Six files updated.

3. **`build.rs` writes SPIR-V to workspace root.** `Path::new("../../assets/shaders")`
   from the engine crate dir resolves to the workspace root's
   `assets/shaders/`.

## Why this approach

Alternatives considered:

- **Resolve assets from the binary's location instead of cwd.**
  Would require threading a "where do I live" path through every
  asset-loading site. Lots of code churn, lots of places to break.

- **Embed all assets via `include_bytes!`.** Right for distribution
  (one self-contained binary), but biomes JSON files would bloat
  the binary considerably and lose hot-reload during development.

- **Keep `assets/` in the engine crate, search multiple candidate
  paths at runtime.** Complex. Different cwd assumptions for
  developer (workspace root) vs. tester (binary's location) makes
  the search order ambiguous.

The chosen approach matches the c.11 layout: `assets/` at the repo
root, runtime code reads relative to cwd. Simplest, least churn,
matches what every code path already expects.

For long-term distribution to testers (c.21+), assets will probably
be embedded into the binary via `include_bytes!` for a fully
portable single-file artifact. That's filed in DESIGN_NOTES.

## Validation

- `cargo test -p unendlich-shared` — 70 pass
- `cargo test -p unendlich-launcher` — 19 pass
- `cargo build -p unendlich-engine --features render --features hot-shaders --bin unendlich-world` — clean
- Engine tests not re-run here (they don't touch asset loading); they
  should still match c.12-b's 580 fast + ~21 slow.

## What c.12-b worked correctly (validated on user's machine)

The c.12-b validation run produced this log line on Asahi M2 Max:

```
GPU info: vendor=0x10005 device=0x0000 driver_version_raw=0x06403006
          name="Honeykrisp" info="Mesa 25.3.6" hash=drv-7892b4dc8cdd660d
```

That's the c.12-b driver-id capture working end-to-end on real
hardware. The launcher resolved `@HEAD`, cloned, built, ran the
binary, and the Vulkan device-properties query returned real values.
This was the half of c.12-b we couldn't test in the dev environment.

The asset-path bug interrupted the run before the spec finished, so
no `.unendresult.json` was written. With this c.12-c fix, the smoke
test should now run to completion.

## Also filed in DESIGN_NOTES

A note about the **tester onboarding experience as a product goal**.
The c.12-b validation revealed how much migration friction exists
even for the project author — testers will hit ten times more.
Captured as a c.21+ aspiration: single-artifact installer that
routes to a user-chosen workspace, downloads + verifies platform
binary, writes a launcher script. Not today's work, but knowing it's
coming should shape c.13 (GUI) and c.16 (distrib) decisions.
