# v0.24.29 / v0.24.30 design memo

Written autonomously during the v0.24.28-bumpy-foundation work
session, pending user review. Captures architectural choices that
should be discussed before implementation.

## v0.24.29: GPU-side output equivalence test

### Motivation

v0.24.28 ships a CPU reference port, but does NOT compare GPU
output against it at runtime. The output-sanity probe only checks
structural invariants (AABB, finite, ratio). The CPU reference
exists purely as a unit-test oracle.

A direct GPU↔CPU output compare would catch any divergence between
the two implementations, including:
- Different `hash2d` results from float precision differences
  (e.g., `fma` vs `mul+add`).
- Different winding order (CW vs CCW) for a face.
- Different per-block color tables.
- Sub-vertex grid mismatches.

### Why mesh equality is non-trivial

The GPU emits vertices in *non-deterministic order* because
`atomicAdd` returns the value before the add — and many threads
race. Two runs of the same GPU mesh, on the same input, produce
the same SET of vertices but in different ORDER. Linear comparison
fails.

### Proposed implementation

A new function `mesh_set_equal(a, b)` that canonicalizes both
meshes into a sorted list of `(quad_corners, color)` tuples:

1. Walk indices in groups of 6 (two triangles per quad). For
   each pair of triangles `(i0,i1,i2)`, `(i0',i2',i3')` sharing
   the first index, extract the four vertex positions as a
   `[Vec3; 4]`.
2. Canonicalize the quad: rotate so the lexicographically
   smallest vertex is first; record color.
3. Sort the resulting `(Quad, Color)` vec.
4. Compare for equality.

Cost: O(n log n) per chunk for both sides. Fine to run as a
gated test on a few sample chunks per session.

### Where to invoke

Gated by `UNENDLICH_OCTREE_MESH_COMPARE=1`. The dispatcher, after
producing GPU output and before returning the MeshResult, calls
the CPU reference on the same chunk and asserts set-equality. On
mismatch, dumps both meshes to disk and logs a WARN with chunk
coord.

### Performance worry

The CPU reference at 20K vertex chunks is ~0.5ms (estimated from
sparse mesher CPU baseline). Running it for every chunk in mode
2 doubles total mesher load. So this gate MUST be off by default.
For visual development it can be on (since perf isn't yet the
focus); for benchmarking it must be off.

A cheaper variant: run CPU reference for only 1 in N chunks.

## v0.24.30: shared OctreeBufferPool between renderer and mesher

### Current state (after v0.24.28)

Two separate octree buffers on GPU:
- **Renderer's `OctreeBufferPool`** (in `chunk_renderer.rs` /
  `octree_buffer_pool.rs`). Span allocator; can hold the full set
  of currently-visible chunks. Verified by the v0.24.26 probe.
- **Mesher's internal octree buffer** (in `gpu_meshing_octree.rs`).
  Fixed-slot (64 slots × 40960 nodes × 40 bytes = 100 MB).
  Uploaded fresh per dispatch batch. NOT verified by the v0.24.26
  probe.

This duplicates octree data on GPU (~200 MB of redundant memory
for the worst case) and creates the unverified-consumer-buffer
class of bug that v0.24.27 spent three sub-ships chasing.

### Constraints

- Renderer's `OctreeBufferPool` allocates octree spans into a
  single large buffer indexed by `chunk_coord -> first_node_index`.
  Span sizes vary by chunk complexity.
- Mesher's compute kernel currently expects fixed-stride slots
  (`slot_idx * MAX_NODES_PER_CHUNK`). It uses `meta.octree_base =
  slot_idx * MAX_NODES_PER_CHUNK` and the GLSL `octree_sample` walks
  from that base.
- Mesher and renderer run concurrently. Renderer reads its octree
  buffer during draw; mesher would also read during dispatch.
  Vulkan barriers needed.

### Architectural sketch

```
build_renderer():
  let octree_pool = Arc::new(Mutex::new(OctreeBufferPool::new(...)));
  let renderer = ChunkRenderer::new(.., octree_pool.clone());
  let mesher = OctreeGpuMesher::new(.., octree_pool.clone());

frame loop:
  // (1) chunk_manager emits "octree changed" events into a chan.
  // (2) octree_pool.lock() and upload changed octrees. Single
  //     copy. Slot index returned per chunk.
  // (3) renderer draws using octree_pool buffer at known slots.
  // (4) mesher dispatches with meta.octree_base = pool_slot_index[c]
  //     * <variable_stride>. Mesher reads from the SAME buffer.
```

### The variable-stride wrinkle

Renderer's `OctreeBufferPool` uses *variable-size* spans (one
chunk takes 12 nodes, another takes 8000). Mesher's GLSL kernel
currently assumes `base = slot_idx * STRIDE` for some fixed stride.
Doesn't translate to variable spans.

Two options:

**Option A** — Use absolute node indices instead of slots. Pass
`meta.octree_node_base` (already a `u32` node index, not a slot
index) directly. The renderer's span allocator returns this. GLSL
unchanged otherwise. *Preferred.*

**Option B** — Keep the mesher's fixed-stride contract. Renderer
reserves fixed-stride aligned space in the pool for "in-flight
mesh requests." More memory, simpler mesher.

Option A is cleaner. It's a small GLSL change (already largely
indexes by absolute node, just need to confirm) plus a Rust
restructure to thread `octree_node_base` through `ChunkMetaGpu`.

### Synchronization

Renderer reads octree during draw call recording (host side: just
records `vkCmdBindIndexBuffer` etc., GPU reads later during
execution).

Mesher's compute dispatch reads octree during its shader execution.

If both happen in the same frame:
- Frame N start: upload all changed octrees to pool.
- Frame N compute pass: mesher dispatches (reads pool).
- Frame N graphics pass: renderer draws (reads pool).
- Need a memory barrier between upload and compute (already exists
  in the mesher's setup), and between compute and draw (also exists
  — the indirect-draw barrier).
- The renderer reads chunk octrees during its OWN compute passes
  (e.g., the probe). That happens before the mesher's dispatch in
  command order, so no conflict.

### Rollout plan

1. v0.24.30-a: minimal sharing — `OctreeGpuMesher` accepts an
   `Arc<OctreeBufferPool>` constructor argument but still uses
   internal buffer as fallback when the pool doesn't have the
   chunk. Verifies the constructor refactor compiles and runs.

2. v0.24.30-b: switch mesher to read pool exclusively. Remove
   internal buffer. Save ~100 MB. Verify with the v0.24.28
   output-sanity probe (CPU↔GPU equivalence) — if mesh output
   matches, the shared buffer didn't introduce a regression.

3. v0.24.30-c: prove the pool's probe now covers the mesher's
   reads. Add explicit doc note that "any reader of `OctreeBufferPool`
   is verified by the v0.24.26 probe."

## v0.24.29 alternative: cross-chunk neighbor lookups

Independent of shared buffer. Currently the mesher uses
"open-boundary" semantics — out-of-chunk neighbors treated as air.
This produces double-emission at chunk seams (each side of the
seam emits a face that should be occluded). Visible as light
z-fighting or doubled normals at chunk borders.

Fix: when sampling a neighbor cell `(x±1, y, z)` that's out of
chunk bounds, sample the NEIGHBORING chunk's octree instead.
Requires the dispatcher to upload not just the current chunk's
octree but also up to 6 neighbor octrees per dispatch.

### Cost analysis

- Memory per dispatch: 6 neighbors × ~40K nodes × 40 bytes =
  9.6 MB per chunk. With 64 chunks per batch: 614 MB. Too much.
- Mitigation: share neighbors between chunks in the same batch.
  At RD=6 there's lots of overlap — a 5x5x5 batch of chunks
  shares many neighbors. With deduplication memory drops to
  somewhere around 1.5x the single-chunk cost.

If v0.24.30 (shared OctreeBufferPool) lands first, this becomes
trivial: the mesher already sees ALL chunks' octrees in the pool.
Just sample any in-bounds world coord, regardless of which chunk
it's in.

### Recommendation

Do v0.24.30 first (shared buffer), THEN v0.24.29 (cross-chunk
neighbors) becomes a simple shader change. Reverses the original
numbering — relabel as v0.24.29 = shared buffer, v0.24.30 =
cross-chunk neighbors.

## Open questions for the morning sync

1. Visual confirmation: did v0.24.28-bumpy-foundation actually
   look right? If `hash2d`'s `x↔z` symmetry produces a visibly
   diagonal-striped pattern, we need a better hash before more
   work on this branch.

2. Is the 4×4 grid the right resolution? Per-chunk vertex inflation
   for an all-grass chunk: 1024 top faces * 25 verts = 25600 verts.
   Comfortable below 65535. 8×8 would be 81 * 1024 = 82944 — over
   the limit. So 4×4 is the maximum without changing
   `VERTEX_CAPACITY`.

3. Should bumpy emission apply only to NEAR LOD chunks (current)
   or also to FAR? Far chunks don't see the bumpiness anyway —
   could save the vertex inflation on far chunks. Easy to gate:
   pass a `enable_bumpy` flag in `ChunkMeta` and the shader skips
   the bumpy branch when false.

   before iterating on Ship B proper (per-block weathering
