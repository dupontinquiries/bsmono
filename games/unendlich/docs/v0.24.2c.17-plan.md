# v0.24.2c.17-plan — Multiview CSM implementation plan

Working doc. Not a ship; this is the roadmap for the c.17-a/b/c/d ships
that actually implement multiview-based cascaded shadow maps.

Written after reading the existing shadow rendering subsystem in
detail. Findings + plan below.

---

## What we know now (post-c.13-scout)

### Hardware/driver

Honeykrisp on Mesa 25.3.6 supports multiview generously:
- `max_views=32` (we need 4)
- `max_instance_index=4294967295` (effectively unbounded)
- `geom=false, tess=false` (irrelevant — we use neither)

c.13-scout confirmed this on real M2 Max hardware. No known
multiview-specific bugs surfaced in Mesa/Asahi search.

### Baseline numbers (c.13-scout rd8_smoke on Honeykrisp)

```
gpu shadow   n=713  mean=91.4ms  p50=94.9ms  p99=217.5ms  ← 64% of GPU
gpu main     n=713  mean=45.7ms  p50=25.4ms  p99=177.3ms  ← 32% of GPU
gpu total    n=713  mean=143.7ms p50=140.5ms p99=317.4ms
```

That's ~7 FPS at rd=8. Shadow is the steady-state bottleneck (not
just a tail problem — p99/p50 is only 2.3×, meaning shadow is
*consistently* bad).

### What today's shadow path actually does

Reading `world_renderer.rs` line 1779-1899 reveals a surprise:

> **The current shadow pass renders only cascade 0.** Not all 4.

The image is a 4-layer array; the cascade math + GPU cascade_fit +
view_compute pipelines run for all 4 cascades; but the actual
shadow render pass binds C0's view-proj as a push constant, begins
one render pass into framebuffer wrapping layer 0, and draws the
visible-chunks list once.

Cascades 1, 2, 3 exist as `view_params` slots in GPU memory but
nothing draws into their corresponding shadow-map layers. The main
fragment shader samples only `shadow_map` (layer 0, single-layer
`sampler2DShadow`).

This is why c.5/c.6 abandoned per-cascade-pass rendering: an attempt
to draw all 4 cascades caused a 2.8× regression on Honeykrisp (per-
framebuffer overhead). The comment on `shadow_map.rs:67` explicitly
flags multiview as the planned path forward.

**c.17 is finishing what c.5 started.** The infrastructure has been
half-built for the right approach since v0.24.2a.

### Existing CSM infrastructure already in place (do not re-build)

1. **4-layer shadow image**: `crates/unendlich-engine/src/render/shadow_map.rs`,
   `array_layers(NUM_CASCADES)` at line 95. ✓
2. **Per-cascade view-proj computation**: `cascade_fit_pipeline.rs` +
   `view_compute_pipeline.rs` both already dispatch 4× per frame (one
   per cascade), populating `view_params[cascade_slots[ci]]` for
   ci = 0..4. See `world_renderer.rs:1279, 1317`. ✓
3. **GPU-side `view_params` buffer**: holds all 4 cascade matrices,
   updated every frame. ✓
4. **`ViewGroup::PRIMARY`** with `cascade_slots[4]` = `[1, 2, 3, 4]`.
   ✓
5. **`cascade_subresource_range(layer)`** helper to build per-layer
   image views (tested). ✓
6. **Multiview capability probed** (c.13-scout). ✓

What's missing is the actual multiview shadow pass and the main
fragment shader's per-cascade sampling.

## The c.17 ship list

Four ships, each individually testable + measurable. Total estimate
~1-2 weeks of focused work.

### c.17-a — Multiview shadow pass, visual parity (main pass)

Goal: shadow rendering switches to multiview. All 4 cascades render
in one pass. Main fragment shader still samples only cascade 0 (so
visual output is identical to today). Validates multiview wiring
works on this driver.

**Changes:**

- **`shadow_map.rs`** — render pass creation:
  - Add `VkRenderPassMultiviewCreateInfo` with
    `viewMasks = [0b1111]` (one subpass, all 4 cascades active).
    `correlationMasks = [0b1111]` (all 4 views can share GPU work).
  - Framebuffer: change `layers(1)` → `layers(4)` (line 208).
  - Image view: change from `TYPE_2D` of layer 0 to `TYPE_2D_ARRAY`
    spanning all 4 layers (or, equivalently, keep single-layer views
    per cascade and don't change the framebuffer attachment). Pick
    one; the latter is closer to today's code.

- **`shadow_pipeline.rs`** — pipeline:
  - Remove the 64-byte push constant range (no longer needed; the
    matrix selection happens in-shader via `gl_ViewIndex`).
  - Add a descriptor set layout entry for the view_params storage
    buffer at binding 1 (vertex stage). Today's set_layout has only
    binding 0 (CameraUbo); we add binding 1 for view_params.

- **`chunk_shadow.vert`** — rewrite:
  ```glsl
  #version 450
  #extension GL_EXT_multiview : require

  layout(location = 0) in vec3 in_position;
  layout(location = 1) in vec3 in_color;

  // Shared CameraUbo (unused but kept for layout compat).
  layout(set = 0, binding = 0) uniform CameraUbo { /* ... */ } ubo;

  // View params: one per cascade. The cascade slots for our ViewGroup
  // are at indices CASCADE_SLOT_BASE..CASCADE_SLOT_BASE+4.
  // (Or pass the base as a small push constant — see "open question" below.)
  struct ViewParams {
      mat4 view_proj;
      // ... other fields the compute pipelines write
  };
  layout(set = 0, binding = 1) readonly buffer ViewParamsBuffer {
      ViewParams view_params[];
  };

  // Push constant: tells us which cascade slot range this view group uses.
  // For PRIMARY this is always 1 (slots 1, 2, 3, 4 = C0, C1, C2, C3).
  layout(push_constant) uniform PC {
      uint cascade_slot_base;
  } pc;

  void main() {
      uint slot = pc.cascade_slot_base + gl_ViewIndex;
      gl_Position = view_params[slot].view_proj * vec4(in_position, 1.0);
      // Force in_color non-dead (existing pattern).
      gl_Position.x += in_color.x * 0.0;
  }
  ```
  Note: `gl_Layer` is set automatically by multiview based on
  `gl_ViewIndex`. We do NOT write it manually.

- **`world_renderer.rs`** shadow recording (lines 1809-1899):
  - Remove the per-cascade-VP push constant (only push the 4-byte
    `cascade_slot_base = 1`).
  - Bind the view_params SSBO to the shadow pipeline's descriptor
    set (add a write_descriptor_set for binding 1).
  - Begin ONE render pass into the layered framebuffer. The driver
    will rasterize each vertex 4 times (once per view) writing to
    layers 0-3 of the depth attachment.
  - Single `cmd_draw_indexed_indirect_count` (or per-chunk fallback)
    inside the pass. The driver replicates internally.

- **Validation:** main fragment shader still samples only layer 0
  (via the existing `shadow_map` view of layer 0). So even though
  layers 1-3 now contain real shadow depth, nothing reads them yet.
  Visual output should be byte-identical to c.13-scout's rd2 and rd8
  smoke runs.

**Expected perf result:** shadow_p50_ms should be roughly the SAME
as today, or somewhat HIGHER, at rd=2 (one render pass with 4×
rasterization vs. one pass with 1× rasterization). At rd=8, where
fragment shading dominates, we expect a NET INCREASE in shadow time
because we're now actually doing 4× the depth fill instead of 1×.

**This is the cost we must accept** to get to a place where the main
fragment shader can actually USE cascades 1-3 (the c.17-c ship). The
win is in c.17-c.

**Risk: pass overhead might dominate.** The c.5/c.6 regression
suggests per-framebuffer overhead is real on Honeykrisp. Multiview
should sidestep this because it's still ONE framebuffer. But we
won't know until we measure.

**Fallback:** introduce `UNENDLICH_MULTIVIEW_SHADOWS` env var
defaulting to `1`. Setting it to `0` keeps the old single-cascade-0
path. Lets us A/B in one binary and gives an escape hatch if the
driver misbehaves.

**Validation:** `rd2_smoke` and `rd8_smoke` both still PASS
(visual parity). The `compare` against `@v0.24.2-c.13-scout` will
show shadow_p50_ms ROUGHLY EQUAL or SOMEWHAT HIGHER. That's
EXPECTED for this ship. The win is in c.17-c.

### c.17-b — Per-cascade GPU culling for the multiview pass

Goal: each cascade culls against ITS OWN frustum, not the main
camera's. Currently cull runs once for the main camera and the
shadow pass re-uses that list. With multiview now drawing all 4
cascades, we want each layer to only have its visible chunks
rasterized.

But — multiview makes per-view culling fundamentally hard, because
ONE vertex stream feeds all 4 views. We can't tell the GPU "skip
this chunk for view 2 but draw it for views 0, 1, 3."

**Two approaches:**

**Approach A: Frustum union.** Cull against the union of all 4
cascade frusta. Draw the chunks visible to at least one cascade.
Some over-draw (vertices that don't contribute to layer 2 still get
rasterized), but no wasted draw calls. **Probably the right starting
point.**

**Approach B: Subgroup view-index masking.** Use shader subgroup
operations to discard fragments per-view. Complex, driver-dependent.
Skip for now.

**Approach C: Per-cascade indirect draws.** Build 4 separate cull
results (one per cascade frustum). Then submit ONE multiview render
pass, but issue 4 cmd_draw_indexed_indirect calls back-to-back —
each with a `viewMask`-restricting trick. This is wrong; multiview
doesn't let us restrict view mask per draw within a subpass.

**c.17-b ships Approach A** (frustum union):
- Cascade_fit already computes each cascade's frustum into
  `view_params[slot].planes[6]`. Use those 6 × 4 = 24 planes to
  build a combined "union frustum" plane set on the CPU (or skip
  CPU and let a new compute shader do it).
- Cull pass tests each chunk AABB against the union. If visible to
  any cascade, include in indirect list. If not, skip.
- This requires a new variant of the cull compute shader OR
  duplicating the existing cull and changing its frustum-test
  function.

**Expected perf result:** Some shadow time reduction at rd=8
(fewer chunks in the indirect draw list). The win depends on what
fraction of chunks are visible to all cascades vs. only to nearby
ones. Probably 10-30% improvement.

**Validation:** visual parity still holds (we're only culling
unconditional non-contributors). `shadow_p50_ms` at rd=8 should drop
modestly. Compare against `@c.17-a`.

### c.17-c — Main fragment shader samples per-cascade

Goal: actually USE cascades 1, 2, 3. This is where the real CSM
quality win lives, AND where the perf story gets interesting.

**Why this is the big win:** today the single shadow cascade covers
the entire ~200m view distance at rd=8. That's why shadow texture
resolution is poor in the foreground (~10cm/texel). With cascades,
C0 covers ~25m at much higher per-texel resolution (~3cm/texel for
the same 2048² map), C1 covers 25-50m, etc. **Foreground shadows
become crisp.**

**The perf opportunity:** once we can drop unused cascades, we can:
- Reduce shadow map size from 2048² to 1024² per cascade. **Quarters
  fill rate per cascade.** With 4× cascades, total stays the same,
  but per-cascade quality is now matched to coverage.
- Tighten each cascade's frustum to its actual range. Today's C0
  frustum is built to cover the full view distance; with 4
  cascades, C0's frustum covers only 25m and fits a much tighter
  light-space box.

**Changes:**

- **`chunk.frag`** — shadow sampler binding:
  - Change `sampler2DShadow shadow_map` → `sampler2DArrayShadow shadow_map`.
  - Add a per-cascade view-proj array as a binding (probably already
    available via view_params SSBO).
  - In the fragment shader, compute which cascade this fragment
    falls into based on view-space depth, transform the fragment
    into THAT cascade's light space, sample.
- **`shadow_map.rs`** — `view` field should be `TYPE_2D_ARRAY` so
  the descriptor binding matches `sampler2DArrayShadow`.
- **`renderer.rs`** / descriptor binding for the main pipeline:
  - Provide the array view as the shadow descriptor target.
- **`chunk_pipeline.rs`** — if any descriptor types need updating.

**Cascade selection logic in chunk.frag** (rough sketch):
```glsl
int select_cascade(float view_z, vec4 cascade_far_distances) {
    // cascade_far_distances.x = C0's far in view-z
    // ...y = C1's far
    // ...
    for (int i = 0; i < 4; ++i) {
        if (view_z < cascade_far_distances[i]) return i;
    }
    return 3; // fall back to furthest
}

vec4 light_pos = view_params[cascade_slot_base + cascade].view_proj
                 * vec4(world_pos, 1.0);
vec3 lp = light_pos.xyz / light_pos.w;
vec2 uv = lp.xy * 0.5 + 0.5;
float shadow = texture(shadow_map, vec4(uv, float(cascade), lp.z));
```

**Expected perf result:** **THIS is where shadow_p50_ms drops
significantly.** Reasoning:
- We can drop shadow_map_size from 2048² to 1024² (4× less fill
  per cascade, 1× total).
- Frustum tightening means C0 doesn't have to cover 200m — it
  covers 25m. Far fewer chunks visible to C0.
- Cascades cover what they need to cover; no wasted depth fill.

Best-case target: **shadow_p50_ms at rd=8 from 95ms → 25-40ms.**
A 2-4× speedup. The variance is because much depends on per-cascade
fill-rate-vs-state-change tradeoff on this specific driver.

**Validation:** visual SHOULD IMPROVE (sharper foreground shadows).
The smoke test's assertion on `shadow_p50_ms` may need updating —
right now `rd2_smoke.unendtest` asserts `shadow_p50_ms < 2.0`. With
sharper shadows on more cascades being filled, even rd=2 might tick
up — likely still under 2ms but worth keeping an eye on.

### c.17-d — Tuning + fallback drop

Goal: explore the tuning space now that the architecture works.
Drop the `UNENDLICH_MULTIVIEW_SHADOWS` fallback once we've run
suite-stable for a few sessions.

**Things to explore:**
1. **Cascade count.** 4 is conventional. With multiview, 3 is one
   `viewMask` change and reduces shadow work by 25%. 5-6 might
   improve foreground quality further if the perf budget allows.
2. **Shadow map size.** 1024² per cascade is a good default. 768²
   or 512² might trade quality for fps in heavy scenes.
3. **Frustum tightening.** The cascade-fit shader currently builds
   "wraps-the-camera-frustum-slice" light-space bounding boxes. For
   the near cascades, we could tighten further by using the actual
   loaded chunk extents.
4. **Drop the fallback env var.** Once we have a few stable runs
   in suite at c.17-c, remove `UNENDLICH_MULTIVIEW_SHADOWS=0` path.

## Open questions (decide during c.17-a)

1. **Push constant vs. uniform for cascade_slot_base.** A 4-byte
   push constant is the simplest. Could be a specialization constant
   if we want zero runtime cost.

2. **Single 2D_ARRAY framebuffer view, or four 2D views?** Either
   should work with multiview. Single 2D_ARRAY view is cleaner.
   I'll start there.

3. **Reuse `view_params` SSBO for shadow vert?** The cascade matrices
   are already there. Just need a new descriptor binding on the
   shadow pipeline. Saves a duplicate buffer.

4. **Cascade index for fragment-shader sampling: per-fragment loop
   or precomputed?** Per-fragment is simpler. Precomputed (e.g., a
   compute pass that writes per-pixel cascade index) is more complex
   but lets us pack cascades tighter. Start per-fragment.

## Risks called out

1. **Driver-specific multiview implementation strategy.** Mesa picks
   between primitive replication (writing gl_Position as an array)
   or instanced rendering (gl_InstanceID multiplied by view count).
   Honeykrisp/Asahi/Mesa likely picks one or the other; either
   should work for our use case, but if there's a bug in the
   chosen path, we'll see it.

2. **Validation layer warnings.** With multiview pipeline state,
   the synchronization gets more nuanced. Specifically: the depth
   image now has 4 layers being written in one pass, and the main
   pass samples from those layers. The render pass subpass
   dependencies need to cover all 4 layers (default behavior
   probably covers this, but watch for layer-specific barrier
   warnings).

3. **Shadow performance regression in c.17-a.** Expected. We're
   doing 4× the depth fill in one pass. This intermediate state is
   accepted because c.17-b + c.17-c recover and surpass it. Don't
   abandon the path if c.17-a regresses by 30-50% — that's the
   plan working.

4. **Indirect draw output reuse.** The current cull pass produces
   ONE indirect draw list keyed to the main camera. The shadow
   pass reuses this. After c.17-a, the shadow pass still reuses
   it (one list, 4 views). After c.17-b, we have a different list
   (frustum-union-culled). Make sure we don't accidentally use the
   main pass's culled list for the shadow pass after c.17-b.

5. **Main fragment shader compile error.** Changing
   `sampler2DShadow` to `sampler2DArrayShadow` is a binding type
   change. The descriptor write must match. If we forget to
   update one side, the shader won't link / the descriptor will
   fail validation.

## What gets measured at each step

Per-ship validation, using the c.12-e launcher infrastructure:

```bash
# Baseline before each ship.
unendlich-launcher run tests/specs/rd8_smoke.unendtest --version @PREVIOUS
# Apply the ship.
unendlich-launcher run tests/specs/rd8_smoke.unendtest --version @THIS
# Compare.
unendlich-launcher compare tests/specs/rd8_smoke.unendtest \
    --versions @PREVIOUS,@THIS
# Drill into the new run.
unendlich-analyze optimize ~/.unendlich/runs/r-<new>/result.unendresult.json
```

Per-ship perf targets:
- **c.17-a**: shadow_p50_ms stays within ±50% of c.13-scout's 95ms
  (gives room for the 4× rasterization cost). Visual parity:
  byte-identical output as today since main frag still reads layer 0.
- **c.17-b**: 10-30% reduction in shadow_p50_ms vs c.17-a.
- **c.17-c**: shadow_p50_ms at rd=8 down to 25-40ms (target 2-4×
  total improvement from c.13-scout baseline). Visual: sharper
  foreground shadows.
- **c.17-d**: incremental tuning gains, fallback dropped.

If c.17-a perf regresses MORE than 50%, pause and investigate
before c.17-b — likely a driver-specific multiview overhead we
need to understand.

## Rollback / abort criteria

We bail on multiview-CSM and pivot to per-cascade culling (without
multiview) if:

1. c.17-a smoke test produces visual artifacts on Honeykrisp that
   suggest a multiview driver bug.
2. c.17-a perf regression is so severe (>3×) that we can't trust
   even the wiring is correct.
3. Validation layer errors that can't be cleanly resolved.

In any of these cases, the fallback env var keeps us shippable on
the c.13-scout-equivalent path, and we re-plan around per-cascade
culling without multiview (smaller but still real win).

## Order of operations (c.17-a workflow)

1. **Add fallback flag and stub.** New env-var flag, but old code
   path unchanged. Smoke test passes (no behavior change).
2. **Refactor shadow_map.rs to support a multiview render pass and
   layered framebuffer.** Render pass is created with multiview
   create info but the old single-pass code still uses it. Smoke
   test passes (the old code's draw still hits layer 0, ignoring
   the additional structures).
3. **Update shadow_pipeline.rs descriptor layout.** Add binding 1
   for view_params. The new descriptor is bound, but the shader
   doesn't read it yet.
4. **Rewrite chunk_shadow.vert.** Now the shader reads from
   view_params[1 + gl_ViewIndex]. With multiview disabled,
   gl_ViewIndex = 0, so the behavior should match the old push
   constant path's slot 1. Smoke test passes.
5. **Switch render pass to use the multiview structure (viewMask =
   0b1111).** Now all 4 cascades render. Smoke test passes if
   visual parity holds (main frag only reads layer 0 still).
6. **Validate on real hardware.** Compare against c.13-scout
   baseline. Expect shadow_p50_ms to stay similar or rise modestly
   at rd=2; rise more at rd=8.

This staging means every intermediate state compiles AND runs AND
passes the smoke test. We never have a broken intermediate.
