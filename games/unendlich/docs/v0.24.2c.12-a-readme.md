# v0.24.2c.12-a — Workspace refactor

First half of the c.12 arc. Mechanical migration of the single
`unendlich` crate into a Cargo workspace with four member crates. No
new behavior, no new features — just a clean foundation for everything
that comes after.

c.12b (the second half) will add the cross-version compare features
that were originally planned for c.12: driver-id capture in result
files, `unendlich-launcher compare`, `unendlich-launcher run-suite`.
Doing the workspace refactor first means those features land in the
right crate (launcher) with the right module boundaries from day one.

## What changed

### Workspace layout

```
unendlich-game/                         ← repo root
├── Cargo.toml                          ← [workspace] manifest
├── commands/                           ← workflow scripts
├── crates/
│   ├── unendlich-shared/               ← spec/result types, run_id, events, ...
│   ├── unendlich-engine/               ← game engine + unendlich-world + dev bins
│   ├── unendlich-launcher/             ← launcher library + CLI binary
│   └── unendlich-analyze/              ← log analysis CLI
├── tests/specs/                        ← canonical .unendtest suite
└── docs/                               ← design notes + per-ship readmes
```

Sibling layout outside the repo (recommended):

```
~/unendlich-development/
├── unendlich-game/         ← this workspace
└── claude-zips/            ← zip archive
```

### Crate boundaries

**`unendlich-shared`** — pure data + light I/O. No engine deps (no
Vulkan, no glfw, no nalgebra). Modules: `test_spec`, `run_id`,
`events`, `run_summary`, `zone_stats`. Anything both the engine and
the launcher need to agree on lives here.

**`unendlich-engine`** — game engine. The renderer, world model, plant
lifecycle, physics, etc. Most binaries live here: `unendlich-world`,
`unendlich-demo`, `unendlich-triangle`, `unendlich-chunk`,
`unendlich-palette`, `unendlich-spin`, `world-bench`, `mesh-bench`,
`winding-check`. Depends on `unendlich-shared` only — pulls heavy
deps (ash, glfw, vk-sys) through optional features.

**`unendlich-launcher`** — launcher library + `unendlich-launcher`
binary. Depends on `unendlich-shared` only — *no* engine deps. The
GUI/TUI crates in c.13/c.14 will depend on this as a library, calling
its API directly (no subprocess to launcher).

**`unendlich-analyze`** — `unendlich-analyze` binary. Self-contained
(just serde_json from cargo). Reads `events.jsonl` files for
retrospective analysis.

### Dependency graph

```
unendlich-engine     unendlich-launcher   unendlich-analyze
       │                    │
       └────────┬───────────┘
                ▼
        unendlich-shared
```

No engine dep in the launcher path — `cargo build -p unendlich-launcher`
builds only what the launcher needs (shared crate, log, std libs).
GUI/TUI consumers can call the launcher's library API without pulling
in any rendering machinery.

### Build commands (no behavior change)

The launcher binary builds the same way as before:

```bash
cargo build --release -p unendlich-launcher
```

The world binary needs render features as before:

```bash
cargo build --release -p unendlich-engine --features render --features hot-shaders --bin unendlich-world
```

The `commands/launcher_smoke.sh` script's existing command still works
because cargo respects `--bin <name>` against the workspace.

## What did NOT change

- Game behavior: the engine produces identical results before and
  after the refactor.
- Test specs: `tests/specs/*.unendtest` is unchanged. They live in the
  workspace root (not inside a crate) because they're consumed by the
  launcher binary at runtime, not at compile time.
- Launcher CLI surface: `unendlich-launcher run ...` works exactly as
  in c.11.
- Result-file schema: unchanged. (c.12b will add `gpu_driver_id` and
  related fields.)
- Test count: ~673 total across crates (65 shared + 7 launcher + 580
  fast engine + ~21 slow engine = matches c.11).

## Why workspace, why now

Path B from the c.11 planning: launcher exposes library API, GUI/TUI
will consume directly (no subprocess). The workspace makes this work
cleanly — GUI crate depends on `unendlich-launcher` as a library,
calls `unendlich_launcher::run()` directly, no IPC overhead.

If we shipped GUI/TUI in a single-crate layout, the heavy GUI deps
(egui, winit, wgpu) would have leaked into every `cargo build` of the
launcher CLI. With the workspace split, `cargo build -p
unendlich-launcher` builds a lean tool — heavy frontend deps land
only in their own crates.

The workspace also unblocks `unendlich-distrib` (c.16) and
`unendlich-tui`/`unendlich-gui` (c.13/c.14) as their own crates
without disturbing the engine or shared layers.

## Migration on the receiving side

If you're extracting this zip over a c.11 working tree:

```bash
cd ~/unendlich-development/unendlich-game
./commands/update_from_claude_zip.sh unendlich-v0.24.2c.12-a.zip
git status        # massive diff: src/ deleted, crates/ added
git diff --stat   # confirm nothing surprising
git add -A && git commit -m "Workspace refactor (c.12a)"
./commands/tag_current_version.sh
./commands/launcher_smoke.sh
```

The first build will be slow (cargo re-resolves the dep graph for the
workspace). Subsequent builds are normal speed.

## Files changed

This is a structural ship — nearly every Rust file moved location.
The interesting top-level changes:

- `Cargo.toml` — now a workspace manifest (was a package manifest).
- `Cargo.lock` — regenerated for the workspace; pinned versions are
  the same.
- `src/` — DELETED at the repo root.
- `crates/` — NEW. Four subdirectories.
- `build.rs` — moved into `crates/unendlich-engine/build.rs`.
- All Rust source files moved into their respective crate
  directories.
- Imports rewritten: `crate::util::*` → `unendlich_shared::*`,
  `unendlich::launcher::*` → `unendlich_launcher::*`,
  `unendlich::*` (in bins) → `unendlich_engine::*`.

## Tests

Tests are spread across the crates now:

```bash
cargo test -p unendlich-shared             # 65 tests
cargo test -p unendlich-launcher           # 7 tests
cargo test -p unendlich-engine --features render --lib  # 580 fast + 21 slow
```

Or all at once:

```bash
cargo test --workspace --features render
```

`launcher_smoke.sh` exercises the launcher end-to-end against the
engine — the closest thing to an integration test we have.

## Path forward

- **c.12b**: cross-version compare features. Adds `gpu_driver_id` to
  shared's result schema, adds `compare` and `run-suite` subcommands
  to the launcher.
- **c.13**: TUI crate (`unendlich-tui`) on ratatui. List runs, show
  latest assertion status, point at snapshots once they exist.
- **c.14**: GUI crate (`unendlich-gui`) on egui. Drag-drop
  `.unendtest` to run, drag-drop `.unendresult.json` to inspect,
  version dropdown.
- **c.15**: Snapshot capture in engine. 1Hz screenshot to
  `~/.unendlich/runs/<uuid>/snapshots/`.
- **c.16**: Distribution stubs (`unendlich-distrib`). ed25519 keygen
  + sign/verify primitives. CLI subcommands as stubs.
- **c.17+**: Real perf work — multiview CSM, shadow culling,
  indirect mesh, adaptive workload. Validated through the launcher's
  cross-version compare.
- **c.18+**: Distrib actual wiring to a dufs-backed HTTPS server,
  cross-build production, tester contribution flow.
