# v0.24.40-greedy-mid

## Tagline

1D greedy meshing at Mid LOD: adjacent same-block cells emit one
wide quad instead of N adjacent ones. 2-10x vertex reduction at
Mid distance. Gated on `stride > 1u` so Near's per-cell AO/bumpy
are unaffected.

## Status

Built autonomously on top of RC5 (v0.24.39-mid-lod). Shader
compiles in head. Not yet built with cargo or run on hardware.
Same opt-in: requires `UNENDLICH_GPU_MESHER=2` AND
`UNENDLICH_GPU_MESHER_MID=1` to be visible.

## Why this matters

At Mid LOD, the shader iterates 16³ = 4096 cells per chunk
(vs Near's 32³ = 32768). Each surface cell emits 1-6 faces; per
typical surface block ~2-3 faces. Without greedy, every cell
emits its own 4-vertex quads even when adjacent cells would
emit visually-identical adjacent quads.

Greedy merges these runs. For a 16-block-long horizontal stone
wall at Mid: instead of 16 separate +Z quads (64 vertices), one
big quad (4 vertices). 16x reduction on that wall.

Realistic per-chunk reduction: 2-10x depending on terrain. Most
significant on plateaus, deep cliff faces, and underground
ceilings.

## How it works

For each face direction, we pick a **run-axis**:
- ±X faces (normal along X): run along Y
- ±Y faces (normal along Y): run along X
- ±Z faces (normal along Z): run along X

Each cell asks: "am I a run-start?"
- Look at the previous cell on the run-axis.
- If it has the same block_id AND its face-direction neighbor is
  also non-solid (meaning it would also emit this face), then
  prev is part of (or starts) a run that extends through me.
  **I skip.**
- Else, I'm the start. **I sweep forward** along the run-axis
  to find the run extent, emit one quad covering all matching
  consecutive cells.

This is **1D greedy** — only merges along one axis per face
direction. 2D greedy (also merging perpendicular runs into
rectangles) requires sequential processing within a slice, which
doesn't parallelize cleanly on GPU. Filed as a follow-up.

## Gated to stride > 1

At Near LOD (stride == 1), `greedy_run_for_face` returns `stride`
(= 1) immediately. Every cell emits its own quad. Per-vertex AO,
bumpy top, and per-position tint all work identically to
v0.24.38.

At Mid (stride == 2), the per-cell features are already disabled
in RC5 — so greedy at Mid composes cleanly:
- No per-vertex AO to lose.
- No bumpy sub-grid to subdivide.
- Per-position tint now also gated on stride == 1 (was applied
  unconditionally before).

## Performance expectations

Per chunk at Mid:
- Cell count: 4096 (already 8x fewer than Near).
- Greedy: only run-starts do work. Non-starts return early
  after a single previous-cell check.
- Per run-start: scan walk up to 32/stride = 16 steps.
- Total per-cell work amortized: still O(1) since each cell is
  a run-start at most once per direction.

Vertex output: 2-10x fewer at Mid. Faster GPU readback + smaller
mesh upload to the renderer.

## Sampling considerations

The "prev cell would also emit this face" check uses
`sample_or_neighbor` for the face-side cell. At chunk boundaries
this samples the neighbor chunk's octree (v0.24.30 cross-chunk).
If the neighbor isn't resident, treats as air → would-emit = true.
This means at a chunk boundary, a cell might incorrectly think
prev is part of the run when it isn't (because prev's face is
actually occluded by a missing neighbor we don't know about).

Worst case visual: at chunk boundaries, an "unstarted" cell
might fail to emit a face that should be visible. Acceptable
artifact — same chunks would be in pool via the v0.24.32
prewarm anyway.

## What's still deferred

- **2D greedy at Mid** (merge runs perpendicular to the first
  axis too). Cleaner result, harder to parallelize. Filed.
- **Greedy at Near**. Requires per-vertex AO that scales with
  merged quads + bumpy sub-grid that subdivides bigger faces.
  Significant rework. Filed.
- **Per-direction axis tuning**. Right now ±X uses Y, others use
  X. Could choose based on terrain shape (e.g., +Y faces could
  use Z if Z-runs are longer in this chunk).
- **Far / VeryFar greedy**. Will work automatically once those
  LODs are routed through GPU (same gating: stride > 1 enables
  greedy).

## Failure modes

- **Crack between runs**: if the run-start check fails to
  recognize that prev is in a different run (e.g., different
  block_id), it might either skip when it shouldn't (visible
  hole) or emit when it shouldn't (z-fight with the actual
  run-start's quad). Visual symptom: missing or doubled quads
  at column transitions.
- **Run extends across air gap**: if `find_greedy_run` doesn't
  properly stop when next cell has different block_id, it would
  emit a quad spanning the air gap. Visual: floating quads.
  Both helpers explicitly check `next_block != self_block`;
  this would be a logic bug in those functions.
- **Wrong corner positions on bumpy**: at Near with bumpy
  weatherable + greedy disabled, the dy values still apply.
  At Mid with greedy active, dy values are all 0 (side_top_bumpy
  is false). Independent paths so they shouldn't interfere.
  If you see Y-corner misalignment at chunk corners, check the
  dy values being applied.

## Rollback

Shader-only. To revert:
- Replace each face emit's `greedy_run_for_face` branch with the
  v0.24.39 form (per-cell emit, run=stride, run_extent ignored).
- Remove the four new helper functions (`offset_by_face`,
  `offset_by_axis`, `find_greedy_run`, `greedy_run_for_face`)
  and the FACE_*/AXIS_* constants.
- Restore `tint_for_position` application to always run.
- Restore c*** corner adjustments by `bumpy_height(c***.x, c***.z)`
  in the side_top_bumpy block.
- Rebuild SPV.

## How to verify on hardware

```bash
UNENDLICH_GPU_MESHER=2 \
UNENDLICH_GPU_MESHER_MID=1 \
  cargo run --release --bin unendlich-world --features render
```

What to look for:
- Mid LOD chunks render correctly (terrain visible, no holes).
- Surface vertex count noticeably lower at Mid distance vs RC5.
- No z-fighting between adjacent runs.
- Near LOD (close-up) unchanged from RC4.
- Chunk boundaries at Mid: should still be invisible (cross-chunk
  v0.24.30 still works, octree neighbor sampling unchanged).
