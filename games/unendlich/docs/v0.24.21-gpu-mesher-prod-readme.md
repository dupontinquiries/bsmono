# v0.24.21-gpu-mesher-prod — wire `gpu_meshing_sparse` into production

The "Layer A.3" wiring that's been pending since v0.24.6. The
GPU sparse-mesher infrastructure has been sitting dormant behind
`gpu-mesh-bench`, used only for kernel correctness validation.
This ship plugs it into the production meshing pool so live
gameplay routes Near-LOD chunks through GPU compute instead of
CPU greedy meshing.

## TL;DR

- **New env var: `UNENDLICH_GPU_MESHER=1`** (default 0, off).
- When enabled: workers do `extract_surface` (cheap CPU scan)
  and forward Near-LOD chunks to a dedicated GPU dispatcher
  thread that batches up to 64 chunks per `vkQueueSubmit`.
- Mid/Far/VeryFar tiers continue on CPU (their per-chunk vertex
  counts don't amortize a GPU submission).
- Backward-compatible. With the env unset, behaviour is identical
  to v0.24.20.

## Architecture

```
                    (existing)
  chunk_manager ──submit──▶ MeshingPool ──┐
                                          │
                                          ▼
                                ┌───── workers ─────┐
                                │ (4 threads)       │
                                │ extract_surface() │     for Near LOD
                                │  records ────────────────────┐
                                │                              │
                                │  CPU greedy mesh   ← fallback│ + Mid/Far/VeryFar
                                └─────────┬─────────┘          │
                                          │                    │
                                          │                    ▼
                                          │       ┌─ GPU dispatcher ─┐
                                          │       │ (1 thread)       │
                                          │       │ coalesce N or 8ms│
                                          │       │ ↓                │
                                          │       │ mesh_chunks_batch│
                                          │       │ → SparseGpuMesher│
                                          │       └─────────┬────────┘
                                          ▼                 │
                                       res_tx ◀─────────────┘
                                          │
                                          ▼
                                     render thread
                                     drain_up_to(N)
                                     upload_prebuilt_mesh_at_lod
```

The dispatcher exists because `SparseGpuMesher` is non-trivially
stateful (persistent-mapped buffers, single command buffer, internal
mutex). Single-threading GPU work through a coalescer is the simplest
way to realize the kernel's intended amortization: one `vkQueueSubmit`
per N chunks instead of one per chunk.

**Batching parameters**:
- Target: `effective_batch_size()` = 64 by default (cap at
  `MAX_BATCH_CHUNKS=64`; `UNENDLICH_GPU_MESH_BATCH` overrides).
- Timeout: `GPU_BATCH_TIMEOUT = 8ms` after the first request.

Worst-case latency for any individual chunk waiting for batchmates
is 8ms — half a frame at 60 FPS. Under high streaming pressure
(chunks arriving faster than 8ms apart) batches fill before the
timeout and dispatch fires immediately on hit.

## How to A/B vs v0.24.20

```bash
# v0.24.20 behaviour (CPU only)
UNENDLICH_GPU_MESHER=0 \
UNENDLICH_RENDER_DISTANCE=10 \
UNENDLICH_VSYNC=0 \

    -p unendlich-engine --bin unendlich-world

# v0.24.21 GPU path
UNENDLICH_GPU_MESHER=1 \
UNENDLICH_RENDER_DISTANCE=10 \
UNENDLICH_VSYNC=0 \
  cargo run --release --features="render,gpu,hot-shaders" \
    -p unendlich-engine --bin unendlich-world
```

Compare the Mesher timer summary at shutdown:

```

```

CPU baseline from your last v0.24.20 RD=10 run:
`near n=11982 mean=4.46ms p50=1.75ms p90=13.97ms p99=24.96ms`.

GPU path expectation from the v0.24.6 bench data:
- Batch=1 (steady drip): per-chunk ~700µs–1ms — slightly faster
  than CPU greedy.
- Batch=16+ (chunk-stream-in): per-chunk amortized to ~50–80µs —

The Mesher timer attributes the batch's wall-clock cost evenly
across its members, so you'll read per-chunk amortized cost
directly.

## What this does NOT change

- **Render thread cost.** The GPU mesher is upstream of the
  renderer. Your latest probe data showed render-thread `working`
  at 85.6% and `wait_fence` at 11.6%, with `record p50 = 1.57ms`
  rock-steady. None of those numbers should move materially.
- **Shadow pass cost.** The dominant GPU draw cost is
  unchanged. `UNENDLICH_SHADOW_CHUNK_STRIDE=8` is still the
  highest-value flag for the GPU-bound part of the frame.
- **Upload bandwidth.** v0.24.20's vertex pack already cut this
  3×. The GPU mesher's output still flows through the renderer's
  existing packed-upload path; no change to bytes-on-the-wire per
  chunk.
- **Mid/Far/VeryFar mesher times.** Those stay on CPU. The
  downsample/virtual paths produce sub-millisecond meshes already
  and don't benefit from GPU compute at their record counts.

## What WILL change visibly

**Climate-tinted lighting on Near-LOD chunks is NOT applied when
GPU meshing is on.** The current `mesh_chunk_sparse.comp` kernel
produces flat per-block color; it doesn't consume the sky uniform,
the world-model field, or the tick-progress that
`mesh_chunk_with_sky_model_and_tick` uses to bake climate-driven
brightness and tint into vertex colors.

Practical effect: Near-LOD chunks will look slightly more uniform
(fewer face-by-face brightness variations from sun angle, less
climate-driven hue shift). The colors are still per-block from
the palette — chunks remain visually distinguishable — but the
"painterly" detail the CPU mesher contributes is absent.

This is a known v0.24.21 limitation, NOT a bug. The fix is a
later ship that extends the kernel to consume the climate state
as a buffer input. For testing the GPU mesher's correctness and
throughput, the simpler kernel suffices.

If you want full climate-tinted Near LOD, leave `UNENDLICH_GPU_MESHER`
unset and run with the CPU mesher.

## Cross-thread Vulkan submit safety

`SparseGpuMesher` submits compute work to the same queue the
renderer uses for graphics work (Honeykrisp/M2 has a single
graphics-and-compute queue family). Vulkan requires external
synchronization on `vkQueueSubmit` calls to the same `VkQueue`
handle.

This ship adds:
- `VulkanContext::queue_submit_lock: Arc<Mutex<()>>`.
- The renderer's main-frame `queue_submit` acquires this lock
  briefly, releases before fence-wait/present.
- `SparseGpuMesher`'s submits (both records and runs kernels)
  acquire the same lock briefly.

The lock is held only across the `vkQueueSubmit` call itself —
typically tens of microseconds. Fence waits, readbacks, and
record-build happen outside the lock so neither thread blocks
the other beyond the submit instant. This should be invisible in
the per-frame budget.

If your build target has a dedicated compute queue family (i.e.
`compute_queue_is_distinct` is true), a later ship can route the
mesher to `compute_queue` and skip the lock for compute submits
entirely. Honeykrisp on M2 doesn't have this — single family —
so the lock applies.

## Worst-case behavior

- **Per-chunk overflow** (>16K surface records in a chunk): the
  worker pre-screens and falls back to the CPU greedy mesher for
  that one chunk. Logs a warning. In practice this never triggers
  for 32³ chunks — surface cells are bounded by ~6K per chunk
  even in dense terrain.
- **Per-batch GPU error** (e.g. device lost): the dispatcher
  logs an error and sends back empty meshes for the batch. The
  renderer treats these as "chunk yielded no geometry" — no
  upload, no crash. The chunk-streaming layer's re-request logic
  picks them up again on the next refresh wave.
- **Output overflow** (vertex/index buffer for one slot
  overflows the kernel's per-chunk capacity): per-chunk failure,
  logged warning, empty mesh for that chunk only. Other batch
  members are unaffected.

## Drop ordering

The pool's GPU dispatcher thread holds an `Arc<SparseGpuMesher>`
clone. The mesher's Drop uses `device.destroy_*(...)` which needs
`ctx.device` alive. So shutdown order matters:

1. `renderer.destroy(&ctx)` — frees renderer's Vulkan resources.
2. `drop(mesh_pool)` — joins workers and dispatcher; the
   dispatcher's Arc clone is released on its exit.
3. `drop(_gpu_mesher_for_cleanup)` — last Arc clone dies,
   mesher's Drop runs against the live device.
4. `drop(ctx)` — device + instance teardown.

The explicit-drop block at end of `unendlich_world.rs` was
reordered to enforce this. For builds without `UNENDLICH_GPU_MESHER`,
`_gpu_mesher_for_cleanup` is `None` and the drop is a no-op —
no regression for the default CPU-only path.

## What comes next

In rough priority order:

1. **Climate-tinted lighting in the GPU kernel.** Pass sky
   uniform, world-model field samples, and tick-progress as
   buffer inputs. Restores Near-LOD visual fidelity, removes
   the v0.24.21 caveat.
2. **GPU-direct mesh-pool writes.** Currently the mesher reads
   back to CPU `Vec<Vertex>` then the renderer's `upload_mesh`
   writes packed bytes to the pool. The next step is having
   the kernel write packed `PackedVertex` directly into the
   mesh-pool's vertex buffer at a compute-time-allocated offset.
   Eliminates the readback + re-upload round trip.
3. **GPU surface extraction.** Move `extract_surface` from
   CPU workers to a pre-pass on GPU. Chunks then never touch
   CPU memory after generation (they already generate on GPU
   when the GPU generator is enabled). This is the
   "chunks live on the GPU" milestone.
4. **Sparse octree edits.** With GPU-resident chunks, the
   player-edit overlay (`Chunk::explicit_indices`) becomes a
   sparse GPU buffer keyed by chunk slot. Edits are
   coordinate-write into the overlay, never re-mesh the whole
   chunk.

Each step is incrementally useful — you can stop at any of
them with a working system.
