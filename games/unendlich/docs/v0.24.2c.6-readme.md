# v0.24.2c.6 — Shadow regression fixed; CSM rendering paused

This ship is the resolution of the v0.24.2c shadow regression. The c.5 bisect playtest gave me the data I needed.

## What the bisect found

Three 15-second runs at RD=8, all other env vars identical:

| run | CASCADES | LEGACY_FB | shadow p50 | shadow p99 | total p50 |
|---|---|---|---|---|---|
| 1 | 1 | 0 | 70.68ms | 220.49ms | 109.96ms |
| 2 | 4 | 0 | 217.19ms | 526.98ms | 271.13ms |
| 3 | 1 | 1 | **25.42ms** | 207.10ms | **75.06ms** |

Run 3 is dramatically faster. The legacy framebuffer (the single one created at startup, wrapping `view`) is 2.8× faster than the per-layer framebuffer I added in c.2, *for the same render workload*. Switching cascade count from 1 to 4 with the new framebuffers scales perf roughly linearly (217ms ≈ 70ms × 3 + base), showing the per-cascade cost is what we're paying — not a synergy bug.

Both framebuffers wrap functionally identical views of the same image subresource. They produce different `VkImageView` and `VkFramebuffer` handles. **Honeykrisp's perf is sensitive to that handle identity.** Why exactly isn't known — likely some tile-binner state or per-framebuffer driver cache that the legacy path benefits from. Filed for driver investigation.

## What this ship does

- **Reverts shadow rendering to a single render pass into the legacy `framebuffer`**, just like v0.24.2b. Cascade 0's view-projection is computed CPU-side (with the GPU also computing it via cascade_fit + view_compute, but the GPU result isn't read by anything yet — kept as infrastructure for future multiview work).
- **Removes the bisect knobs** `UNENDLICH_SHADOW_CASCADES` and `UNENDLICH_SHADOW_LEGACY_FB`. Their job is done.
- **Removes the dead `layer_views` and `layer_framebuffers` arrays** from the `ShadowMap` struct. Not needed for the single-cascade path; multiview won't need them either (it uses one 2D_ARRAY view).
- **Keeps**: shadow image with 4 array layers (memory pre-allocated for future cascades), per-cascade CPU `cascades[0..4]` computation, GPU cascade_fit + view_compute populating all 4 ViewParam slots, push-constant route in the shadow vertex shader. These are infrastructure-ready for the multiview-based CSM that's the planned path forward.

## What this ship does NOT do

- **No CSM**. The renderer only writes to one shadow cascade. Distant shadows still degrade at the C0 split boundary (~200m by default). The CSM visual win is deferred until multiview lands.
- **Doesn't explain the Honeykrisp framebuffer-perf issue**. We worked around it. Filed for investigation when we have more time.
- **Doesn't fix `UNENDLICH_INDIRECT=0` being 30-150× faster than indirect at large render distances**. That's the older barrier-cost hypothesis from the session-before-bisect; the bisect confirmed it's actually framebuffer-creation cost, but the indirect path's `record_cull_pass` still has overhead even with this fix. Less urgent now that the dominant cost is gone.

## Path forward for CSM

When we resume CSM work, the plausible architectures are:

1. **Multiview** (`VK_KHR_multiview`): single render pass, single framebuffer with a 2D_ARRAY view, fragment shader sees `gl_ViewIndex` to know which layer it's rendering. Each draw call rasterizes to all layers in one go. Bypasses the per-framebuffer-handle issue entirely. Standard for CSM and VR on tile renderers.

2. **One image per cascade** (4 separate VkImage objects with their own VkFramebuffers): more memory bandwidth but each framebuffer is "first-class" the way Honeykrisp seems to prefer. Memory cost: 4× shadow image. We'd want to drop SHADOW_MAP_SIZE to 1024 to compensate.

3. **Bisect-step our way to understanding the per-layer-fb cost**: rebuild and try more configurations (e.g. flipping view creation order, using identical view-handles via VkImageView aliasing, etc.) to localize what specifically Honeykrisp dislikes. Useful if the answer turns out to be cheap (e.g. a specific flag in CreateInfo).

I'd start with (1) — multiview is the standard answer for this exact use case, and our infrastructure (per-cascade GPU view-params, push-constant shader path) is already shaped for it.
