# v0.24.3-upload-pressure — test the upload-contention hypothesis

After multi-queue-a confirmed Honeykrisp exposes only one queue
(closing the multi-queue path), we read the render loop end-to-end
and found:

1. **`MAX_FRAMES_IN_FLIGHT = 1`.** Single-frame-in-flight. When the GPU
   spikes, the CPU waits the full GPU spike duration — no pipeline
   buffer. The chug magnitude IS the GPU spike magnitude.
2. **The GPU mesher (`gpu_mesher_vk.rs`) is not wired in.** Meshing
   runs on CPU worker threads via `meshing_pool.rs`, already async,
   already version-stamped.
3. **Mesh upload is a CPU memcpy** into `HOST_VISIBLE | HOST_COHERENT`
   persistently-mapped GPU memory. No staging, no `cmd_copy_buffer`.
4. **Both shadow + main render passes read from the same pool buffer.**

The revised chug hypothesis: **the CPU's memcpy into HOST_COHERENT
mapped memory triggers cache-coherency cost the GPU pays on its next
read of the same buffer.** Both shadow and main draws read the same
pool, so the cost shows up as correlated spikes — matching the
observed shadow+main-spike-together pattern from chug-debug-2.

This ship tests that hypothesis directly.

## What it adds

### 1. `UNENDLICH_UPLOAD_BYTES_BUDGET` env var

New per-frame budget in BYTES (not just ms). Both the existing
`UPLOAD_BUDGET_MS` and this new bytes-budget gate the upload loop —
whichever fires first wins.

Default: 8 MB. Observed peak in chug-debug-2/multi-queue-a was ~30+
MB/sec during chug windows; 8 MB per frame caps well under that.

To test the hypothesis, run with various budgets:
```bash
UNENDLICH_UPLOAD_BYTES_BUDGET=8388608   # 8 MB (default)
UNENDLICH_UPLOAD_BYTES_BUDGET=2097152   # 2 MB (aggressive cap)
UNENDLICH_UPLOAD_BYTES_BUDGET=33554432  # 32 MB (effectively disabled)
```

### 2. `upload_pressure` event

Emitted when per-frame upload bytes >= 2 MB. Fields:
- `frame`: monotonic wall-clock frame counter.
- `upload_bytes`: bytes memcpy'd this frame.
- `upload_chunks`: chunk count.
- `upload_ms`: elapsed time.

### 3. `unendlich-analyze upload_pressure` subcommand

Summarizes the events: distribution of bytes/chunks/ms, top 10
high-upload frames, and **cross-references against gpu_spike and
wait_fences_spike event counts** to test the hypothesis.

If `upload_pressure` events have comparable count to `gpu_spike`
events (ratio 0.5-2x), upload pressure plausibly co-occurs with
chugs. Confirming requires looking at chronological clustering in
events.jsonl, but count-similarity is a strong first signal.

## What this ship does NOT do

- **No fix yet.** Diagnostic + budget knob only.
- **No GPU mesher wire-up.** That's the strategic next move once we
  confirm the chug source.
- **No descriptor / pipeline changes.** Single, focused diagnostic
  surface.

```bash
# Then run with AGGRESSIVE upload cap — 2 MB.

UNENDLICH_UPLOAD_BYTES_BUDGET=2097152 \
    cargo run --release -p unendlich-launcher -- \

UNENDLICH_EVENTS_PATH=~/.unendlich/latest-events.jsonl \

UNENDLICH_EVENTS_PATH=~/.unendlich/latest-events.jsonl \
    cargo run --release -p unendlich-analyze -- gpu_spikes
```

## What we're looking for

**Baseline run (default 8 MB budget):**
- `upload_pressure` event count vs `gpu_spike` event count.
- If ratios are similar (~0.5-2x), strong hypothesis support.
- If `upload_pressure` events are much fewer than gpu_spikes, the
  threshold needs lowering OR upload pressure isn't the cause.

**Aggressive cap run (2 MB budget):**
- Compare `wait_spikes` / `gpu_spikes` counts to baseline.
- If reduced by 30%+, hypothesis confirmed; we have a fix lever.
- If unchanged, hypothesis falsified; chug source is elsewhere.

The aggressive cap will make terrain load slower (fewer chunks per
frame uploaded), so it's a tradeoff if it works. The point right now
is diagnosis, not the production setting.

## What success looks like

If hypothesis confirmed: next ship is **tune the production default**
to find the sweet spot between chug reduction and terrain-load speed.
After that, wire up the GPU mesher to eliminate uploads entirely —
that's the strategic destination.

If hypothesis falsified: we look elsewhere. The chug-debug instrumentation
stays; the bytes-budget knob is still useful for terrain-load tuning.
Next exploration likely targets the per-frame command-buffer recording
costs or driver-side state-change overhead.

## Honest concerns

- **The hypothesis might be wrong.** I've changed my mental model
  three times this arc. Even with end-to-end code read, I could be
  missing something. The aggressive-cap test is designed to falsify
  cleanly: if it doesn't reduce chugs, we move on.
- **Even if confirmed, the fix isn't "lower budget forever."** Lower
  budget = slower terrain load. The real fix is wiring up the GPU
  mesher (no more uploads) or moving to staging buffers. This ship
  is diagnostic, not solution.
- **`MAX_FRAMES_IN_FLIGHT=1` is a separate lever** worth knowing
  exists. Going to FIF=2 would hide upload pressure behind GPU work
  at the cost of +1 frame latency. Not advocating; just noting.
