# v0.24.2c.13-instrumentation — Warmup, world snapshots, shadow buckets

Instrumentation ship. Three new diagnostic capabilities for c.17 perf
work. No engine behavior change for production runs.

## What's new

### 1. Warmup window — `[engine] warmup_ms` in specs

**The problem:** the first few seconds of every run are chunk-gen-heavy,
pipeline-cache-cold, mouse-uncaptured warmup. Those samples pollute
assertion-relevant percentiles (your c.13-scout rd8 baseline shadow
p50=95ms is partly the warmup curve, not steady state).

**The fix:** specs can now set `warmup_ms` to delay the start of the
measurement window:

```toml
spec_version = 1
name = "rd8_smoke"

[engine]
duration_ms = 8000   # total run length
warmup_ms = 3000     # ignore first 3 seconds
```

At t=3000ms, the engine:
- Logs `Warmup complete after 3000ms — resetting timer stats. World state: loaded_chunks=N non_air_blocks=M`
- Resets GPU and CPU timer LIFETIME accumulators (the per-second
  window is untouched — it rolls naturally).
- Emits a structured `warmup_complete` event.
- Captures the start workload snapshot.

The result file's `shadow_p50_ms`, `shadow_p99_ms`, etc. now reflect
only the steady-state window — much more comparable across runs.

For runs without `warmup_ms`, behavior is unchanged. The boot-mode
events (first 3 seconds, tagged `mode: "boot"`) still apply and are
still excluded from triage classification.

### 2. World-state snapshots in result files

Every spec run now captures world-state snapshots at:
- **Start** of measurement (warmup_complete OR boot-end, whichever
  comes first).
- **End** of run (just before shutdown).
- Plus a **delta** for convenience.

Format in `stats.workload.snapshot`:

```json
{
    "stats": {
        "workload": {
            "loaded":    {...},
            "rendering": {...},
            "snapshot": {
                "start": {"loaded_chunks": 33, "non_air_blocks": 845620},
                "end":   {"loaded_chunks": 34, "non_air_blocks": 867430},
                "delta": {"loaded_chunks": 1, "non_air_blocks": 21810}
            }
        }
    }
}
```

Plus flat sugar keys for assertions:
- `workload_chunks_delta`
- `workload_blocks_delta`

You can now assert that the world didn't churn during measurement:

```toml
[expect]
workload_blocks_delta = { max = 1000 }
```

**Cost:** ~1ms per snapshot (iterates every block in every loaded
chunk). Cheap.

**Today's snapshot is intentionally thin:** just `loaded_chunks` and
`non_air_blocks`. Plant count, creature count, weather state, etc.
will be added opportunistically when working in those subsystems —
not as their own ship. Filed in DESIGN_NOTES.

### 3. Shadow bucket timing — `UNENDLICH_SHADOW_BUCKETS=N`

**The problem:** the existing `gpu shadow` zone aggregates the entire
shadow pass into one number. We can't tell if shadow cost is
front-loaded (warmup), back-loaded (last chunks expensive), or
uniformly distributed.

**The fix:** opt-in diagnostic mode. Set `UNENDLICH_SHADOW_BUCKETS=N`
(typically 4 or 8), and:

1. The shadow pass switches to the per-chunk fallback path
   (overriding `UNENDLICH_INDIRECT`).
2. The visible-chunk list is divided into N quarters.
3. After each quarter, a GPU timestamp is written.
4. Per-frame, a structured `shadow_buckets_timing` event records
   `us_per_bucket: [...]` — microseconds per bucket.
5. A companion `shadow_buckets_record` event records
   `chunks_per_bucket` (how the chunk list was partitioned).

A run with `UNENDLICH_SHADOW_BUCKETS=4` produces events like:
```json
{"kind": "shadow_buckets_record",
 "payload": {"frame": 100, "visible_chunks": 24, "bucket_count": 4, "chunks_per_bucket": 6}}
{"kind": "shadow_buckets_timing",
 "payload": {"frame_idx": 100, "us_per_bucket": [18200, 18950, 19100, 18430], "total_us": 74680}}
```

**Interpretation:**
- Roughly equal per-bucket microseconds → workload is uniform.
  Optimization should focus on per-chunk cost reduction.
- Front-loaded (first bucket dominant) → pipeline/state setup is
  expensive on the first draw. Multiview should help.
- Back-loaded (last bucket dominant) → later chunks are bigger or
  there's growing state. Look at chunk size distribution.

**Limitations:**
- This is diagnostic-only. The per-chunk fallback path is slower
  than indirect drawing.
- The bucket timer uses a separate small query pool, so it doesn't
  perturb the main `gpu shadow` zone's accumulator.
- Reading `events.jsonl` is currently required to see bucket data —
  `unendlich-analyze` doesn't yet aggregate bucket events into the
  optimize output. Filed for c.13-instrumentation-followup if needed.

### 4. `unendlich-analyze optimize` surfaces workload context

The `optimize` subcommand now reads workload info from the result
file and prints it BEFORE the ranked tables:

```
Workload context
────────────────
  loaded chunks      min=32 p50=33 max=34 (n=5 samples)
  rendering chunks   min=18 p50=24 max=24 (n=5 samples)
  start state         loaded_chunks=33 non_air_blocks=845620
  end state           loaded_chunks=34 non_air_blocks=867430
  delta               loaded_chunks=+1 non_air_blocks=+21810

Where time is spent (ranked by mean contribution)
───────────────────────────────────────────────────
...
```

Now when you paste optimize output, the SHAPE of the workload (rd
distance, chunk count, growth during measurement) is visible
alongside the timing data. "91ms shadow" means different things at
6 vs. 33 vs. 200 loaded chunks.

For backward compatibility: if a result file predates the workload
snapshot (c.13-scout and earlier), the workload context is silently
omitted.

```bash
cd ~/Code/unendlich-development/unendlich-game
./commands/update_from_claude_zip.sh unendlich-v0.24.2c.13-instrumentation.zip
git add -A && git commit -m "Update to v0.24.2-c.13-instrumentation"
./commands/tag_current_version.sh

cargo build --release -p unendlich-launcher -p unendlich-analyze

# Try the warmup feature. Add `warmup_ms = 3000` to rd8_smoke.unendtest:
#   [engine]
#   duration_ms = 8000
#   warmup_ms = 3000
# Then run:
unendlich-launcher run tests/specs/rd8_smoke.unendtest --version @HEAD
# Compare shadow_p50_ms against your c.13-scout baseline — should be
# lower (steady-state only) than the 95ms that included warmup samples.

# Try the bucket feature. Don't add it to a spec; set the env var
# as a one-off diagnostic:
UNENDLICH_SHADOW_BUCKETS=4 \
    unendlich-launcher run tests/specs/rd8_smoke.unendtest --version @HEAD
# Then look at events.jsonl for shadow_buckets_timing events.
# (The result file's shadow_p50_ms will be SLOWER than non-bucketed
# because we forced the per-chunk fallback path. Don't compare
# bucket-mode timings to indirect-mode timings.)

# unendlich-analyze now shows workload context up top:
unendlich-analyze optimize ~/.unendlich/runs/r-.../result.unendresult.json
```

## What's NOT in this ship

- **`UNENDLICH_SHADOW_BUCKETS` aggregation into `unendlich-analyze`.**
  Today bucket data lives in events.jsonl only. A future ship could
  read those events and produce a per-bucket distribution.
- **Plant/creature/weather counts in the snapshot.** Filed as
  "opportunistic — add when working in those subsystems."
- **Cross-run correlation analysis.** "Shadow time correlates with
  non_air_blocks r=0.7" is a real perf question we can ask later
  when we have many runs.

## Path forward

c.17-a is the next code ship: multiview shadow render pass, visual
parity. The c.13-instrumentation ship gives us the diagnostic
capabilities we'll use to measure c.17-a's effect properly:

- **Warmup**: shadow_p50_ms is no longer polluted by chunk-gen
  warmup, so c.17-a's effect is measurable cleanly.
- **Workload snapshots**: confirms the workload was identical
  across @c.13-instrumentation and @c.17-a (no churn confounding
  the comparison).
- **Shadow buckets**: if c.17-a regresses shadow as expected, the
  bucket data tells us WHERE the regression lives.

When you're ready to start c.17-a, paste back:
- c.13-instrumentation rd8_smoke output with `warmup_ms=3000`
  (this is the cleaner baseline c.17-a is trying to compete with)
- Any concerns about the plan

Then we begin.
