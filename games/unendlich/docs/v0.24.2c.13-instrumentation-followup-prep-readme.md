# v0.24.2c.13-instrumentation-followup-prep — c.17 prep work

**Pure prep ship. No engine runtime changes.** Three additions to
make starting c.17-a focused execution rather than exploration.

## What's new

### `tests/specs/rd8_warmup.unendtest`

Anchor spec for c.17 baselining. Like `rd8_smoke` but with
`warmup_ms = 3000` baked in and a `shadow_p50_ms = { max = 150.0 }`
performance guard.

Every c.17-a/b/c/d ship should PASS this spec. Ships that BEAT the
113.9ms baseline should tighten the threshold downward.

### `commands/baseline_for_c17.sh`

Builds launcher, runs rd8_warmup against @HEAD, prints diag. Run
this before starting any c.17 ship to lock in the comparison baseline.

```bash
./commands/baseline_for_c17.sh
```

### `docs/v0.24.2c.17-a-implementation-notes.md`

Detailed pre-implementation plan for c.17-a multiview shadow render
pass. Goes file-by-file through the actual diff shape, captures
discoveries from re-reading the code:

- Multiview feature isn't currently enabled on the device (probed
  but not requested). Must be added in `context.rs` first.
- Shadow and main pipelines share descriptor sets — the new
  view_params SSBO binding must go in BOTH DSLs (binding 3,
  STORAGE_BUFFER, VERTEX stage).
- Framebuffer `layers(1)` is correct under multiview; the view_mask
  determines layer count, not the framebuffer.
- Two image views needed: one 2D_ARRAY for multiview framebuffer
  attachment, one 2D layer-0 for the main fragment shader's
  `sampler2DShadow`.

Honest concerns flagged:
- Subpass dependency stages might need `VK_DEPENDENCY_VIEW_LOCAL`
- Honeykrisp's multiview path may have driver-edge bugs (brand-new
  driver, c.13-instrumentation hit DEVICE_LOST on a different
  in-render-pass code path)

Read this before starting c.17-a. The estimated session scope is
3-4 hours of focused work plus ~1 hour of debugging budget for the
risky shadow_map.rs and world_renderer.rs descriptor-write changes.
