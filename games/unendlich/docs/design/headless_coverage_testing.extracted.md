The world is bit-exact given a seed and an input log. The only butterflies are the player. Fuzz the inputs, fix everything else, and the world becomes a reproducible, scoreable, differentiable integration test for every system in the engine.

1.  Design Philosophy — Why This Works for Unendlich
Unendlich was designed for determinism. The physics simulation uses Fixed-point arithmetic (the Rust `Fixed` type). Mob RNG is seeded from mob entity ID — the same mob on the same tick with the same inputs makes the same decision. The tick scheduler is deterministic. The Choir voice recognition pipeline produces deterministic output given identical PCM input. World generation from a fixed seed produces bit-exact terrain.

This means the world is a function: `world_state_n+1 = tick(world_state_n, player_inputs_n)`. Given a fixed initial state and a recorded sequence of player inputs, the world state at every subsequent tick is computable. This is the foundation for the test harness — not a simulation of the game, the game, running headless.

Non-determinism source
Treatment in test harness
World generation
Fixed seed per campaign run. Identical seed → identical world. Seed is a run parameter, not random.
Mob AI decisions
Each mob's internal RNG seeded from EntityId (u64). Same entity, same tick, same decision — always.
Item genome mutation
Mutation RNG seeded from (forge_id, tick_count, ingredient_hash). Fully deterministic given inputs.
Choir voice recognition
Injected as pre-computed PCM frames from the fuzzing corpus. No live microphone in headless mode.
Player position / look
THE BUTTERFLY. Generated by PlayerAgent from a fuzzing seed. Saved to input log. Replays exactly.
Player gesture tokens
THE BUTTERFLY. Generated by PlayerAgent's bending planner. Part of the input log.
Real-world timing
Replaced by a fixed-step tick counter. No wall clock. No sleep. Runs as fast as the CPU allows.

The headless harness skips: the renderer (no GPU, no window), the audio output pipeline (no speaker, no OS audio), the network server (no remote clients), the OS input loop (no keyboard, no mouse). It keeps: the entire world simulation, mob AI, bending, crafting, quest systems, and all state machines. Performance target: 100× realtime on a single core.

2.2  HeadlessWorld
  Rust — HeadlessWorld: real engine, no-op render/audio, instrumented simulation
// The headless world is the real engine entry point with the render/audio
// subsystems replaced by no-ops at the trait boundary.

pub struct HeadlessWorld {
    pub sim:      WorldSim,          // the real simulation
    pub observer: StateObserver,     // instruments sim without modifying it
    pub agent:    PlayerAgent,       // generates player input each tick
    pub tick:     u64,
    pub config:   RunConfig,
}

impl HeadlessWorld {
    /// Run N ticks as fast as possible. Returns coverage at each checkpoint.
    pub fn run(&mut self, ticks: u64) -> RunResult {
        for _ in 0..ticks {
            // 1. Generate player input for this tick
            let input = self.agent.generate(self.tick, &self.sim);
            self.agent.log.push(input.clone());  // save for replay / divergence

            // 2. Tick the real simulation
            self.sim.tick(input);

            // 3. Observe state (zero-cost if sampling rate not met)
            if self.tick % self.config.snapshot_interval == 0 {
                self.observer.snapshot(&self.sim, self.tick);
            }

            self.tick += 1;
        }
        self.observer.finalise()   // compute coverage scores from observations
    }
}

// The render/audio traits are satisfied by no-ops:
impl Renderer for NoopRenderer { fn submit_frame(&self, _: &Frame) {} }
impl AudioOut  for NoopAudio   { fn play_sample(&self, _: f32) {} }

2.3  PlayerAgent — The Fuzzer
The PlayerAgent generates player input each tick from a configurable style profile and a fuzzing seed. It is the only source of non-determinism in the run. Its output is saved to an input log, making every run fully replayable.

  Rust — PlayerAgent: fuzzed input generation with style profiles
pub struct PlayerAgent {
    pub rng:     StdRng,              // seeded from fuzz_seed — all input from here
    pub log:     Vec<PlayerInput>,    // every generated input, for replay
    pub profile: StyleProfile,        // what kind of player to simulate
    pub plan:    BendingPlanner,      // what bending to attempt each tick
}

pub struct StyleProfile {
    /// Exploration bias: probability of moving toward unseen chunks per tick
    pub explore_bias:       f32,  // 0.0 = stay still, 1.0 = always push frontier
    /// Combat bias: probability of engaging vs fleeing when mob is in range
    pub combat_bias:        f32,
    /// Bending density: probability of attempting a technique sequence per tick
    pub bending_density:    f32,
    /// Crafting frequency: probability of visiting a forge per 1000 ticks
    pub crafting_freq:      f32,
    /// Voice density: probability of injecting a voice event per 10 ticks
    pub voice_density:      f32,
    /// Choir match quality: how close to target frequency the injected PCM is
    pub choir_accuracy:     f32,  // 1.0 = perfect match, 0.0 = random noise
}

2.4  Fuzz Campaign — Parallel Runs
A FuzzCampaign runs N instances of HeadlessWorld in parallel, each with a different fuzz_seed but the same world_seed and style_profile. Coverage is union-aggregated across all runs — a code path exercised in any run is counted as covered.

  Rust — FuzzCampaign: parallel headless runs, coverage union
pub struct FuzzCampaign {
    world_seed:   u64,
    fuzz_seeds:   Vec<u64>,    // one per parallel run
    style:        StyleProfile,
    duration:     CampaignDuration,
    snapshot_every: u64,       // ticks between state snapshots
}

pub enum CampaignDuration {
    Ticks(u64),         // precise tick count
    SimDays(u32),       // 24000 ticks/day * n
    UntilCoverage(f32), // run until aggregate coverage reaches target
    WithTimeout(Duration, Box<CampaignDuration>),  // time-capped
}

// Standard campaign sizes:
// Smoke test: 1 run × 1 simulated day (24000 ticks) — ~5 seconds on one core
// Nightly:    8 runs × 10 days (240000 ticks each) — ~10 minutes on 8 cores
// Release:   32 runs × 100 days (2400000 ticks each) — ~2 hours on 32 cores
// Exhaustive: 128 runs × 100 days, 7 style profiles — targets 95%+ coverage

impl FuzzCampaign {
    pub fn run_parallel(&self) -> AggregatedResult {
        let results: Vec<RunResult> = self.fuzz_seeds.par_iter()  // rayon
            .map(|&fuzz_seed| {
                let mut world = HeadlessWorld::new(
                    self.world_seed, fuzz_seed, self.style.clone(),
                    self.snapshot_every,
                );
                world.run(self.duration.to_ticks())
            })
            .collect();
        AggregatedResult::union(results)
    }
}

  🔀  Fuzzing Strategy — Generating Realistic Player Input

4.  Fuzzing Strategy
The fuzzer generates player input from three sources: a movement planner (position deltas and look direction), a bending planner (gesture tokens and technique selection), and a voice corpus (injected PCM frames for Choir events). All three are seeded and reproducible.

4.1  Movement Planner — Structured Exploration
Random walk is not realistic enough. The movement planner uses a hierarchical structure: a long-term goal (explore, reach a discovered forge, fight nearby mob), a short-term path (A* to goal with noise), and per-tick jitter (the realistic micro-variation of human movement):

  Rust — MovementPlanner: goal-directed movement with jitter and idle states
pub struct MovementPlanner {
    goal:          Goal,
    path:          Vec<ChunkCoord>,  // computed by A* toward goal
    jitter_rng:    SmallRng,
}

pub enum Goal {
    Explore,               // push toward unseen chunk frontier
    ReachForge(ForgeId, WorldPos),
    EngageTarget(EntityId),
    FleeFrom(EntityId),
    EnterZone(BiomeType),  // deliberately target a property zone for coverage
    Idle,                  // stand still — tests mob approach, Lauscher patience
}

impl MovementPlanner {
    pub fn next_input(&mut self, world: &WorldSim, tick: u64, profile: &StyleProfile,
                      rng: &mut StdRng) -> MovementInput {
        // Re-evaluate goal every 200 ticks (realistic re-planning frequency)
        if tick % 200 == 0 { self.goal = self.pick_goal(world, profile, rng); }

        // Inject IDLE states: realistic players stop and look around
        let idle_prob = 0.02_f32;  // 2% per tick = ~30 seconds/hour at idle
        if rng.gen::<f32>() < idle_prob { return MovementInput::stationary(); }

        // Micro-jitter: additive noise on direction (simulates mouse drift)
        let base  = self.path_direction(world);
        let noise = Vec2::new(rng.gen_range(-0.05..0.05),
                               rng.gen_range(-0.05..0.05));
        MovementInput { move_dir: (base + noise).normalise(), sprint: rng.gen::<f32>() < 0.2 }
    }

    fn pick_goal(&self, world: &WorldSim, profile: &StyleProfile,
                  rng: &mut StdRng) -> Goal {
        let roll = rng.gen::<f32>();
        if roll < profile.explore_bias  { return Goal::Explore; }
        if let Some(mob) = world.nearest_hostile() {
            if rng.gen::<f32>() < profile.combat_bias { return Goal::EngageTarget(mob); }
        }
        // Bias toward unvisited zones for coverage:
        if let Some(zone) = world.unvisited_zone_nearest(world.player_pos()) {
            if rng.gen::<f32>() < 0.3 { return Goal::EnterZone(zone); }
        }
        Goal::Idle
    }
}

4.2  Bending Planner — Technique Sequences
The bending planner selects gesture token sequences and voice frames based on the player's current situation and the coverage observer's feedback. The observer can report which techniques have not yet been exercised, and the planner prioritises those:

  Rust — BendingPlanner: coverage-guided technique selection and voice synthesis
pub struct BendingPlanner {
    coverage_hint:  CoverageHint,     // fed by observer: 'these haven't fired yet'
    active_discipline: Discipline,
}

impl BendingPlanner {
    pub fn plan_bending(&mut self, world: &WorldSim,
                         rng: &mut StdRng,
                         profile: &StyleProfile) -> Option<BendingInput> {

        if rng.gen::<f32>() >= profile.bending_density { return None; }

        // Coverage-guided: prefer techniques not yet exercised
        let target = if rng.gen::<f32>() < 0.3 {  // 30%: try to hit uncovered
            self.coverage_hint.next_uncovered_technique()
                .unwrap_or_else(|| self.random_technique(rng))
        } else {
            self.random_technique(rng)
        };

        // Build the gesture token sequence for this technique
        let tokens = target.canonical_token_sequence();
        // Add realistic noise: 15% chance of a wrong token
        let tokens = self.apply_input_error(tokens, 0.15, rng);

        Some(BendingInput { tokens, voice_frame: None })
    }

    pub fn plan_voice(&mut self, world: &WorldSim,
                       rng: &mut StdRng,
                       profile: &StyleProfile) -> Option<VoiceInput> {
        if rng.gen::<f32>() >= profile.voice_density { return None; }

        // Pick a voice shape or Choir frequency to attempt
        let target = self.coverage_hint.next_uncovered_voice()
            .unwrap_or_else(|| VoiceTarget::Random(rng.gen()));

        // Synthesise a PCM frame matching target frequency at given accuracy
        let pcm = synthesize_voice_pcm(target, profile.choir_accuracy, rng);
        Some(VoiceInput { pcm })
    }
}

4.3  Voice Corpus — Synthetic PCM Injection
The Choir recognition system expects raw PCM frames. In headless mode, these are synthesised directly. Three sources:

Pure tone: sine wave at the target Choir base frequency (e.g., 220 Hz for Earth). Accuracy = 1.0 tests exact match. Accuracy 0.8 = ±30 cents off — tests near-match behavior.
Formant voice synthesis: a simple LPC-based synthesis producing voiced phonemes for voice shape words ('rise', 'surge', etc.). Not realistic — realistic enough to exercise the phoneme recognition pipeline.
Reactive noise injection: short broadband bursts (gasps), mid-frequency decaying pulses (grunts), sub-50ms plosive bursts (pops). These test the reactive voice classifier independently of the Choir pipeline.
Silence injection: 2+ seconds of below-noise-floor signal. Tests the breath-hold detector and the Lauscher's audio database accumulation behavior under player silence.



  🔀  Divergence Analysis — Finding the Butterflies

5.  Divergence Analysis
Divergence analysis compares two runs with identical world seeds but different fuzz seeds. Every 1000 ticks (the snapshot interval), a deterministic hash of the full world state is computed. The first tick where the hashes differ is the divergence point. Binary search on the input logs finds the exact player input that caused the fork.

5.1  World State Hash
The hash must cover all simulation state that persists between ticks. Rendering state, audio state, and log data are excluded — they are downstream of the simulation, not part of it:

  Rust — world state hash: deterministic, covers all persistent simulation state
/// Deterministic world state hash. Same state → same hash. Always.
pub fn hash_world_state(world: &WorldSim) -> u64 {
    use std::hash::{Hash, Hasher};
    use std::collections::hash_map::DefaultHasher;
    let mut h = DefaultHasher::new();

    // Player state
    world.player.position.hash(&mut h);        // Fixed-point: exact
    world.player.chi_pool.hash(&mut h);
    world.player.active_discipline.hash(&mut h);
    world.player.harmonic_mesh.hash(&mut h);   // dragon coupling depths
    world.player.genome_reader_active.hash(&mut h);

    // All active entities — sorted by EntityId for determinism
    let mut entities: Vec<_> = world.entities.iter().collect();
    entities.sort_by_key(|(id, _)| *id);
    for (id, entity) in &entities {
        id.hash(&mut h);
        entity.position.hash(&mut h);
        entity.fsm_state.hash(&mut h);
        entity.mob_memory_hash().hash(&mut h); // deterministic hash of MobMemory
        entity.certainty_quantised().hash(&mut h); // ghost tracking state
    }

    // Item genomes — sorted by item instance ID
    for (iid, genome) in world.item_genomes.iter_sorted() {
        iid.hash(&mut h);
        genome.hash(&mut h);
    }

    // Quest state
    world.quest_state.hash(&mut h);

    // Environmental property field (sampled at 16 points)
    for pos in PROPERTY_SAMPLE_POSITIONS {
        world.env_field.at(pos).quantised_hash().hash(&mut h);
    }

    h.finish()
}

5.2  Butterfly Tracer — Binary Search on Input Log
When the snapshot hashes diverge at tick T, the butterfly is somewhere between the previous snapshot (tick T−1000) and T. Binary search on the input log finds it in log₂(1000) ≈ 10 replay runs:

  Rust — ButterflyTracer: binary search on input logs to find divergence cause
pub struct ButterflyTracer {
    world_seed: u64,
    log_a:      Vec<PlayerInput>,   // run A's input log
    log_b:      Vec<PlayerInput>,   // run B's input log
}

impl ButterflyTracer {
    /// Find the exact tick where run A and B diverge.
    /// Returns (diverge_tick, input_a, input_b) — the inputs that forked the world.
    pub fn find_butterfly(&self, diverge_range: Range<u64>) -> ButterflyResult {
        let mut lo = diverge_range.start;
        let mut hi = diverge_range.end;

        while hi - lo > 1 {
            let mid = (lo + hi) / 2;

            // Replay both runs up to mid from the same initial state
            let state_a = replay(self.world_seed, &self.log_a[..mid as usize]);
            let state_b = replay(self.world_seed, &self.log_b[..mid as usize]);

            if hash_world_state(&state_a) == hash_world_state(&state_b) {
                lo = mid;  // same up to mid — butterfly is after
            } else {
                hi = mid;  // different at mid — butterfly is before
            }
        }

        ButterflyResult {
            tick:    lo,
            input_a: self.log_a[lo as usize].clone(),
            input_b: self.log_b[lo as usize].clone(),
            diff:    InputDiff::compute(&self.log_a[lo as usize],
                                         &self.log_b[lo as usize]),
        }
    }
}

7.2  Regression Gating
Every CI run compares against a stored baseline. A regression is flagged when any dimension drops by more than its tolerance, or when the overall weighted aggregate drops by more than 2 points:

  Rust — RegressionPolicy: per-dimension tolerance and CI gate
pub struct RegressionPolicy {
    /// Overall weighted aggregate must not drop by more than this
    aggregate_tolerance: f32,   // 2.0 points

    /// Per-dimension tolerances — tighter for critical systems
    dimension_tolerances: HashMap<DimensionId, f32>,
    // Examples:
    // Simulation:          0.5  (nearly zero tolerance)
    // AI FSM coverage:     1.5  (some variation expected with fuzzing)
    // Bending techniques:  2.0  (technique coverage depends on path)
    // Content coverage:    5.0  (broad tolerance — content coverage is noisy)
}

pub fn check_regression(baseline: &ScoreCard, current: &ScoreCard,
                          policy: &RegressionPolicy) -> RegressionReport {
    let mut failures = vec![];
    for dim in DimensionId::all() {
        let drop = baseline.score(dim) - current.score(dim);
        let tol  = policy.dimension_tolerances.get(&dim).copied()
                         .unwrap_or(policy.aggregate_tolerance);
        if drop > tol {
            failures.push(RegressionFailure {
                dimension:  dim,
                baseline:   baseline.score(dim),
                current:    current.score(dim),
                drop,
                tolerance:  tol,
            });
        }
    }
    RegressionReport { failures, passed: failures.is_empty() }
}

9.  Coverage Heatmap and Reporting
9.1  Heatmap Categories
The heatmap shows which specific items within each category were never exercised across all runs in a campaign. Each item is an individual code path, FSM state, recipe, biome ID, technique ID, or voice shape. Items that were never hit are candidates for targeted test additions or confirmation that they require unreachable game states.

Heatmap category
What 'never exercised' means
Mob FSM states
A specific FSM state (e.g., dragon THERMAL_SOAR) was never entered by any mob of that type during any run. May indicate: the condition for that state is unreachable in the style profiles used, or the state transition has a bug.

9.2  Never-Exercised Code Path Report
The StateObserver can instrument at the code path level using a coverage counter array (a bitset of code path IDs, where each ID corresponds to a tagged branch in the engine code). After the campaign, unset bits identify code that never ran:

  Rust — COVERAGE! macro: lightweight code path instrumentation (zero-cost in prod)
// Instrument engine code with coverage tags:
// In production builds, COVERAGE macro compiles away to nothing.
// In headless test builds, it records a hit in the coverage bitset.

#[cfg(test)]
macro_rules! COVERAGE {
    ($id:literal) => {
        COVERAGE_BITSET.set($id, Ordering::Relaxed);
    }
}
#[cfg(not(test))]
macro_rules! COVERAGE { ($id:literal) => {} }

// Usage in engine code:
fn dragon_fsm_tick(dragon: &mut Dragon, world: &World) {
    match dragon.state {
        DragonFsmState::Grounded_Rest => {
            COVERAGE!(1001);  // 'dragon FSM: grounded rest tick'
            // ... rest of logic
        },
        DragonFsmState::Thermal_Soar => {
            COVERAGE!(1007);  // 'dragon FSM: thermal soar tick'
            // Only reachable if dragon detects a thermal column
            // May show as 0 if the test world has no active thermals
        },
        // ...
    }
}

// After campaign, report any COVERAGE IDs that were never set:
pub fn uncovered_paths(bitset: &CoverageBitset) -> Vec<CoveragePath> {
    COVERAGE_REGISTRY.iter()
        .filter(|path| !bitset.get(path.id, Ordering::Relaxed))
        .collect()
}




  🔗  ECS Wiring Coverage — Components, Archetypes, Events, Dataflows

10.  ECS Wiring Coverage — What Is Actually In The Game
Gameplay coverage (§3) measures whether features happened. ECS wiring coverage measures whether the underlying wiring that makes features possible was actually exercised. These are different. A bending technique can fire without the ItemGenome→SwayMark→Enchantment edge ever activating. A Lauscher FSM can reach all six states without any of its state transition paths from Freeze being taken. The wiring graph is orders of magnitude larger than the feature list.

For Unendlich specifically, the wiring graph has several cycles (the Lauscher degradation loop, the expression profile → world adaptation → player reaction → expression profile cycle) and continuous-valued edges (the property field threshold checks — 7 properties × ~8 techniques each = ~56 independent graph edges per discipline) that standard DAG-based dataflow coverage tooling cannot handle. The coverage model requires extensions.

10.1  Component Coverage
Components are the atoms of the ECS. A component that is defined but never instantiated is dead code. A component that is instantiated but never mutated may indicate a missing system link. A component that is mutated but never read by any consuming system is a write with no effect.

10.6  Interaction Matrix Coverage
Interactions are pairs of things that produce an emergent result when they meet. In Unendlich, the interaction space is extremely large — every combination of element × property condition × mob state × item genome × formation context can produce a distinct result. Full coverage is impossible; meaningful coverage focuses on the interactions most likely to harbour bugs.

10.7  Resource Coverage
Resources are global singletons accessed by multiple systems. A resource that is written by one system but never read by its downstream consumers is a wasted write. A resource that is read by a system before it has been initialised produces undefined state.

Resource
Type
Coverage risk
EnvironmentalPropertyField
Continuous spatial, 7 channels
Most-read resource in the engine. Risk: a property channel (e.g., B — Brine mineral richness) that is computed correctly but never queried by any bending system. Verify all 7 channels are read at least once per 1000 ticks.
FormationLexicon

Written by proximity detection, read by formation context activation. Risk: the formation is registered but the FormationContext component on nearby entities is never updated. Registry → Component write edge.

The 56% ECS wiring aggregate is not a failure:  It means the 100-day benchmark exercises the features but leaves 44% of the wiring paths unexercised. Most of that 44% is in the long-tail interaction pairs and in property threshold edges that only activate in specific biome combinations. These require targeted campaigns, not longer general-purpose runs. Document the wiring gaps and write focused test scenarios to close them.
