# v0.24.7-gpu-mesh-batch — batched GPU sparse mesher (Layer A.2 v2)

Continues Layer A.2. The previous ship (v0.24.6) validated GPU
sparse meshing on AGX with topology parity 36/36 but per-chunk
performance was 0.51× CPU because the ~550us dispatch floor was
paid per chunk. This ship amortizes that floor by batching multiple
chunks into one submission.

## What changed

### Batched API

```rust
pub struct ChunkBatchInput<'a> {
    pub coord: ChunkCoord,
    pub records: &'a [SurfaceRecord],
}

pub struct ChunkBatchOutput {
    pub coord: ChunkCoord,
    pub mesh: Result<ChunkMesh>,
}

impl SparseGpuMesher {
    pub fn mesh_chunks_batch(&self, chunks: &[ChunkBatchInput])
        -> Result<Vec<ChunkBatchOutput>>;
}
```

Per-chunk `Result` so one chunk's overflow doesn't sink the whole
batch. Caller can fall back to CPU mesher for individual chunks.

### Per-chunk slots in shared buffers

Buffers expanded to hold `MAX_BATCH_CHUNKS = 16` slots each:
- Records buffer: 16 × 16K × 16B = 4 MB
- Vertex buffer: 16 × 43K × 24B = ~16 MB
- Index buffer: 16 × 64K × 4B = 4 MB
- Counter buffer: 16 × 16B = 256B

Total ~24 MB persistent HOST_VISIBLE GPU memory. Fine on M2's
unified memory.

### Shader changes

Push constants extended with per-chunk offsets:
- `record_offset`: where this chunk's records start in the records buffer
- `vertex_offset`: where this chunk's output vertices start
- `index_offset`: where this chunk's output indices start
- `counter_offset`: u32 offset of this chunk's 4-u32 counter group

Counters changed from struct binding to array — one 4-u32 group per
slot. Index values written to the indices buffer are **slot-local**
(matches v1's single-chunk semantics; readback knows the slot
boundaries).

### Single-chunk API preserved

`mesh_chunk(coord, records)` still works — implemented as a
batch-of-one. Existing callers (including `gpu-mesh-bench`'s v1
path) unchanged.

### Dispatch model

One `cmd_dispatch` per active chunk slot, all in one command buffer,
one `vkQueueSubmit`, one fence wait. The ~550us per-submit floor is
paid once for the whole batch (up to 16 chunks). Per-dispatch
overhead within a command buffer is much smaller (~us, not ms).

Batches larger than `MAX_BATCH_CHUNKS` split internally into
multiple submissions — the API accepts any size, the implementation
chunks them.

## Bench expansion

`gpu-mesh-bench` now runs both paths:

1. **v1 path**: 36 chunks, one mesh_chunk call each. Reports
   per-chunk numbers and overall.
2. **v2 path**: All 36 chunks submitted as one batch. Reports
   total time and per-chunk average.

The v2 vs v1 speedup is the headline number — directly measures
the dispatch-floor amortization on real hardware.

## Expected output

v1 section (unchanged from v0.24.6): per-chunk CPU vs GPU, totals,
36/36 topology match.

v2 section (new):
```
─ Batched (v2) path ─

Batched dispatch (36 chunks): N us total (M us/chunk avg)
Topology matches: 36/36 chunks
Total quads emitted: ...

v2 vs v1 speedup: X.XX×
v2 vs CPU speedup: Y.YY×
```

What I'm predicting:
- **v2 total time: 1-3 ms** for 36 chunks. The 36 dispatches split
  into 3 batches of 16/16/4 ≈ 3 submissions, paying ~550us × 3 =
  ~1.6 ms minimum plus compute.
- **v2 vs v1 speedup: 10-15×.** v1 paid 36 × ~636us = ~23 ms; v2
  pays ~3 submissions worth of round-trip.
- **v2 vs CPU speedup: ~3-5×.** CPU did 36 × ~326us = ~12 ms. If
  v2 lands at ~2-3 ms total, it beats CPU comfortably.

If v2 is dramatically slower than expected, the dispatch-amortization
hypothesis is wrong on AGX and we need to look at compute saturation
within the batch.

If v2 beats CPU comfortably, this is the green light for production
wiring (Layer A.3).

## What this ship does NOT do

- **No production wiring.** The world bin still uses the CPU
  mesher. v2 is exercised only through the bench.
- **No async dispatch.** `mesh_chunks_batch` blocks the caller
  until GPU completes. Production wiring will need async dispatch
  to avoid blocking the chunk loader thread.
- **No overlay / prediction integration.** Edits and predicted
  edits aren't part of this layer yet.
- **No lighting / AO / tints.** Same provisional palette as v1.

## Honest concerns

1. **AGX dispatch behavior with many cmd_dispatch in one cmd_buffer
   is untested.** v0.24.6 used one `cmd_dispatch` total. v2 records
   up to 16 in one command buffer. If AGX firmware serializes
   between dispatches (it shouldn't, but TBDR has surprised us),
   the speedup won't materialize.

2. **No per-dispatch barrier.** All 16 dispatches share the
   pre-dispatch counter barrier and the post-dispatch readback
   barrier. They DON'T need barriers between each other because
   they write to non-overlapping slot regions. But Vulkan's
   validation might complain anyway. If validation errors appear,
   we'd need per-dispatch barriers (still much faster than per-
   submission).

3. **Counter buffer cmd_fill_buffer fills all 256 bytes** even if
   only a few slots are active. Cheap operation but worth noting.

4. **HOST_VISIBLE memory pressure.** 24 MB per mesher instance.
   On systems with constrained mappable memory this could matter.
   M2's unified memory makes this trivial.

5. **The bench's v2 path is a single batch** (36 chunks via the
   `mesh_chunks_batch` splitter). The internal splitter does 3
   submissions back-to-back. The reported v2 time includes all 3
   submissions; it's not measuring a single-batch best case.

## Next ship

If v2 hardware result shows substantial speedup over v1:
**Layer A.3** — production wiring. Route Near-LOD mesh requests
through `mesh_chunks_batch` instead of the CPU mesher. Requires:
- Async dispatch (current API blocks the caller)
- Per-chunk fallback to CPU on overflow
- Integration with existing `MeshingPool`'s `MeshResult` channel

If v2 doesn't show speedup: investigate AGX compute saturation
within the batch, possibly merge multiple chunks' records into
one dispatch with thread→chunk mapping (the "Strategy B" from
the architecture conversation).
