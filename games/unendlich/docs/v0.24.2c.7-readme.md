# v0.24.2c.7 — Upload knobs + workload-shape summary

Two diagnostic surfaces added so we can test the "shadow GPU cost scales with `rendering:` chunk count" hypothesis from the c.6 analysis.

## What's in this ship

### `UNENDLICH_MAX_UPLOADS_PER_FRAME=N`

Hard cap on number of chunk meshes uploaded per frame in `unendlich-world`. Default 16. Lower values slow world fill but reduce the per-frame GPU work growth rate.

```bash
UNENDLICH_MAX_UPLOADS_PER_FRAME=4 cargo run ... --bin unendlich-world
```

Was already wired in `unendlich-spin`; now also wired in `unendlich-world`. Registered in the runtime-flags table so its value appears in `run_summaries.txt`.

### `UNENDLICH_UPLOAD_BUDGET_MS=F`

Soft cap on CPU milliseconds spent uploading per frame. Default 4.0. Whichever cap (count or budget) trips first wins. Useful when meshes vary in size — a raw count cap may admit very large or very many uploads, while the time cap keeps per-frame work bounded.

### Workload-shape summary in run-summaries.txt

Added to each run block. Samples `loaded` and `rendering` once per FPS-log window (= ~1s) and reports min/p50/p90/max over the run:

```
Workload-shape summary (samples taken once per FPS-log window):
  loaded     n=  30  min=  120  p50=  450  p90=  650  max=  680
  rendering  n=  30  min=   45  p50=  120  p90=  140  max=  145
```

This is the diagnostic surface I needed to disambiguate "shadow GPU cost varied because the workload varied" from "shadow GPU cost varied because the code changed." Now every run records its workload shape.

## Why this ship now

The c.6 analysis ran into a confounder. The c.5 bisect run-3 (legacy framebuffer, 25ms shadow p50, 15s duration) and the c.6 30s run (legacy framebuffer, 72ms shadow p50, 30s duration) used the same code path but produced very different perf numbers. The most plausible explanation is **steady-state workload differs by duration**: longer runs have more chunks loaded and more chunks visible to the shadow pass, so shadow GPU cost is higher.

But without the workload counters in the saved summary, I couldn't confirm this from the data. The c.7 summary fills that gap.

The upload knobs add the ability to bound workload growth directly — useful to test whether holding `rendering:` low produces stable, cheap shadow frames regardless of run duration.

## Suggested test sequence

Three 30-second runs at RD=8, same other env vars, three different upload caps:

```bash
# Baseline (default 16).
UNENDLICH_MAX_DURATION_MS=30000 \
UNENDLICH_RENDER_DISTANCE=8 \
cargo run --release --features render --features gpu --features hot-shaders --bin unendlich-world

# Capped at 4 — slows world fill significantly.
UNENDLICH_MAX_DURATION_MS=30000 \
UNENDLICH_MAX_UPLOADS_PER_FRAME=4 \
UNENDLICH_RENDER_DISTANCE=8 \
cargo run --release --features render --features gpu --features hot-shaders --bin unendlich-world

# Capped at 1 — extreme test.
UNENDLICH_MAX_DURATION_MS=30000 \
UNENDLICH_MAX_UPLOADS_PER_FRAME=1 \
UNENDLICH_RENDER_DISTANCE=8 \
cargo run --release --features render --features gpu --features hot-shaders --bin unendlich-world
```

What I'd be looking for:

| MAX_UPLOADS=16 | MAX_UPLOADS=4 | MAX_UPLOADS=1 | conclusion |
|---|---|---|---|
| rendering p50=130, shadow p50=70 | rendering p50=60, shadow p50=30 | rendering p50=20, shadow p50=15 | shadow cost ~linear in rendering count — upload cap is a real tuning knob |
| similar across all three | similar across all three | similar across all three | shadow cost is dominated by something other than chunk count (per-frame overhead, etc.) |

Even one run with `MAX_UPLOADS_PER_FRAME=4` should be informative — if the `Workload-shape summary` shows `rendering: max=60` instead of `max=130` and shadow p50 is lower too, the hypothesis is supported.
