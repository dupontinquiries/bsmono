# v0.24.2c.2 — Shadow Bisect Playtest

## What happened in v0.24.2c

v0.24.2c made the shadow pre-pass render 4 cascades into a 4-layer 2D array image. Visual contract was "no change" (main fragment shader still samples layer 0 with the same C0 cascade matrix). Playtest showed **shadows entirely missing**. Static analysis came up empty:

- Push constant byte layout: column-major std430-compliant (3 new tests, all pass).
- Cascade subresource ranges: each targets one layer, correct index (4 new tests, all pass).
- Vulkan-spec layout tracker: after the v0.24.2c shadow pre-pass, every layer is in DEPTH_STENCIL_READ_ONLY_OPTIMAL — matching the descriptor's expected layout (5 new tests, all pass).
- GPU vs CPU cascade-fit math: matches within 1e-3 (existing test, passes).
- Slot resolution, plane derivation, ViewGroup: all existing tests pass.

In total: 600 lib tests passing. The bug is in a class CPU tests can't catch (Vulkan runtime / driver, push-constant binding interaction, or something else outside the spec-modelable surface).

## How to use the bisect knobs

This build exposes two env vars to A/B different parts of the v0.24.2c change:

```
UNENDLICH_SHADOW_CASCADES=1..=4   (default 1)
UNENDLICH_SHADOW_LEGACY_FB=0|1    (default 1)
```

**`UNENDLICH_SHADOW_CASCADES`** controls how many cascades the shadow pre-pass renders.
- `1` (default): render only cascade 0 into layer 0. Skips cascades 1/2/3 entirely.
- `4`: render all 4 cascades. Matches v0.24.2c behavior.

**`UNENDLICH_SHADOW_LEGACY_FB`** controls which framebuffer cascade 0 renders into.
- `1` (default): legacy `framebuffer` (wraps `shadow.view`, a layer-0-only image view created the same way pre-v0.24.2c).
- `0`: new `layer_framebuffers[0]` (wraps the v0.24.2c-added `layer_views[0]`).

## The 4 configurations and what each tests

| CASCADES | LEGACY_FB | Description | Diagnosis if shadows visible | Diagnosis if shadows missing |
|---|---|---|---|---|
| 1 | 1 | Most v0.24.2b-like. One cascade via legacy framebuffer. | Means the push constant path works, the bug is the new framebuffer wiring AND/OR multi-cascade interference. | Push constant path is broken (or interacts badly with the new pipeline layout's push constant range). |
| 1 | 0 | One cascade, new framebuffer. | The new framebuffer wiring is fine; bug is in cascade 1/2/3 interference. | The new `layer_framebuffers[0]` is the bug — it differs from `framebuffer` in a way that matters. |
| 4 | 1 | All cascades, but C0 uses legacy framebuffer. | Multi-cascade rendering works, but `layer_framebuffers[0]` is the bug. | Bug is in cascade 1/2/3's render passes interacting with layer 0. |
| 4 | 0 | Full v0.24.2c. Should show whatever broke originally. | Wait... shadows actually work now? Surprising. Try without the shipped first run. | (Expected based on prior playtest.) |

## Recommended playtest sequence

If only one playtest per env-var combo is practical, this order maximizes information:

1. `UNENDLICH_SHADOW_CASCADES=1 UNENDLICH_SHADOW_LEGACY_FB=1` — closest to v0.24.2b.
   - **Shadows visible** → the new framebuffer or multi-cascade is the bug. Continue to #2.
   - **Shadows missing** → the push constant path itself is broken. Stop and report.

2. `UNENDLICH_SHADOW_CASCADES=1 UNENDLICH_SHADOW_LEGACY_FB=0` — one cascade, new framebuffer.
   - **Shadows visible** → multi-cascade is the bug. Continue to #3.
   - **Shadows missing** → the new framebuffer is the bug. Stop and report.

3. `UNENDLICH_SHADOW_CASCADES=4 UNENDLICH_SHADOW_LEGACY_FB=1` — all cascades, C0 via legacy fb.
   - **Shadows visible** → `layer_framebuffers[0]` is the bug. Stop and report.
   - **Shadows missing** → cascade 1/2/3 interaction is the bug. Stop and report.

## How to set env vars

```bash
UNENDLICH_RENDER_DISTANCE=6 UNENDLICH_VSYNC=1 UNENDLICH_INDIRECT=1 \
UNENDLICH_SHADOW_CASCADES=1 UNENDLICH_SHADOW_LEGACY_FB=1 \
cargo run --release --features render --features gpu --features hot-shaders --bin unendlich-world
```

Look at the log line at startup that says `Shadow bisect knobs: ...` to confirm what's active.

## What I'll do with the result

Based on which config restores shadows:
- **`(1, 1)` works**: build v0.24.2c.3 that diagnoses why the multi-render-pass interferes with layer 0 OR why the new framebuffer differs from the legacy one. Both are testable hypotheses with focused experiments.
- **`(1, 0)` works**: build v0.24.2c.3 that compares `framebuffer` and `layer_framebuffers[0]` byte-for-byte. They should be functionally equivalent.
- **`(4, 1)` works**: build v0.24.2c.3 that adds an explicit `DEPTH_STENCIL_READ_ONLY_OPTIMAL` barrier on layer 0 before the main pass sample, forcing the layout regardless of what cascades 1/2/3 did.
- **Nothing works**: revert to v0.24.2b on disk and we look at the renderer with fresh eyes.

## v0.24.2c.2 logging additions

This build (v0.24.2c.2-with-summaries) also includes:

- **`run_summaries.txt`** appended in cwd at shutdown — every bisect run gets its own block with timestamp, env vars, and full summaries. Run all 4 bisect configurations in sequence, then diff the saved blocks instead of scraping scrollback.
- **Rich per-zone summary** with p50/p90/p99 percentiles and `over_8.3ms=count (pct%)` stutter-rate field. The percentiles will tell us whether shadow's variance is bimodal (streaming spikes) or steady (always-slow).
- **ASCII box plots** below each summary block, visually showing the shape of each zone's distribution.

For details on the format and how to extract specific runs see `docs/v0.24.2c.2-logging-readme.md`.
