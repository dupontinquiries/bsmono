# v0.24.66/67-biased-walk + upload-priority

## Tagline

Two independent env-gated flags that bias the chunk-streaming
pipeline toward "what the player is looking at": biased shell walk
(submission-time) + priority queue (upload-time). Stage 1 Option D
+ Stage 2 from `docs/speculative/upload-scheduler-design.md`.
Zero added latency. Composes with RC29 (count cap), RC30
(submit-skip), RC31 (slack scheduler).

## Status

Drafted in sandbox during the rc29-adaptive-uploads session,
stacking on RC31. Not yet built with cargo or run on hardware.
Ship zip: `unendlich-rc32-biased-walk-and-upload-priority.zip`.
Single file (`bin/unendlich_world.rs`). Strict-additive on RC31.

## What this ship does

### Part 1: Biased shell walk (`UNENDLICH_BIASED_SHELL_WALK=1`)

The submit-phase shell walk (~2197 coords at RD=6) visits coords
in face-round-robin order via `ShellWalker`. Direction-fair, but
that means the chunks the player is *looking at* compete with
chunks behind their head for the per-tier budget slots.

This RC re-orders each shell so high forward-dot coords are
processed first. The per-tier budgets (NEAR_BUDGET=64, etc.) still
apply, but they fill with ahead-of-player coords first. Chunks
behind get leftover slots (or wait for the next frame).

Implementation:
1. Compute `player_forward = local_player.forward()` once per
   frame after `player_chunk` (cheap: ~3 trig ops).
2. Collect `ShellWalker::new(shell)` into a `Vec<(i32,i32,i32)>`
   (~300 entries).
3. If flag enabled, `sort_by` descending dot product with
   `player_forward`.
4. Iterate the Vec in sorted order; the existing per-coord work
   is unchanged.

Sort cost: O(N log N) where N ≤ 294 per shell. ~2400 ops.
Negligible vs the DashMap reads per coord.

Allocation overhead when flag is OFF: ~7 shells × ~300 entries
× 12 bytes ≈ 25 KB per frame. Negligible.

### Part 2: Upload priority (`UNENDLICH_UPLOAD_PRIORITY=1`)

The upload phase drains FIFO from the mesh pool's output channel.
The pool has multiple worker threads (default 4) that may finish
mesh work out of submission order; FIFO can then interleave a
Far-LOD chunk for shell 12 ahead of a Near chunk for shell 2.

This RC sorts the drained Vec by:
- Primary key: LOD (Near=0 < Mid=1 < Far=2 < VeryFar=3 — exploits
  `LodLevel`'s derived `Ord` with `#[repr(u8)]`)
- Secondary key: Chebyshev distance from `player_chunk`

After sort, the upload loop iterates in priority order. The
existing per-upload work (version check, mesh-cache restore, pool
allocation, byte memcpy) is unchanged.

Sort cost: O(N log N) over the drained Vec. With `upload_cap=64`
(default), ~384 comparisons. ~1µs. Negligible.

### How they compose

| Layer | Bias source |
|---|---|
| Submission (RC32 Part 1) | Forward direction × shell coord |
| Upload (RC32 Part 2) | LOD × Chebyshev distance to player |

These bias different points in the pipeline; together, a chunk the
player is looking at is more likely to (a) be submitted to the
mesh pool first and (b) be uploaded first when its mesh result
arrives.

## Activation

```bash
# Just biased shell walk:
UNENDLICH_BIASED_SHELL_WALK=1 \
  cargo run --release --bin unendlich-world --features="render,gpu,window"

# Just upload priority:
UNENDLICH_UPLOAD_PRIORITY=1 \
  cargo run --release --bin unendlich-world --features="render,gpu,window"

# Both:
UNENDLICH_BIASED_SHELL_WALK=1 UNENDLICH_UPLOAD_PRIORITY=1 \
  cargo run --release --bin unendlich-world --features="render,gpu,window"
```

Each independent. Default off. Init log line per flag:

```
[INFO] biased_shell_walk: ENABLED — chunks ahead of player processed first within each shell
[INFO] upload_priority: ENABLED — upload queue sorted by (LOD, distance) each frame
```

## Architecture changes (single file: bin/unendlich_world.rs)

### State (3 declarations near top of main())

```rust
let biased_shell_walk_enabled: bool = /* env */;
let upload_priority_enabled: bool = /* env */;
// player_forward computed per-frame inside the loop
```

### Per-frame forward direction

```rust
let player_forward = local_player.forward();  // glm::Vec3
```

Computed unconditionally because the cost is ~3 trig ops and it
gives a single uniform code path.

### Shell walk modification

Collect to Vec, sort if biased, iterate. Old direct
`for (dx,dy,dz) in ShellWalker::new(shell)` becomes:

```rust
let mut shell_coords: Vec<(i32, i32, i32)> = ShellWalker::new(shell).collect();
if biased_shell_walk_enabled {
    shell_coords.sort_by(|a, b| {
        let da = /* dot product */;
        let db = /* dot product */;
        db.partial_cmp(&da).unwrap_or(std::cmp::Ordering::Equal)
    });
}
for (dx, dy, dz) in shell_coords { /* existing per-coord work */ }
```

### Upload-phase sort

```rust
let mut drained = mesh_pool.drain_up_to(upload_cap);
if upload_priority_enabled {
    drained.sort_by(|a, b| {
        let a_dist = chebyshev(a.coord, player_chunk);
        let b_dist = chebyshev(b.coord, player_chunk);
        a.lod.cmp(&b.lod).then(a_dist.cmp(&b_dist))
    });
}
// existing loop over drained...
```

## Expected effect

**Qualitative**: chunks the player is actively looking at land
first when:
- Loading the world from scratch
- Crossing into a chunk boundary with ungenerated terrain
- After a fresh teleport / map reload

**Quantitative** (less certain without hardware data):
- Total world load time: unchanged (no chunks dropped, only
  reordered).
- p99 frame time: probably unchanged (these RCs don't reduce
  per-frame cost, just reorder it).
- Perceptual quality: improved (fewer "I'm staring at a hole
  while behind-me chunks are already done" moments).

## Risks

- **Vec allocation per shell**: the `shell_coords` Vec is
  fresh-allocated every shell, even with the flag off. ~25 KB/frame
  total. If profiling shows this as a real cost, hoist outside the
  loop and `.clear()` between shells.
- **Sort stability (biased walk)**: when `player_forward` ≈ zero
  (mostly looking down at exact ±y), dot products are all near
  zero and the sort becomes order-undefined for tied entries.
  Probably harmless; flagged.
- **Sort stability (upload priority)**: when two MeshResult entries
  have the same LOD AND same Chebyshev distance, the sort is not
  stable. Could reorder same-priority chunks frame-to-frame.
  Probably harmless; flagged.
- **Player forward at startup**: `local_player.forward()` is valid
  immediately on construction (uses pitch/yaw which start at zero).
  No NaN risk.

## Stage 3 status

Stage 3 (off-thread upload + DEVICE_LOCAL backing + staging
buffer ring) is the next architectural step but is NOT in this
ship. Detailed implementation guide written to
`docs/speculative/stage-3-implementation-guide.md` with three
sub-stages (A: in-frame DEVICE_LOCAL + staging; B: off-thread
memcpy; C: ring sizing optimization). Each sub-stage is
independently verifiable on hardware.

Data points from this session's verification reads:
- Mesh pool memory: confirmed `HOST_VISIBLE | HOST_COHERENT`
  (line 367 of mesh_buffer_pool.rs). Cache-coherency hypothesis
  validated.
- Queue topology: confirmed single-queue on AGX/Honeykrisp.
  Stage 3's wins come from (a) memcpy-off-render-thread and
  (b) DEVICE_LOCAL memory, NOT from queue parallelism.

Recommended: ship Stage 3 sub-stage A in a session with hardware
available. Validation layers must be enabled to catch sync errors
during initial development.
