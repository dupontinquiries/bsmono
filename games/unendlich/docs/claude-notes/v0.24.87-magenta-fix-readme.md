# v0.24.87 — magenta blocks fix (GPU mesher color table) + build restore

**Brick:** `unendlich-v0.24.87-magenta-fix.zip` (patch series, `git am --3way`)
**Files:** 3 (`shaders/chunk_mesh_octree.comp`, `render/mesher.rs`, `render_parity.rs`)
**Status:** code written + statically verified in authoring sandbox; **not**
compiled there (no cargo / no glslang available). The patch applies cleanly to
the baseline via `git am --3way`. Compile + on-hardware A/B is the apply step
below.

This is the "magenta foliage / holes" item from `docs/BACKLOG.md` and the
overflow-fix readme. It turned out to be two coupled problems with one root
cause, plus a latent build break.

---

## TL;DR

- GPU-meshed chunks (`UNENDLICH_GPU_MESHER=2`) rendered **bright magenta**
  for 13 blocks — *sandstone, obsidian, copper ore, quartz* (these generate
  in terrain, so the magenta is visible in the world) plus the placed/crafted
  blocks *oak planks, stone bricks, bricks, glass, iron/gold/coal block,
  bookshelf, pumpkin*. (The backlog called it "foliage"; it's actually these
  mineral/building blocks. Leaves/flowers were already handled — they are not
  the offenders.)
- Root cause: `BlockId` ids **48–51 and 57–66** were added to the enum after
  the earlier render-parity pass, but the GPU shader's `color_for_block`
  table was never extended, so those ids fell through to the magenta debug
  default (`vec3(0.80, 0.20, 0.80)`).
- The regression test built to catch exactly this
  (`render_parity::gpu_shader_colors_every_cpu_colored_block`) **passed
  blind**, because it checked a *hardcoded* block list that itself stopped at
  id 56/80 and omitted 48–66.
- **Separately: the crate almost certainly does not compile as it was zipped.**
  `render/mesher.rs::block_color` matched on a `BlockId::BerryBush` variant
  that exists **nowhere** in this tree (unresolved-variant error) and was also
  **non-exhaustive** (missing the same 13 ids → `E0004`). This looks like a
  half-applied RC23 berry-bush edit (see `rc23-berry-bush-prep.md`, which flags
  "exhaustive match locations" as the hazard). If your local tree wouldn't
  `cargo build`, this is why.

---

## What changed and why

**1. `shaders/chunk_mesh_octree.comp` — `color_for_block`** *(the visible fix)*
Added the 13 missing ids (48–51, 57–66) with colors = `base_color()/255`
(flat, no-climate). After this, every meshable block has a real color and
nothing reaches the magenta default in normal play.

**2. `render/mesher.rs` — `block_color`** *(restores the build)*
- Removed the stray `BerryBush => …` arm (and its comment): that variant
  does not exist in this tree.
- Added the same 13 blocks as explicit arms, so the match is exhaustive
  again. Values match the shader exactly, so CPU- and GPU-meshed chunks paint
  these blocks identically.

**3. `render_parity.rs` — `gpu_shader_colors_every_cpu_colored_block`**
*(so this can't silently regress again)*
Replaced the hardcoded `(id, BlockId)` list with iteration over
`BlockId::ALL` (skipping `Air` and `Water`, which don't flow through
`color_for_block`). Now **adding any block to the enum makes this test fail
until the shader handles it.** It will fail loudly instead of passing blind.

## ⚠️ BerryBush fork — read before applying

This brick assumes **RC23 (berry-items) is NOT applied** — i.e. there is no
`BlockId::BerryBush` variant, matching the tree you handed me. Under that
assumption the `mesher.rs` hunk removes the stray arm and the build is
restored.

**If your working tree HAS since applied RC23** (a real `BlockId::BerryBush`
exists), then:
- `git am --3way` will most likely **conflict** on the `mesher.rs` hunk. That
  is the safe outcome — it won't silently clobber.
- Resolve by **keeping** the `BerryBush => [0.55, 0.10, 0.20]` arm **and**
  adding the 13 arms from this brick. Also make sure RC23 added `BerryBush`
  to `base_color()` and `BlockId::ALL`, and gave it a shader color in
  `color_for_block` (otherwise it will render magenta and the now-exhaustive
  parity test will fail on it — which is correct).

If `cargo build` complains about `BerryBush` after applying, that's the tell
that your tree and this brick disagree on RC23 — reconcile as above.

## Apply

This is a **partial patch series**, not a full snapshot. Use the overlay/patch
tool, **not** `commands/update_from_claude_zip.sh` (that one wipes the whole
working tree and expects a complete `unendlich/` snapshot — it would blow away
unrelated in-flight work, e.g. the parallel entity/mob thread).

```bash
# from anywhere; pass your repo dir or set UNENDLICH_REPO
./toolkit/apply_from_zip_v2.sh unendlich-v0.24.87-magenta-fix.zip /path/to/unendlich-game
```

Preflight refuses on a dirty tree. The manifest `base` is the sha of the
snapshot you sent me; it won't exist in your repo, so you'll see
`WARNING: base … not present locally — applying anyway`. That's expected; the
diff applies by context. Roll back with the printed `git reset --hard`.

## Verify

**Build (also proves the compile break is fixed):**
```bash
cargo build --release -p unendlich-engine --features render
```

**Regression test (now exhaustive over BlockId::ALL):**
```bash
cargo test --release -p unendlich-engine --features render --lib \
  gpu_shader_colors_every_cpu_colored_block
```
It should pass now and would fail on any future block missing a shader color.

**On-hardware A/B (the actual magenta):**
```bash
# GPU mesher, seasonal tint off so colors are the flat base values
UNENDLICH_GPU_MESHER=2 UNENDLICH_SEASONS=0 \
  cargo run --release --bin unendlich-world --features="render,gpu,window"
```
Fly to a desert / sandstone exposure, obsidian near lava, or a copper/quartz
vein (or place oak planks / glass / pumpkin). Previously magenta, now their
real colors. Cross-check against the CPU mesher (`UNENDLICH_GPU_MESHER=0`) —
they should match.

## Out of scope (separate future bricks)

- **Missing top faces** on rendered chunks — GPU top-boundary neighbor
  sampling (a chunk's top blocks need to know the chunk above is air). Geometry
  bug in `chunk_mesh_octree.comp`'s boundary face-visibility, not color. Still
  open.
- **LOD overlap** beyond the hole effect — LOD-band management. Still open.
- **`render/gpu_meshing_octree_cpu_ref.rs::color_for_block`** is intentionally
  left as-is here. It's a minimal *diagnostic* CPU reference (12 of 59 ids;
  the rest default to magenta) and no test color-checks it, so it isn't a
  shipped bug — but if you ever render through it for a visual diff, those
  blocks will look magenta there. Tightening it into a true mirror of the
  shader table is a clean, low-risk follow-up if you want the reference mesher
  to be faithful.
