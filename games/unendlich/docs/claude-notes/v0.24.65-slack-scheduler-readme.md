# v0.24.65-slack-scheduler

## Tagline

Slack-based upload pacing: instead of a fixed per-frame upload time
budget, tighten the budget based on how much frame-time is left.
Opt-in. Stage 1 Option A from the upload-scheduler design memo.
Zero added latency. Composes with RC29 (adaptive count cap) and
RC30 (submit-phase skip).

## Status

Drafted in sandbox by Claude during the rc29-adaptive-uploads
session, stacking on RC30. Not yet built with cargo or run on
hardware. Stacks on RC30 omnibus (rebuild the bin after applying).
Ship zip: `unendlich-rc31-slack-scheduler.zip`. Strict-additive,
single file (`crates/unendlich-engine/src/bin/unendlich_world.rs`).

## What this ship does

### Before

```rust
// Upload loop checks (existing, v0.24.3 era):
if elapsed_ms > upload_budget_ms { break; }       // fixed cap, default 8ms
if upload_bytes_this_frame >= upload_bytes_budget { break; }
```

The `upload_budget_ms` is a static value set at startup from
`UNENDLICH_UPLOAD_BUDGET_MS` (default 8.0). Works as a worst-case
cap, but ignores the frame's actual progression. If other phases
were fast and we have 6ms of slack left at the 120Hz target, we
still cap at 8ms (potentially overrunning). If other phases were
slow and we're already at 12ms, we still spend the full 8ms
uploading (compounding the stall).

### After

```rust
// New entry point (slack scheduler, behind env flag):
let effective_upload_budget_ms = if slack_scheduler_enabled {
    let frame_elapsed_ms = last_frame.elapsed().as_secs_f64() * 1000.0;
    let slack_ms = (frame_target_ms - frame_elapsed_ms).max(0.0);
    upload_budget_ms.min(slack_ms.max(upload_min_ms))
} else {
    upload_budget_ms
};

// Used in the same break check, now dynamic:
if elapsed_ms > effective_upload_budget_ms { break; }
```

Math: `effective = clamp(slack, [upload_min_ms, upload_budget_ms])`.

The scheduler can only TIGHTEN, never loosen — it's bounded above
by the operator-set `upload_budget_ms`. The lower bound
(`upload_min_ms`, default 1ms) preserves forward progress when the
frame is already over budget.

## Activation

```bash
UNENDLICH_SLACK_SCHEDULER=1 cargo run --release --bin unendlich-world \
    --features="render,gpu,window"
```

Default off (env unset OR != "1"). A logged confirmation line fires
on startup:

```
[INFO] slack_scheduler: ENABLED — frame_target_ms=8.33, upload_min_ms=1.00, upload_budget_ms (cap)=8.00
```

Tunable env vars:

```bash
UNENDLICH_FRAME_TARGET_MS=8.33   # frame-budget target (default 8.33 = 120 FPS)
UNENDLICH_UPLOAD_MIN_MS=1.0      # floor; prevents starvation (default 1.0)
```

## Architecture changes

### State (~7 lines, after the submit_skip block)

```rust
let slack_scheduler_enabled = std::env::var("UNENDLICH_SLACK_SCHEDULER")
    .ok().as_deref() == Some("1");
let frame_target_ms: f64 = /* env or 8.33 */;
let upload_min_ms: f64 = /* env or 1.0 */;
```

These are READ-ONLY for the rest of the loop — no per-frame
mutation. The dynamic part is `effective_upload_budget_ms`,
computed each frame at the upload-loop entry.

### Per-frame computation (~10 lines, at upload phase entry)

`effective_upload_budget_ms` is computed once per frame, just
before the drain-and-upload loop. The cost is one `Instant::elapsed`
read (~ns) and two f64 ops.

### Existing break check (1 line changed)

The `if elapsed_ms > upload_budget_ms { break; }` becomes
`if elapsed_ms > effective_upload_budget_ms { break; }`. No other
changes to the upload loop.

## Composability with existing scheduling features

| Flag                              | Adjusts             | Signal                                       | RC   |
|-----------------------------------|---------------------|----------------------------------------------|------|
| `UNENDLICH_ADAPTIVE_UPLOADS=1`    | upload COUNT cap    | EMA of past frames' `wait_fences_ms`         | RC29 |
| `UNENDLICH_SUBMIT_SKIP=1`         | submit-phase skip   | World stationary signals (edit/load/player)  | RC30 |
| `UNENDLICH_SLACK_SCHEDULER=1`     | upload TIME cap     | This frame's elapsed time so far             | RC31 |

All three can run together. They target orthogonal metrics:
- RC29 reacts to GPU pressure (past-frame fence wait)
- RC30 reacts to world topology (anything changed?)
- RC31 reacts to CPU pacing (frame budget headroom)

## Expected effect

| Condition                                  | Expected change with RC31         |
|--------------------------------------------|-----------------------------------|
| Frame running fast (<frame_target_ms used) | Same as before (cap = 8ms)        |
| Frame running on-target                    | Same as before (cap = 8ms)        |
| Frame running slow (overshoot small)       | Cap tightens to remaining slack   |
| Frame already over budget                  | Cap = 1ms (upload_min_ms)         |

The expected net effect during burst-upload windows: shorter peak
frames at the cost of slightly slower world buildout. The world
still loads (chunks queue and retry next frame), just paced more
gently.

If the chug arc's hypothesis is correct (CPU memcpy into
HOST_COHERENT memory → GPU cache-coherency cost on next read),
RC31 should reduce the chug-frame magnitude by shrinking the
memcpy burst inside a slow frame. It does NOT eliminate the
per-upload cost — that's Stage 3 (off-thread upload + DEVICE_LOCAL
backing).

## Risks and known issues

- **Pathological starvation**: if the frame is *consistently* over
  budget by a lot, `upload_min_ms` (1ms default) is the only forward
  progress. World loading would be slow. Mitigation: the flag is
  opt-in; if observed, bump `UNENDLICH_UPLOAD_MIN_MS` higher or
  disable the flag.
- **Interaction with RC29**: RC29's adaptive count cap could let
  through more uploads than RC31's time budget allows; in that
  case RC31's break check fires first, dropping the rest. This is
  the intended behavior, but worth A/B-testing the combination.
- **`last_frame` timing accuracy**: the slack calculation reads
  `last_frame.elapsed()`. `last_frame` is set at start-of-frame
  (line ~999 in the bin). The math is correct as long as the
  variable isn't shadowed or reused. Spot-check confirms
  `last_frame = now` appears exactly once in the file.
- **frame_target_ms vs actual frame target**: the default 8.33ms
  (120 FPS) is a guess. Operators on 60Hz hardware should set
  `UNENDLICH_FRAME_TARGET_MS=16.67`. Operators on 240Hz should
  set 4.17. Mismatch creates wrong-direction pacing — too lax on
  60Hz, too tight on 240Hz.

## Future stages (per design memo)

- **Stage 1 Option D**: forward-biased shell walk — chunks the
  player is moving toward get meshed first. ~100 LoC.
- **Stage 2**: priority queue over the upload pool — within the
  budget, prefer chunks in the camera frustum. ~150 LoC.
- **Stage 3**: off-thread upload + DEVICE_LOCAL backing + staging
  buffer ring. ~600-800 LoC. THE real architectural decoupling
  the user flagged.
