# Playtest notes — 2026-09-02 batch

What changed in the engine since the 2026-09-01 build, what each change
should do on your machine, how to turn each one off if it misbehaves, and
what to send back. Commits `6b95e651..aa9ea94a` (bundle
`c14unified-022-delta`). Nothing in this batch has run on a GPU — every
verification below is a type-check or a headless test. Treat the first
run as the test.

## Changes, in the order you'll feel them

| change | what it should do | if it misbehaves | proof so far |
|---|---|---|---|
| **Vertices packed on the meshing worker** (`ChunkMesh::pack`, `MeshResult.packed`) | Render thread does a memcpy per chunk instead of a per-vertex quantize loop. Fewer LONG FRAMEs during a streaming burst on the CPU-mesher path — the path `UNENDLICH_PROFILE=honeykrisp` and the phone use. | No switch; the pack function is unchanged, only the thread differs. A mesh looking wrong here would look wrong before too. | lib + fullgame `cargo check` green |
| **Persisted edits + octree rebuild on the loader worker** (`ChunkLoader::set_world_root`) | No file read on the main thread per arriving chunk; edited chunks stop costing a 32³ rebuild in the frame. | No switch. Symptom to watch: an edit you made not being there after re-entering the area (would mean the worker read the wrong root). | lib `cargo check` green |
| **Walk cursor** (`request_visible` banks up to 1 024 unloaded coords; completions refill from it) | The O(rd³) sphere walk runs on chunk crossings only, not every frame while streaming. Most visible at rd ≥ 12. | No switch. Symptom: chunks in view that never load while the loader is idle (cursor logic wrong). Log `MGR_REQUEST_US` should drop. | lib `cargo check` green; gate function unit-tested |
| **Mesher ring** (`gpu_meshing_octree`, only with `UNENDLICH_GPU_MESHER=2`) | Mesh dispatches are submitted, not waited on; batch sized by a per-chunk GPU-time model; compute queue when the driver has a distinct one. The five 450–860 ms spikes after warmup should not happen. | `UNENDLICH_GPU_MESH_INFLIGHT=1` = old synchronous shape. `UNENDLICH_GPU_MESH_DISPATCH_US` (default 3000 shared queue / 16000 dedicated) bounds one dispatch's queue time. `UNENDLICH_GPU_MESHER=1` or the honeykrisp profile avoids this mesher entirely. | `cargo check` green; ring layout tests; **the Vulkan sync model is unverified** |
| **Readback stride fix** (same mesher) | GPU-meshed chunks stop being geometric garbage (every vertex after the first was read at a 28 B stride from a 24 B buffer since r594). If anyone saw broken meshes with `GPU_MESHER=2`, this is that. | none | static assert + test |
| **Pool buffer CONCURRENT across queue families** | Only when the driver gives a distinct compute family. Correctness, not speed. | none (`INFLIGHT=1` still uses the compute queue; `GPU_MESHER=1` avoids it) | `cargo check` green |

| **Binary mesher** (`UNENDLICH_MESHER=binary`, opt-in) | Near-LOD CPU meshing with bit-op visibility/merging; same emitters, same picture (coverage-tested against the greedy mesher). 3–4× faster on plain terrain; ~1.2× on surface chunks because those are dominated by the special emitters and grass-tuft decoration, not by meshing. | Unset the env. | in-crate parity tests; timing report |
| **`UNENDLICH_MESHER_PLAIN_TOPS=1` / `UNENDLICH_MESHER_PLAIN_SIDES=1`** (with `MESHER=binary`) | Jittered/subdivided grass tops and sagging soft sides become flat merged quads: a surface chunk goes from ~236 K to ~157 K vertices and 13 ms → 3 ms. **Visual change** — this is the A/B the numbers are asking for. The remaining 127 K vertices are the grass tufts (sub-voxel grids, ~280 vertices each). | Unset. | parity test on coverage; timing report |

| **`UNENDLICH_TUFT_STYLE=cross`** (any mesher) | Grass tufts as a double-sided cross-quad (8 vertices) instead of a sub-voxel grid (~280). Same density, same sway tags. On a surface chunk: 127 K → ~4 K decoration vertices. **Visual change.** `=none` removes tufts for the no-decoration baseline. | Unset (default `grid`). | in-crate test (8 verts / 24 indices per tuft, both windings); timing report |
| **`UNENDLICH_TOP_SUBDIVISION=2`** (existing knob, default 8) | Weathered tops are a 9×9 vertex grid per face at 8 (81 vertices, 128 triangles); at 2 they are 3×3 (9 vertices). Keeps sag + weathering, drops the special-emitter share from ~16 to ~5 vertices per face. | Unset. | arithmetic on the emitter; not separately timed |

### The surface-chunk A/B, in one table

Per grass/dirt surface chunk (the in-crate timing chunk; real chunks vary):

| configuration | mesh time (1 core) | vertices | look |
|---|---|---|---|
| today (greedy, grid tufts, subdivision 8) | 10–16 ms | 236 K | reference |
| `MESHER=binary` | 8–13 ms | 236 K | identical |
| `MESHER=binary TOP_SUBDIVISION=2 TUFT_STYLE=cross` | est. 3–4 ms | est. ~40 K | same sag/jitter/soft sides, cross tufts, coarser weathering |
| `MESHER=binary PLAIN_TOPS=1 PLAIN_SIDES=1 TUFT_STYLE=cross` | ~1–2 ms | ~34 K | flat merged terrain, cross tufts |

The third row is the one to try first: it changes the least and removes
~85 % of the vertex data that every downstream stage (pack, memcpy,
mesh pool, draw) pays for. Vertex data per surface chunk drops from
5.6 MB (`Vertex`) / 1.9 MB (wire) to ~1 MB / ~320 KB.

Removed: `UNENDLICH_GPU_POOL_PIN`, `UNENDLICH_GPU_POOL_EARLY_UNLOCK` (the
lock-held mode they toggled no longer exists; pinning is unconditional on
the ring path). Setting them does nothing.

## What to send back

The startup lines, verbatim:
- `Compute queue acquired: family=… distinct=…` — decides whether the
  compute-queue half of the ring applies on that machine.
- `OctreeGpuMesher initialized: ring inflight=… slot_chunks=… queue=…`
- `octree pool: CONCURRENT across queue families […]` (if it appears)
- `octree-gpu-mesh-dispatcher: ring inflight = …, slot cap = …, per-dispatch budget = …`

And a `perfbisect` run before/after (same knobs as 2026-09-01) — the
`gpu_spike` count and p99 are the two numbers this batch is meant to move
on the desktop; `MGR_DRAIN_US` / `MGR_REQUEST_US` per frame during a
straight-line drive are what the loader/cursor changes move. Every 10 s
the octree dispatcher logs `per_chunk_gpu=…us (N samples) in_flight=…`:
that number is the model the batch sizer runs on — if it's wildly off
from what the frame timers say, the sizer is wrong, not the driver.
