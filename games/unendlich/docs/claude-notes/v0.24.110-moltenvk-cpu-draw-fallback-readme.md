# v0.24.110 — auto CPU draw path when drawIndirectCount is absent (MoltenVK fix)

Your Mac's `vulkaninfo` confirmed the build runs and MoltenVK 1.4.1 is live on the
M4 Max — but it also reported `VkPhysicalDeviceVulkan12Features.drawIndirectCount
= false`. The chunk renderer calls `cmd_draw_indexed_indirect_count`, which is
**illegal without that feature**, so the engine would have errored/crashed the
moment it drew chunks.

## Fix

`WorldRenderer::new` now queries `drawIndirectCount` and, when it's absent,
forces the existing **CPU-driven per-chunk draw path** (the `UNENDLICH_INDIRECT=0`
fallback that's been maintained all along). This is the right call on MoltenVK
twice over: the GPU-count draw isn't supported, and even plain
`multiDrawIndirect` is CPU-loop-emulated by MoltenVK — so CPU-side culling + a
per-chunk draw loop is both correct and the better performer there.

Cross-platform and behavior-preserving: on Asahi/Linux `drawIndirectCount` is
true, so `use_indirect` is unchanged and the GPU-driven path runs exactly as
before. The fallback only triggers where the feature is genuinely missing.

## What to expect when you run now

It should reach a rendered frame. Run in the same isolation order:

1. plain (no env vars) → world renders via the CPU draw path. You'll see one log
   line: `drawIndirectCount unsupported … forcing the CPU-driven per-chunk draw
   path.` That's expected on MoltenVK, not an error.
2. `UNENDLICH_POSTFX=1` → should match the plain look.
3. `UNENDLICH_POSTFX=1 UNENDLICH_BLOOM=1` → soft glow; first real run of bloom.

Keep validation on while bringing it up:
`VK_INSTANCE_LAYERS=VK_LAYER_KHRONOS_validation`.

## Lower-probability things to watch (report if they fire)

- **Swapchain format**: MoltenVK offers B8G8R8A8_UNORM/SRGB + R16F + A2B10. If
  swapchain creation complains, the format picker needs a tweak — send the error.
- **Sampleable depth**: v0.24.107 made the depth format require `SAMPLED_IMAGE`
  (for SSR later). D32_SFLOAT should satisfy it on MoltenVK; if device/image
  creation complains about the depth format, that's the spot.
- **Perf**: with the CPU draw path, very high chunk counts are CPU-encode bound.
  Fine for bring-up; a Mac-tuned draw path is a later optimization.
