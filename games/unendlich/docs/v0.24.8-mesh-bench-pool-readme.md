# v0.24.8-mesh-bench-pool — bench extended with real CPU baselines

A bench-only update. No engine code changes — extends `gpu-mesh-bench`
to compare GPU sparse v2 against the realistic CPU alternatives.

## Why

v0.24.7's bench compared GPU v2 to a single-threaded sequential
`mesh_chunk_naive`. That's not what production runs. Production uses
`MeshingPool` with 4 workers, running the greedy + sky-lit mesher.

Wiring v2 into production replaces that pool. The question is: how
does v2 actually compare to what it'd replace? That's the call this
bench answers.

## What the bench now reports

Five paths timed over the same 36 chunks:

1. **CPU naive sequential** — what v0.24.6 measured. 1-thread, naive.
2. **CPU naive parallel (4 workers)** — same kernel, parallelized.
   The upper bound on what naive can achieve at production worker count.
3. **MeshingPool (4 workers, greedy+sky)** — the actual production
   path. Greedy mesh with sky lighting baked in. Not visually
   equivalent to GPU v2 output.
4. **GPU sparse v1 (one chunk per submit)** — v0.24.6 baseline.
5. **GPU sparse v2 (batched)** — v0.24.7 implementation.

Plus three speedup ratios against v2:
- v2 vs CPU naive sequential
- v2 vs CPU naive parallel
- **v2 vs MeshingPool** — the headline number for the production
  wiring decision.

## Predictions

CPU naive parallel: ~3-4 ms total. The single-threaded version took
~11 ms; 4-way parallelism should land around 11/4 = 2.7 ms with some
overhead.

MeshingPool: harder to predict because the greedy + sky-lit path is
slower per chunk than naive. Probably 4-8 ms total. Could be slower
or comparable to GPU v2.

GPU v2: ~4.6 ms (consistent with v0.24.7's measurement).

The interesting comparison is GPU v2 vs MeshingPool. Three possible
outcomes:

- **GPU v2 substantially faster (>1.5×):** Strong case for Layer A.3
  production wiring. Real performance win on top of strategic direction.
- **GPU v2 comparable (0.8-1.5×):** Wash on pure perf; Layer A.3
  decision becomes purely strategic. Worth doing because the
  architecture direction depends on it, but no acute pressure.
- **GPU v2 slower (<0.8×):** Production wiring would regress
  performance. Need to widen the gap before A.3 — larger batch,
  zero-copy, greedy on GPU.

## Honest concerns

1. **The MeshingPool path includes channel/sync overhead.** Submit
   to a bounded channel, workers pull, results go back via another
   channel. That overhead is roughly proportional to chunk count.
   The bench includes it because it's part of what production pays;
   but it means raw greedy mesher time is a bit lower than the pool
   number suggests.

2. **The bench creates a fresh MeshingPool for each run.** Pool
   construction spawns 4 threads. That setup cost is included in
   the timing, which is unfair. To isolate: I could move pool
   creation outside the timer. Defer — the cost is small (~ms for
   thread spawn) and consistent.

3. **Submit-loop with sleep(50us) when queue full** introduces
   small latency that wouldn't be present in production (production
   has flow control via the chunk loader's pacing). Real impact
   tiny but worth knowing.

4. **GPU v2 numbers from this run might differ slightly from
   v0.24.7** because system load varies. Run a couple times if
   they look inconsistent.

5. **Cloning the chunk before submitting to the pool** allocates.
   The original Chunk is borrowed by the parallel-naive pass; pool
   path needs ownership via Arc<Chunk>. That clone is included in
   the pool's timing.

## What comes next

Based on the v2 vs MeshingPool number, the Layer A.3 decision becomes:

- If GPU wins clearly: ship A.3 next. Production wiring with the
  existing path.
- If GPU loses: don't ship A.3 yet. Either raise MAX_BATCH_CHUNKS to
  64+ for one quick win, or move toward zero-copy / greedy-on-GPU as
  the perf-gap closing work.
- If wash: ship A.3 for strategic reasons (advances the architecture
  destination) but tell the user it's strategic not performance.
