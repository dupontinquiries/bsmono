# v0.24.2c.5 — Shutdown hang root-caused and fixed

Two-line change to `MeshingPool::Drop` + a regression test that proves the fix.

## The bug

Diagnostic logs from the c.4 playtest immediately localized the hang:

```
[14:39:45 INFO] Shutdown complete.
[14:39:45 INFO] Pre-exit: dropping mesh_pool (may join worker threads)...
<hang>
```

Looking at `MeshingPool::Drop`, it was:

```rust
drop(real_tx);                            // close request channel
for h in self.workers.drain(..) {
    let _ = h.join();                     // wait for workers — hangs here
}
```

And the worker loop was:

```rust
while let Ok(req) = req_rx.recv() {
    let mesh = mesh_chunk(...);           // takes 1-50ms
    if res_tx.send(result).is_err() { break; }
}
```

The bug: the result channel is `bounded(queue_capacity * 2)`. During gameplay the render thread drains it every frame, keeping it from overflowing. When shutdown begins, the render loop stops. Any workers mid-cycle finish their mesh, call `res_tx.send`, and **block** because the result channel is full and nobody is draining it.

A blocked worker never returns to the `while let Ok(req) = req_rx.recv()` line — so it never sees that the request channel closed. `join()` waits forever.

## The fix

```rust
let (_, dummy_rx) = bounded::<MeshResult>(1);
let real_rx = std::mem::replace(&mut self.result_rx, dummy_rx);
drop(real_rx);                            // ← NEW: drop result_rx first

drop(real_tx);                            // close request channel
for h in self.workers.drain(..) {
    let _ = h.join();
}
```

Dropping `result_rx` makes any in-flight `res_tx.send` return `Err` immediately. The worker hits the `break`, returns, and `join()` completes.

## Regression test

`drop_does_not_hang_when_result_channel_full` reproduces the exact failure mode:

1. Single-worker pool with small queue capacity.
2. Submit ~32 requests in a retry-on-backpressure loop until the worker has processed enough to fill the result channel (>8 sends) and is blocked.
3. Wait 200ms to ensure the worker is wedged in `res_tx.send`.
4. Drop the pool on a separate thread, with a 2-second timeout.

The test verifies both:
- **Correctness**: drop completes (no hang).
- **Performance**: drop completes in <1 second (with the fix it's <10ms).

I verified the test catches the regression by temporarily reverting just the fix:

| State | Result |
|---|---|
| Fix in place | passes in 0.70s |
| Fix reverted | fails in 2.76s (timeout fires) |

So the test is sensitive to exactly the fix.

## Belt-and-suspenders kept for now

The c.4 ship added explicit drops + `std::process::exit(0)` at the bottom of main. **I'm keeping that scaffold in place** for two reasons:

1. The diagnostic logs (`Pre-exit: dropping X` / `dropped X`) will catch any future drop bug immediately.
2. Other drops (chunk_manager, window, glfw) haven't been validated to terminate cleanly on Asahi — the c.4 hang fired before any of them ran.

After your next playtest, look at the log tail. The expected output is:

```
[INFO] Shutdown complete.
[INFO] Pre-exit: dropping mesh_pool ...
[INFO] Pre-exit: dropped mesh_pool          ← NEW (no longer hangs here)
[INFO] Pre-exit: dropping chunk_manager ...
[INFO] Pre-exit: dropped chunk_manager      ← if missing, that's the next hang
[INFO] Pre-exit: dropping window ...
[INFO] Pre-exit: dropped window
[INFO] Pre-exit: dropping glfw ...
[INFO] Pre-exit: dropped glfw
[INFO] Pre-exit: calling std::process::exit(0)
```

If you see all "dropped X" lines for everything, we can remove the `process::exit(0)` in a future ship and rely on natural unwinding. If something else hangs, that line tells us what to fix next.
