# v0.24.31-versioned-pool

## Tagline

Mesher's pool uploads skip when `(coord, version)` is already
resident. Pure perf win, ~130 ms/sec back at steady state.

## Status

Built autonomously between play-test cycles. Compiles in head;
NOT built with cargo or run on hardware. Layered on top of three
prior untested ships (v0.24.29, v0.24.30 — atop the playtested
v0.24.28).

## What this ship does

The mesher's dispatcher in v0.24.29..v0.24.30 called
`pool.upload(coord, octree)` for every chunk in every batch.
That always replaced the slot — allocator churn AND a fresh
memcpy of the octree bytes. For most chunks the bytes are
identical to what's already there (the chunk's contents don't
change between dispatches unless the player edits the world).

This ship adds version tracking to the pool:

- `OctreeBufferPool` gains a `content_versions: HashMap<ChunkCoord, u64>` map.
- New method `upload_if_changed(coord, octree, version)` —
  returns the existing slot if `version` matches, otherwise calls
  `upload` and records the new version.
- `OctreeBatchInput` gains a `version: u64` field threaded
  through from `MeshRequest::version_at_submit`.
- The mesher's dispatcher uses `upload_if_changed`.

Eviction is updated to clear the content_version entry too —
otherwise a re-upload after evict could skip incorrectly.

## What's preserved

- `OctreeBufferPool::upload` is unchanged. The renderer's
  always-replace path (used by the probe and by the v0.24.29-
  skipped post-mesh upload for mode 0/1) keeps that semantics.
- Existing unit tests pass — versions default to 0, so a chunk
  uploaded at version=0 stays at version=0 (no churn either way).

## Expected steady-state savings

Per typical chunk:
- ~10K octree nodes × 40 B = ~400 KB per chunk
- Memcpy @ 6 GB/s ≈ 67 µs per chunk

Per batch:
- 64 chunks × 67 µs = ~4.3 ms saved per batch

Per second (at observed steady-state ~30 batches/sec):
- ~30 × 4.3 ms = ~130 ms/sec saved

That's significant headroom — could push the mesher from 184 fps
to ~250+ on M2 Max, or open the same headroom for other work.

## Failure mode

Pure perf optimization. The pool's `upload_if_changed` is correct
even if version comparison goes wrong:
- Same version, same content: skip upload. ✓
- Same version, different content: skip upload, GPU reads stale
  data. Would visibly look like the chunk didn't update. **This
  is the actual risk** — if a future code path mutates a chunk in
  place without bumping version, we'd silently mesh stale data.
- Different version, same content: redundant upload (worst case
  v0.24.30 behavior).
- Different version, different content: re-upload, correct. ✓

The streaming layer's version bookkeeping is already covered by
the mesh-cache version checks; if version reliably tracks content
mutation, this optimization is correct.

## Rollback

Revert to v0.24.30 behavior:
- Remove `content_versions` field + `upload_if_changed` method.
- Change `OctreeBatchInput.version` back to absent.
- Change dispatcher's `pool.upload_if_changed(...)` back to
  `pool.upload(...)`.
- Revert meshing_pool's `OctreeBatchInput` construction to not
  pass `version`.

The shader, ChunkMetaGpu struct, and CPU reference all stay
valid — this ship is dispatcher/pool side only.
