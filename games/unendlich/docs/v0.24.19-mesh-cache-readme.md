# v0.24.19-mesh-cache — renderer-owned mesh cache

Targets the chug root cause confirmed by v0.24.18's probe data:
GPU upload pressure → drm_syncobj_wait stalls → render-thread
sleeping 85% of chug samples. Fix: stop re-uploading meshes when
the player revisits already-seen chunks.

## How it works

When a chunk leaves the streaming radius, instead of returning its
GPU buffers to the pool, the renderer parks them in a HashMap keyed
by `(coord, lod)`. The chunk-manager regenerates source data
on revisit; the mesh pool produces a fresh mesh; but inside
`upload_prebuilt_mesh_at_lod`, we check the cache first. If we have
an entry for `(coord, lod)` AND its version matches the fresh
mesh's version, restore the cached buffers and discard the
supplied mesh. **Skip the upload entirely.**

Version mismatch (chunk was edited between eviction and revisit)
drops the cached entry and falls through to normal upload.

LRU eviction when the cache is full.

## How to use

```bash
UNENDLICH_MESH_CACHE_SIZE=512 \
UNENDLICH_RENDER_DISTANCE=10 \
UNENDLICH_VSYNC=0 \
UNENDLICH_MAX_UPLOADS_PER_FRAME=32 \
UNENDLICH_UPLOAD_BUDGET_MS=8.0 \
  cargo run --release --features="render,gpu,hot-shaders" \
    -p unendlich-engine --bin unendlich-world
```

Cache size 512 reserves up to 512 chunks worth of GPU buffer slots.
Smaller worlds work fine with 256; very wide explorations might
want 1024.

Default is `0` (disabled), which preserves pre-v0.24.19 behaviour
exactly — useful for A/B comparing.

## What to watch in the FPS log

New line (only when cache enabled):

```
  cache: hits=312 misses=4 size=487/cap=512
```

- `hits`: cached buffers restored. Each hit = one chunk's worth of
  upload bytes saved.
- `misses`: version stale on cache entry (chunk edited between
  eviction and revisit). These cost a cache slot AND a fresh upload
  — the worst case.
- `size/cap`: current cache occupancy.

In a free-play session with `rd=10` and lots of wandering, expect
hits to grow steadily after the initial fill. Misses should stay
low unless you're doing heavy block editing.

## Pairing with the thread probe

If you want to measure the chug reduction directly, run with both:

```bash
UNENDLICH_THREAD_PROBE=1 \
UNENDLICH_MESH_CACHE_SIZE=512 \
UNENDLICH_RENDER_DISTANCE=10 \
UNENDLICH_VSYNC=0 \
  cargo run --release ... unendlich-world
```

Then compare probe-report output between a `MESH_CACHE_SIZE=0` run
and a `MESH_CACHE_SIZE=512` run on the same scenario. The chug%
should drop. The `drm_syncobj_array_wait_timeout` wchan should
appear less often. Lower wait_fences in the cpu_zones log.

## What this ship does NOT do

- Doesn't reduce mesh-pool CPU work. Mesh pool still produces a
  fresh mesh on every revisit; cache discards it. Wasted CPU; the
  win is GPU upload bytes.
- Doesn't compress. Cached buffers are stored as-is. VRAM cost is
  real. Compression is a follow-up.
- Doesn't help the first-load chug (cold cache).
- Doesn't change anything when `UNENDLICH_MESH_CACHE_SIZE=0`.

## Honest concerns

1. **The win depends on revisit ratio.** If you wander linearly
   without backtracking, cache hits stay near zero and we just
   pay VRAM cost. The telemetry tells you.

2. **VRAM cost.** Each cached entry holds one mesh-pool slot.
   Realistic chunk meshes are usually much smaller than the
   per-slot max, but cache size 1024 still reserves substantial
   memory. Watch how this plays in practice.

3. **The cache only kicks in if the SAME mesh gets re-meshed at the
   SAME LOD.** Crossing a LOD band counts as a different cache key
   (`(coord, Near)` vs `(coord, Mid)`). So a chunk you visit at
   close range, walk away from, then approach from far again
   produces a `Mid` mesh first, then maybe `Near` again — the close
   `Near` cache is preserved but the new far visit doesn't hit it.

4. **Restore doesn't free the supplied mesh CPU side.** The
   `ChunkMesh` value passed to `upload_prebuilt_mesh_at_lod` is
   already constructed; we discard it implicitly when we return Ok
   early. RAII drops it; no leak. Just wasted CPU.
