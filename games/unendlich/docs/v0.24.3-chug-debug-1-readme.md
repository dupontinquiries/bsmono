# v0.24.3-chug-debug-1 — wait_fences side-channel instrumentation

First ship of the v0.24.3 chug investigation. **Read-only diagnostic
instrumentation** — does NOT change render scheduling, only adds
visibility into what was happening when `vkWaitForFences` blocked the
render thread.

This is Experiment 4 from the c.13/c.17/c.17-revert design notes,
finally built.

## What it does

When `vkWaitForFences` blocks for more than 10ms, the engine emits a
`wait_fences_spike` event to `events.jsonl` with two key fields:

- **`wait_ms`** — how long the wait was.
- **`last_submit_to_wait_ms`** — time elapsed between the most recent
  `vkQueueSubmit` on this frame slot and the start of the wait that
  followed it.

The ratio of those two tells us whether GPU or CPU side was the
bottleneck for that frame:

| `submit→wait` time      | Interpretation                                   |
|-------------------------|--------------------------------------------------|
| Near 0 (< 20% of wait)  | **GPU-bound**. CPU submitted then immediately    |
|                         | hit wait. Long shadow/main/froxel pass, lots of  |
|                         | geometry, or a barrier stall.                    |
| Large (> 80% of wait)   | **CPU-bound**. CPU did work between submit and   |
|                         | wait, then waited briefly. The CPU work between  |
|                         | (uploads, descriptor updates, game tick) was     |
|                         | what consumed the budget.                        |
| Mixed                   | Both contributed. Look at GPU lifetime stats     |
|                         | from the same run for which zone spiked.         |

## What's NOT in this ship

- No new metrics beyond the two above. Per c.17-a's regression
  cautionary tale, this ship is deliberately minimal. We add more
  signals if/when these two leave a question unanswered.
- No scheduling changes. Read-only instrumentation only.
- No engine renames or refactors.
- No new env vars. The 10ms threshold is hardcoded; it's the right
  number for hunting outliers without spamming events.jsonl.

## How to use

After migrating and rebuilding:

```bash
cd ~/Code/unendlich-development/unendlich-game

# 0. Migrate.
./commands/update_from_claude_zip.sh unendlich-v0.24.3-chug-debug-1.zip
git add -A && git commit -m "Update to v0.24.3-chug-debug-1"
./commands/tag_current_version.sh

# 1. Rebuild.
cargo build --release -p unendlich-launcher -p unendlich-analyze

# 2. Run the chug_capture spec (or any rd=2 free-play scenario).
cargo run --release -p unendlich-launcher -- \
    run tests/specs/chug_capture.unendtest --version @HEAD

# (or for fresh free-play if preferred:)
# UNENDLICH_RENDER_DISTANCE=2 \
#     cargo run --release --features="window,render,gpu,hot-shaders" \
#     --bin unendlich-world
# Walk around 30-60s. Cross chunk boundaries deliberately. Ctrl-C.

# 3. Diagnose the spikes.
cargo run --release -p unendlich-analyze -- wait_spikes
```

The `wait_spikes` output looks like:

```
wait_fences_spike events (all runs in events.jsonl): n=87

  wait_ms                 : n=87  min=10.5  p50=42.1  p90=180.3  max=410.2
  last_submit_to_wait_ms  : n=87  min=0.3   p50=8.7   p90=45.0   max=120.1

  Worst 10 spikes:
       wait_ms  submit→wait_ms       interpretation
         410.2             1.2  GPU-bound (CPU waited)
         385.6           120.1               mixed
         280.4             5.0  GPU-bound (CPU waited)
         ...

  Diagnosis:
    GPU-bound spikes (CPU waited immediately): 71
    CPU-bound spikes (CPU did work between):    8
    Mixed:                                       8
```

That diagnosis is the data we need. Paste it back and we identify the
correct fix:

- **If most spikes are GPU-bound**: a specific render pass is occasionally
  taking ~100-400ms. Likely shadow at low rd is fine in p50 but
  pathologically slow during a chunk-cross moment when the cull
  produces an unusual chunk set. Fix: investigate per-pass GPU spikes
  via existing `gpu_timer` zones, possibly add work-budget limits to
  shadow culling.
- **If most spikes are CPU-bound**: render thread is doing 100-400ms
  of work between submit and the next wait. Likely mesh upload memcpy
  is happening on the render thread when it shouldn't. Fix: offload
  uploads to a worker thread or staging buffer.
- **If mostly mixed**: both contributing. Less clear what to fix
  first; we'd need additional instrumentation.

## Path forward

After the diagnostic data is in:

1. **Fix the dominant spike category** (one ship, targeted at
   GPU-bound OR CPU-bound, not both).
2. **Re-run rd=2 free-play** and confirm spike count + distribution
   drops measurably.
3. **Then consider raising the FPS ceiling** via the
   `UNENDLICH_FPS_CAP` work filed in
   `v0.24.3-chug-investigation-plan.md` (Path 2).

The `wait_spikes` subcommand stays in the engine permanently — even
once chugs are fixed, regression detection benefits from having this
view available. No reason to revert this instrumentation.

## Honest concerns I want to flag

- **Three engine warnings** that the test runner mentioned. These
  pre-date c.17-a and are not introduced by this ship. They're
  in code unrelated to the instrumentation. Filing for cleanup but
  not now.
- **The 10ms threshold is arbitrary.** At 120Hz the frame budget is
  8.33ms, so any wait over 10ms is already a missed frame. But at
  240Hz (4.16ms budget), a "10ms wait" is 2.4× over budget. Future
  ships may want this configurable. For now 10ms catches the chugs
  we care about and avoids spam.
- **`last_submit_to_wait_ms`** doesn't directly measure mesh upload
  CPU time. It measures everything between submit and wait, which
  includes upload + game tick + the wait_for_fences setup itself.
  If diagnosis says "CPU-bound" we may still need a follow-up
  instrumentation ship to break down which CPU work was the culprit
  (specifically targeting upload memcpy).
