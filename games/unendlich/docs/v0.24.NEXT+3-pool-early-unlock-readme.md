# v0.24.NEXT+3 — octree pool early-unlock (burst-stutter mitigation)

## What

The octree GPU mesher held the octree-pool lock across
upload + dispatch + fence-wait + **readback**. The readback reads only
the mesher's own HOST_COHERENT output buffers (counter/vertex/index),
never the octree pool — and the GPU finishes reading the pool at
fence-signal. So holding the pool lock through the readback is
unnecessary; it just makes main-thread octree uploads wait longer.

This ship splits the readback into its own method (`readback_outputs`)
and, behind a new flag, drops the pool lock right after the fence wait,
before the readback:

```
UNENDLICH_GPU_POOL_EARLY_UNLOCK=1
```

## Why it might help your stutter

The pool-lock contention is ~30µs at steady state (author's measure —
not a stutter). But during chunk-storm bursts — huge render distance, a
fresh chunk neighborhood streaming in — many main-thread octree uploads
(~10µs each) stack up behind a run of back-to-back GPU mesh batches.
With `MAX_FRAMES_IN_FLIGHT=1` there's no CPU/GPU overlap to hide that
wait, so it lands directly on the frame. Releasing the pool lock before
the readback memcpy lets those uploads drain during readback instead of
queueing behind it, shortening the worst-case burst stall.

This is **one candidate lever for the stutter, not a confirmed fix.**
See BACKLOG.md — the honest next step is a launcher capture to confirm
pool-lock waits actually appear in the stutter before relying on this.

## Why it's safe (and why it's still gated)

Safety argument: the submitted command buffer contains only this
batch's compute dispatch. `wait_for_fences` returns only after that
dispatch completes. The dispatch is the only GPU work reading the
octree pool. Therefore at fence-signal the GPU is done with the pool,
and a main-thread eviction can't invalidate an in-flight read. The
pre-existing code comment already asserted exactly this ("After this
point the GPU has finished reading the octree slots, so it's safe for
main thread to evict") — this ship just acts on it earlier.

Gated default-off anyway: releasing a lock earlier around GPU memory is
the kind of change that deserves a hardware confirmation before becoming
default. With the flag unset, the lock scope is byte-for-byte the old
behaviour (readback still under the lock). Flip it on to A/B.

## Files changed

- `crates/unendlich-engine/src/render/gpu_meshing_octree.rs`
  - `record_and_submit` → `record_submit_wait` (readback removed; now
    ends at the fence wait).
  - New `readback_outputs` (the extracted readback; pool-lock-free).
  - `dispatch_and_readback` → `dispatch_and_wait` (no longer reads back).
  - `mesh_chunks_batch`: read `UNENDLICH_GPU_POOL_EARLY_UNLOCK`; on the
    early-unlock path `drop(pool)` after the fence, before
    `readback_outputs`. Pure refactor otherwise — same operations, same
    order, same data.

No new tests: the GPU readback path needs a GPU to exercise, and the
`mesh_chunk_octree_cpu_reference` tests cover a *separate* function this
ship doesn't touch. Validation is the hardware A/B below.

## How to verify

Build clean and run the existing sanity set (unchanged at 28 — these
guard the surrounding code didn't regress):

```bash
./scripts/sanity.sh
```

Then A/B on hardware under burst load (high render distance, fly into
unloaded terrain):

```bash
# baseline (flag off) — note the worst-frame / stutter frequency
... <your playtest flag mix> ...
  cargo run --release --bin unendlich-world --features render,gpu

# treatment (flag on)
... <same mix> ... UNENDLICH_GPU_POOL_EARLY_UNLOCK=1 \
  cargo run --release --bin unendlich-world --features render,gpu
```

Or capture both under the launcher and compare diag:

```bash
cargo run --release -p unendlich-launcher -- \
  run tests/specs/chug_capture_rd8.unendtest --version @HEAD
cargo run --release -p unendlich-launcher -- diag
# then re-run with the flag set in the spec's [env] and compare
```

Expected if pool-lock contention is part of the stutter: lower
worst-frame time during bursts with the flag on, no visual change. If
no difference, the stutter is elsewhere (shadow regen / allocation /
FIF=1) — see BACKLOG.md.

## Rollback

Flag-gated: just don't set `UNENDLICH_GPU_POOL_EARLY_UNLOCK`. To remove
the refactor entirely:

```bash
git checkout <prev-tag> -- crates/unendlich-engine/src/render/gpu_meshing_octree.rs
```

See `docs/ROLLBACK.md`.
