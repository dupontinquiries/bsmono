# v0.24.24-octree-sampler — first opt-in consumer of the octree path

Foundation + integration + first real consumer for the architecture
documented in `architecture-v1.md §3.1` and `architecture-v1-addendum.md
§A1.2, §A3.1, §A4`.

## What's new in v0.24.24 (since v0.24.23-octree-propagation)

- **Player block-selection raycast now routes through
  `ChunkManager::raycast_octree`.** Replaces the legacy DDA path
  (`raycast::raycast` over the dense `BlockSampler`). Same break /
  place semantics, but with the octree's hierarchical-skip property:
  rays through homogeneous regions visit one node per region instead
  of one cell per cell. The 6-block player vision ray sees the win
  for any chunk dominated by uniform underground stone or sky air.
  Code in `bin/unendlich_world.rs` around the mouse-input handler.

- **`raycast::BlockFace::from_normal((i32, i32, i32))`** — bridge
  helper that maps the `OctreeWorldRayHit::normal` field (unit
  vector in {-1, 0, 1}^3) to the legacy `BlockFace` enum. Lets
  callers adopt `raycast_octree` without reworking downstream
  face-attachment logic (`hit_face.neighbor(hit_cell)` still works).

- **`OctreeBlockSampler`** in `world/chunk_manager.rs` — adapter
  struct that implements `physics::BlockSampler` over the per-chunk
  octrees. Holds its own `Arc` of the octrees map, so it can be
  passed across threads or moved into closures without coupling to
  manager lifetime. Hand out via `ChunkManager::octree_sampler()`.

  The existing `&ChunkManager` BlockSampler impl is unchanged — it
  still hits the dense path because that's the right default for
  scattered single-point queries. The sampler is the explicit
  opt-in for new code that wants octree-canonical sampling.

## What lands (full picture)

### Foundation

1. **`world/octree.rs`** — `OctreeNode` (40 bytes, repr(C) for GPU SSBO
   consumption), `OctreeArray` flat-buffer encoder with sparse
   homogeneous-subtree collapse, `sample`, `to_chunk` round-trip,
   `mark_path_modified` + `mark_region_modified` for reverse-propagation
   dirty stamps, `region_stable_since` for cache-deferment short-circuit.
2. **`world/octree_region.rs`** — `Aabb3`, `RegionShape::{Cube, Sphere,
   Box}`, `RegionRead` (one-shot dense snapshot, O(1) `get_local`, cheap
   `is_stable` validity check).
3. **`world/octree_raycast.rs`** — hierarchical raycast with front-to-back
   slab descent. Predicate is now `impl Fn(BlockId) -> bool + Copy`.
4. **`world/octree_scheduler.rs`** — `DeferQueue<WorkItem>` that skips
   items whose dependency region is stable.
5. **`shaders/octree_sample.glsl`** — GPU-side struct + traversal sketch.
6. **`bin/octree-bench`** — measurement tool.

### Integration

7. **`world/chunk_loader.rs`** — channel type changed from `Chunk` to
   `LoadedChunk { chunk, octree }`. Workers build the octree alongside
   the chunk so per-chunk build cost is parallelized across the worker
   pool, off the main thread's drain path.

8. **`world/chunk_manager.rs`** structural additions:
   - `octrees: Arc<DashMap<ChunkCoord, Arc<OctreeArray>>>` — parallel
     map, identical lifecycle to `chunks`.
   - `world_edit_tick: Arc<AtomicU64>` — monotonic counter, used as the
     `tick` argument to `octree.mark_path_modified` /
     `mark_region_modified`.
   - Helpers: `install_chunk(chunk, octree)`,
     `replace_edited_chunk(new_chunk, edit_local)`,
     `replace_batch_edited_chunk(new_chunk, edit_aabb)`.

### Consumer entry points

9. **Public API on `ChunkManager`** (cumulative across v0.24.23 + v0.24.24):
   - `octree(coord: ChunkCoord) -> Option<Arc<OctreeArray>>`
   - `world_edit_tick() -> u64`
   - `raycast_octree(origin, dir, max_t, predicate) -> Option<OctreeWorldRayHit>`
     — world-level hierarchical raycast. Walks the chunk grid; dispatches
     each segment into the chunk's octree.
   - **(new v0.24.24)** `octree_sampler() -> OctreeBlockSampler` —
     octree-backed `BlockSampler` adapter.

10. **Edit paths wired through helpers**:
    - `set_block` → `replace_edited_chunk` (rebuilds octree + stamps
      cell)
    - Tick-batch apply → `replace_batch_edited_chunk` (rebuilds octree
      + stamps root conservatively)
    - `bump_chunk_version` and `bump_neighbor_if_edge` — version-only,
      no octree change

11. **Eviction** — `evict_distant` removes from `octrees` alongside
    `chunks`.

12. **(new v0.24.24)** **Player block-selection raycast** in
    `bin/unendlich_world.rs` — routed through `raycast_octree`.

## What this ship looks like at runtime

- Every chunk loaded into the engine has a sparse octree built on the
  loader worker and stored in `ChunkManager.octrees`.
- Every edit rebuilds that chunk's octree and bumps the global edit
  tick. Every eviction drops the octree.
- The player's break/place ray traverses through the octree (one node
  per homogeneous region rather than per cell).
- `OctreeBlockSampler` is available via `mgr.octree_sampler()` for any
  new consumer that wants octree-canonical sampling.

The renderer still draws what the dense mesher produced from `Chunk`.
Mesher migration to octree-consumption is the next ship.

## What it looks like end-to-end

```
chunk_loader worker
  → generate Chunk
  → build OctreeArray::from_chunk
  → send LoadedChunk { chunk, octree }
ChunkManager.update drain
  → install_chunk inserts both into chunks + octrees maps
ChunkManager.set_block (player breaks/places)
  → clone_for_edit on Chunk
  → replace_edited_chunk:
      - clones existing octree (Arc-shared, so cheap)
      - octree.set_block(lx, ly, lz, new_block, tick)  ← INCREMENTAL
      - inserts new Arc<Chunk> + new Arc<OctreeArray>
ChunkManager.raycast_octree (player aim, future mobs/fluids/light)
  → walks chunks the ray crosses
  → per-chunk: octree_raycast::raycast_chunk (hierarchical skip)
  → returns OctreeWorldRayHit
unendlich_world player aim
  → chunk_manager.raycast_octree(...)
  → BlockFace::from_normal(hit.normal)
  → break or place via chunk_manager.set_block
  → octree updated incrementally, mesher invalidates via version bump
ChunkManager.evict_distant
  → drops chunks + octrees together
```

The octree is the canonical-state substrate from the moment a chunk
loads until the moment it evicts. Every edit propagates to it. Every
raycast benefits from its hierarchical skip. Item region reads and the
defer queue have the substrate they need; they wire in as we add
features that use them.

## Wire format

40-byte `OctreeNode`, repr(C). See module docstring in
`world/octree.rs` for the bit layout. GLSL `OctreeNode` in
`shaders/octree_sample.glsl` is bit-for-bit equivalent for the
v0.24.24+ shader work.

## On the "compression" framing

The octree compresses **compute work**, not bytes:

- Surface chunks are 5–10× *larger* than dense storage.
- Underground / sky / homogeneous chunks compress dramatically.
- The real win is hierarchical skip: raycast through 32 blocks of air
  visits one node; same ray on a dense grid visits 32 cells. Region
  queries answer at the highest stable ancestor. Cache-deferment skips
  whole subtrees when nothing changed.

Each win compounds across consumers and across ticks.

## What this ship deliberately does NOT do

- **No mesher rewrite.** The CPU mesher still operates on `Chunk`. The
  octree is now AVAILABLE; the mesher migration is v0.24.24.
- **No GPU shader yet.** GLSL header is a sketch.
- **No DeferQueue consumer wired in.** The queue type exists with unit
  tests; integration into the meshing pool is v0.24.25.
- **No CPU overlay layer** (architecture §3.2). The "predicted edits"
  layer comes once the substrate has measured real consumers.
- **No cross-chunk region reads.** Single-chunk region reads work; the
  cross-chunk wrapper waits for a world-level octree-of-chunks.

## Cost expectation

Per-chunk octree build (on worker thread): O(`CHUNK_VOLUME`) ≈
200–800 µs for typical surface chunks. Underground / sky much less
(early collapse). Parallelized across 12 workers; total wallclock
overhead during chunk streaming is small.

Per-edit overhead (on the editing thread, incremental path):
- `OctreeArray::set_block`: O(depth) ≈ 5 levels. First edit through a
  collapsed subtree adds up to 40 nodes (split-on-write); subsequent
  edits along the same path are even cheaper. Total: a few µs.
- Tick-batch apply: one rebuild per edited chunk (still O(volume)
  there — the rebuild path is preserved for batch cases since the
  edits are already dense by then), with AABB-tightened dirty stamp.

The `octree-bench` tool now includes an "Edit-cost bench" section
that reports the actual µs/edit numbers on your hardware.

## Collapsed-leaf cache invalidation: resolved

Previous foundation docs noted a known limitation: a fully-collapsed
homogeneous chunk that got edited would stamp its single root leaf
with the new tick, which invalidated cache validity for the whole
chunk's volume. The split-on-write expansion in `set_block` now
expands the affected octant down to the edited cell, so
`region_stable_since` queries on unaffected sibling regions of the
same chunk correctly report stable.

Tested by `set_block_resolves_collapsed_leaf_poisoning` in
`octree::tests`.

## Honest concerns

1. **Build never verified by cargo.** Hand-checked against existing
   APIs. Most likely failure: a small Rust syntax or lifetime issue.

2. **Brief race window in `replace_edited_chunk`.** Drops the dashmap
   read guard before re-inserting. Concurrent same-chunk edits could
   race. Benign for single-player; multi-player fix is to hold the
   write guard through octree update.

3. **The incremental-edit path is fast but the cloned octree allocates
   a fresh `Vec<OctreeNode>` per edit.** For high-frequency edits this
   could churn the allocator. Future optimization: pool allocations or
   use Arc::make_mut to mutate in-place when there's only one ref.

4. **No measurement yet of `raycast_octree` vs legacy `raycast::raycast`
   on the player path.** The migration is logically equivalent; cargo
   bench could quantify the win.
